# dev-cycle（開発サイクルの呼び出し口）

手順の本文は `docs/process/index.md` が正。このスキルは Claude Code でその手順を回すときの段取りだけを書く。

## 0. ルートを判定する

`apps/`・`packages/` の振る舞いが変わるならフル。変わらない（docs のみ・試作・小修正）ならライトで、このスキルは使わずコミット前テストだけ通す。迷ったらフル。

## 1. プラン作成

- 始める前に main の CI が通っているか確かめる（セッション開始時のフックの出力。出ていなければ `node scripts/check-main-ci.mjs`）。失敗していれば先に人間に知らせる
- `docs/process/prompt-sample.md` の「1」の依頼文に沿う。質問は `grilling` スキルの手法（フロンティア単位のラウンド）で尽くす
- 仕様ページ（`docs/cartagraph/`）に書いてあることは質問せず読む。未解決論点（`docs/open-questions.md`）に関わる判断だけ人間に聞く
- 書き始める前に `node scripts/branch-id.mjs new feat <名前>` で id 付きのブランチを切る（main にはコミットできない）
- 質問が尽きたら `docs/plans/<日付>-P<id>-<機能>.md` に8項目で書く
- 要望ファイル（`docs/backlog/`）の状態を「検討中」にし、プランのファイル名を足す（手順の本文は `docs/process/index.md`）
- 書き終えたら、「背景」に挙げた正式仕様の決着と各決定事項を突き合わせる（食い違いは人間に確認）

## 2〜3. プランのレビュー

別セッション（または別のサブエージェント）で依頼文「2」「3」を実行し、P0 を直してから次へ進む。依頼文「2」の観点は、プランの中身で絞る（設計整合は必ず。仕様整合・運用は当てはまるときだけ。`docs/process/index.md` の手順2）。

**ここでセッションを区切る。** プランの先頭の状態の行に、済んだ手順と人間に確かめた結果、次のセッションの手順と等級を書いてから、人間に `/clear` を頼む。頼むときも、次の手順と等級（と下の「モデルの等級の割り当て」のモデル）を示す（`docs/process/index.md`「セッションを分ける」）。

## 4〜5. 実装とテスト

新しいセッションで、プランだけを読んで始める（前のセッションの会話は持ち込まない）。

- 依頼文「4」。先に `AGENTS.md` のルール適用表に従って該当ルールを読む
- テストは `tdd` スキルで Red → Green → Refactor
- プランにない変更が必要になったら、実装せず止まって報告する

## 6. AIレビュー（並列）

`design-reviewer`・`edge-case-reviewer`・`spec-reviewer` を並列で起動し、P0〜P2 に整理する。P2 は直さず `docs/architecture/known-issues.md` に1行で記録する。P0・P1 は直して、指摘を出した観点のサブエージェントだけで再レビューする（`docs/process/rules/review.md`「終わりの条件」）。3ラウンドを超えたら人間に裁定を求める。

起動するときは Agent ツールの `model` で等級を指定する（定義の `inherit` は変えない）。既定は `design-reviewer` が `opus`、`edge-case-reviewer`・`spec-reviewer` が `sonnet`（`docs/process/rules/review.md`「レビュー観点」）。

## モデルの等級の割り当て（Claude Code）

プランの「実装順」の等級は、Claude Code では次のモデルにする。

- 強い … `opus`
- 標準 … `sonnet`
- 軽い … `haiku`（Explore など調査のサブエージェントは、`model: haiku` を指定して起動する）

メインのセッションのモデルは、等級が変わるところで人間に `/model` での切り替えを頼む（自分では切り替えられない）。プランの作成・見直し（1〜3）は強い、実装とテスト（4〜5）は標準が既定。

## 7. 人間レビュー

依頼文「7」で説明だけを行う。判定はしない。説明の前に、変更した画面をブラウザで通しで操作して確かめる（`browser-check` スキル。サブエージェントに任せ、スクリーンショットはパスで添える）。

人間レビューで追加の要望が出たら、受け入れ条件に必要なものだけを同じPRで対応し、それ以外は `docs/architecture/known-issues.md` か次のサイクルに回す（`docs/process/index.md`）。

## 8. push・振り返り

- `eng-practices` でセルフレビューしてから push（PR 運用なら `create-pr`）
- マージしたら、要望ファイルのサイクルの状態・PR 番号・更新日を直す（`node scripts/branch-id.mjs new docs <名前> --id P<id>` で同じ id のブランチを切り、main へ早送りで取り込む）
- マージまで済んだら、プランに AI レビューの結果と「人間レビューの結果」の節が書かれていることを確かめ（無ければ人間に聞いて書く。書き漏れは次の `branch-id.mjs new` が止める）、人間に `/clear` を頼む（次は振り返りで、等級は強い、と示す）。振り返りは新しいセッションで、プランと PR を読んで行う
- 依頼文「9」で振り返り、`docs/process/evolution.md` の候補への追記案を出す。採用は人間が決める
