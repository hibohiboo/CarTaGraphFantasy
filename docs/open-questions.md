# 未解決論点トラッカー

カルタグラフの設計と、開発の仕組み（技術・運用）で、まだ決まっていない論点だけを管理する。grillingによる深掘りは、この一覧から優先順位をつけて進める。

決着したら、決まったことを該当するページ（ゲームの仕様、開発の仕組みならアーキテクチャのページ）へ、決めた理由・経緯を[デザイナーノート](notes/index.md)へ書き、ここからは消す。これまでに決着した論点の一覧は[デザイナーノート](notes/index.md#決着した論点)にある。

決まっていないことのうち、決着を待たずに仮のルールで動かしているもの（自動戦闘、GM不在のソロの進行、キャラクター作成の配分、シーンの目的・終了条件など）は、ここではなく[仮ルール](provisional/index.md)に1件ずつ置く（二重に持たない）。

## 次に詰める候補

- **カウント制の1ラウンドの行動回数と数値バランスの両立** — [数値バランスの相場観](cartagraph/balance.md)の「基本攻撃でHPの2〜3割」と「3〜5ラウンドで決着」は、カウント制で1ラウンドに何回行動できるか（行動値とコストの比）が決まらないと同時に満たせない。例えば行動値10〜12・コスト3では1ラウンドに3〜4回行動でき、1〜2ラウンドで決着してしまう（自動戦闘の検討で判明）。
- **正史グラフ・比較体験の「原型」と、シナリオの版・コピーの対応** — シナリオは[下書きと公開版](cartagraph/scenario-flow.md#シナリオの公開)に分かれ、製作者が公開し直すたびに新しい版ができ、前の版も残る。またシナリオをコピーして別のシナリオにでき、コピーは親（どのシナリオのどの版から作ったか）を覚える（[要望](backlog/scenario-draft-api.md)の C3）。[正史グラフ](cartagraph/graph.md#正史グラフとpc発見グラフ)（シナリオ単位）とその「正式採用」による更新が、公開版と下書きのどちらに当たるのか、公開し直すと正史グラフはどうなるのか。[比較体験](cartagraph/comparison-and-titles.md#比較の母集団同じシナリオの定義)の「原型」は、版が替わっても同じ原型として束ねるのか、コピーしたシナリオ（親を辿れる）は親と同じ原型か別の原型か（シナリオの下書きの API のレビューで挙がった）。

## 仕様の細部の未決

優先順位はまだ付けていない。仕様のページには、ここへの1行のリンクだけを置く。

- **カルタグラフの名称** — 概念名を「カルタグラフ」とする方向で、最終決定ではない。中核システム名に「カルタグラフ・コア」を使うかも未決（[検討の経緯](notes/cartagraph.md)）
- **最終的なカード種別** — [カード・デッキの考え方](cartagraph/card-and-deck.md#カード)の種別の例は、現時点の例にすぎない
- **ロケーションカードの分類** — [カードの裏表](cartagraph/card-face-back.md#カード種別ごとの裏表パターン)は、1シーン1ロケーションを想定した暫定分類。シーンとロケーションの関係は今後変わり得る
- **制作側の学習的アンロックの既読状態の保存単位** — アカウントに紐づけるかローカル保存か。アカウントシステムの設計時に決める（[アンロック](cartagraph/unlock.md#制作側の学習的アンロック)）
- **解放済みカードプールの保存単位** — アカウントに紐づけるかローカル保存か。アカウントシステムの設計時に決める（[成長とキャラメイク](cartagraph/character-growth.md)）
- **公開範囲の「特定の人」の指定方法** — 友人リスト等。アカウントシステムの設計時に決める（[PC間の比較体験と称号タグ](cartagraph/comparison-and-titles.md)）
- **別物になったシナリオの比較の母集団** — カスタマイズが大きく異なり別物になったシナリオを、同じシナリオの母集団に含めるか（[PC間の比較体験と称号タグ](cartagraph/comparison-and-titles.md)）
- **同じ称号タグが複数回贈られたときの表示** — 実装のときに決める（[PC間の比較体験と称号タグ](cartagraph/comparison-and-titles.md)）
- **セッションの破棄** — [グラフの役割](cartagraph/graph.md#セッションスナップショットとマージ)の「破棄」（スナップショットごと捨て、何にも反映しない）を、誰が・いつ行えるか、終了の宣言とどう分けるか。GM 不在のセッションでは誰が破棄するか。所有者が結果を[なかったことにする要望](backlog/pc-session-opt-out.md)との関係も（[イベントの流れ](architecture/event-flows.md)を書いていて挙がった）
- **敵の HP・能力の非公開と開示** — 戦闘画面の試作は敵の HP を見せない想定だが、「看破」などのスキルで開示する仕組みは設計していない

## 開発の仕組み

- **バックエンド API・グラフ DB の構成** — Lambda・ECS などの具体的な構成は、セッション管理機能のフェーズで決める
- **バックエンド実装の着手順** — セッション管理系の画面も先にモックで作っているので、バックエンドをどの順で実装するかは改めて判断する（[Webアプリの仕組み](architecture/web-app.md)）
- **TanStack Query のキャッシュ設定** — データ種別ごとのチューニングは、実バックエンドに接続して実レイテンシ・更新頻度を測ってから決める
