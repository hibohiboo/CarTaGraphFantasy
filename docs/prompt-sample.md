
# 概要
開発フローのステップで使う依頼分。【】の穴を埋めて使う。

# 1. プランドキュメントの作成（インタビュー式）

```
【機能名】を作りたい。概要：【２～３行で】
参考： docs/requirements/【要件定義ファイル】と関連コード【ディレクトリ】

まず実装に入らず、プランを書くために必要な質問を私にすること。
技術面・エッジケース・トレードオフについて、答えにくい質問ほど価値がある。
質問が尽きたら、プランを .claude/plans/[ファイル名].mdに８項目(概要・背景・詳細設計・テスト影響範囲・新規テストケース・実装順・コミット前テスト実行・スコープ外)で書き出すこと。
実装順には、どのタスクをどのモデル・サブエージェントに任せるかの割り当てまで書くこと
```

# 2. プランのAI相互レビュー（観点別）
実装セッションとは別のセッションで

```
.claude/plans/[プランファイル].mdをレビューすること。私は書いた本人ではない前提で読む。
観点: [設計整合性/セキュリティ/運用/ビジネス整合性 から１つ]
判定の基準: [docs/rules/の該当ルール または 要件定義ファイル]
指摘はP0(実装前に必ず直す)/P1(推奨)/P2(軽微)に分類し、プランのどいの記述が・どの基準と・なぜズレるのかを１件ずつ示すこと。
```

# 3. テスト網羅のレビュー

```
.claude/plans/[プランファイル].md の「新規テストケース」だけをレビューすること。
要件定義の受け入れシナリオと突き合わせ、
[1] シナリオに対応するテストが欠けていないか
[2] 境界値の両側・異常系が入っているか
[3] 実装しないと決めたスコープ外がテストに紛れていないか
を確認し、足りないテストケースを提案すること
```

# 4. 実装
レビュー済プランを渡すだけにする。

```
.claude/plans/[プランファイル].md の実装順に従って実装すること。
プランの割り当てどおり、[調査/ユーティリティ]はサブエージェントに任せてよい。
プランにない変更が必要になったら、実装せずに立ち止まって報告すること。
```

# 5. テストの実装を全通過

```
プランの「新規テストケース」をテストコードに落とすこと。
各テストは先に実行して失敗（Ｒｅｄ）を確認してから実装を直す。
最初から通ってしまったテストは、実装済かassertが弱いかを判定して報告する。
最後に[コミット前テスト実行のコマンド]を実行し、全通過の出力を見せることｄ。
```

# 6. 実装のＡＩ相互レビュー（観点別並列）

```
実装が終わった。次の３体のサブエージェントを並列で実行し、報告をＰ０からＰ２に整理して返すこと。
- design-reviewer: プランドキュメントとの認識
- edge-case-reviewer: 異常系と境界値の抜け
- security-reviewer: セキュリティ観点
```

# 7. 人間のレビュー（ＡＩへの壁打ち）
ＡＩに判定させない唯一の型。
厚みは機能の重要度で考え、警備のような機能なら省略してよい。

```
実装した【機能名】について、レビューする私に説明すること。判定はしなくてよい。
1. 変更の要点を、データの流れがわかる粒度で説明する。
2. 設計判断を３つまで挙げ、それぞれ採らなかった選択肢と併記する。
3. 各判断の根拠が、 .claude/plans/[プランファイル]/ の何処かにあるかを引用して示す。プランに書いていないものは「実装時の判断」と明示
4. 壊れた時に影響が大きい箇所を、理由とともに挙げる。権限を確認できないものは推測で進めず「不明」と答えること
```

# 8. テスト駆動リファクタリング
機能単位ではなく定期実行する。安全網の確認から始めさせるのが型。

```
【対象ディレクトリ】をリファクタリングすること。機能の変更はしない。
先に対象のテストを実行して全部Ｇｒｅｅｎであることを確認し、そこから１変更ごとにテストを回して、Ｇｒｅｅｎをたもったまま進めること。
観点: １ファイル１責務に反する肥大したファイルの分割、重複した処理の集約、docs/rules/【アーキテクチャルール】との乖離の解消。
テストが赤くなったら、その変更を巻き戻して報告すること。
```
