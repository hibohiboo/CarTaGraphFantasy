# 開発プロセス（AIエージェントとの協働）

このプロジェクトは、人間とAIコーディングエージェントが協働して進める。ここでは、1つの機能を作るときに回す**開発サイクル**と、サイクルの経験からプロセス自体を更新していく**体制の進化**という2つのループを定める。

この章は開発プロセスの正式ページ（SSOT）である。エージェント向けの入口はリポジトリ直下の `AGENTS.md` で、ツール固有の設定（`.claude/` 配下のサブエージェント・スキル）は、ここに書かれた手順を呼び出す薄い層に留める。

出典：書籍『プロフェッショナルAI駆動開発』のサンプル構成（AGENTS.md・rules・agents・skills・依頼文雛形）を、このプロジェクトの構成に合わせて移植した。移植時の判断は[体制の進化ログ](evolution.md)に残している。

## 全体像

```text
開発サイクル（1機能＝1サイクル）
  1. プラン作成（インタビュー式）
  2. プランのAIレビュー
  3. テスト網羅レビュー
  4. 実装
  5. テスト全通過
  6. 実装のAIレビュー（3観点並列）
  7. 人間レビュー（AIが説明・人間が判定）
  8. push・振り返り
        │
        ▼
体制の進化（候補 → 評価 → 採用／却下）
        │  ルール・依頼文・スキルを更新
        └────────────────────▶ 次のサイクルの 1. へ
```

## 開発サイクル

### 適用範囲（フルとライト）

| ルート | 対象 | 手順 |
|---|---|---|
| **フル** | `apps/`・`packages/` の振る舞いが変わる変更（機能追加、仕様反映、リファクタリング） | 下表の1〜8をすべて回す |
| **ライト** | `docs/` のみの修正、UI試作、振る舞いを変えない1ファイル程度の小修正 | プラン・AIレビューを省略してよい。コミット前テスト（`pnpm web:typecheck && pnpm web:test`、docs なら `pnpm docs:build`）は必ず通す |

迷ったらフルにする。ライトで始めて途中で `apps/`・`packages/` の振る舞いに手が伸びたら、そこで止めてプランを書く。

### 手順

| # | ステップ | 主体 | 成果物・判定 |
|---|---|---|---|
| 1 | **プラン作成（インタビュー式）** | AIが質問し、人間が答える（`.claude/skills/grilling` の手法） | `docs/plans/<日付>-<機能>.md` に8項目（後述） |
| 2 | **プランのAI相互レビュー** | 実装とは別セッションのAI。観点（設計整合／仕様整合／運用）を1つずつ | P0〜P2の指摘。P0はプラン修正 |
| 3 | **テスト網羅レビュー** | AI | 「新規テストケース」節と仕様の受け入れ条件を突き合わせ、不足を提案 |
| 4 | **実装** | AI（レビュー済みプランだけを渡す） | プラン外の変更が必要になったら実装せず報告 |
| 5 | **テストの実装と全通過** | AI（`.claude/skills/tdd` の手順） | 各テストは先にRedを確認。最後に全通過の出力 |
| 6 | **実装のAI相互レビュー** | 3体のサブエージェントを並列（design-reviewer／edge-case-reviewer／spec-reviewer） | P0〜P2に整理。P0・P1は修正して再レビュー |
| 7 | **人間レビュー** | AIが説明し、人間が判定する（AIに判定させない唯一の型） | データの流れ・設計判断と採らなかった選択肢・壊れたときの影響箇所 |
| 8 | **push・振り返り** | 人間とAI | [体制の進化](#体制の進化)へ候補を出す |

各ステップの依頼文は[依頼文サンプル](prompt-sample.md)に雛形がある。レビューの優先度分類と終了条件は[レビュールール](rules/review.md)が正。

定期作業として、機能単位ではなく**テスト駆動リファクタリング**（安全網の確認から始め、1変更ごとにテストを回す）を回す。依頼文は同じく[依頼文サンプル](prompt-sample.md)を参照。

### プランドキュメントの8項目

`docs/plans/<日付>-<機能>.md` に、次の見出しで書く。

1. **概要** — 何を作るか（2〜3行）
2. **背景** — なぜ今それか。対応する仕様ページ（`docs/cartagraph/` 等）と未解決論点
3. **詳細設計** — 触るファイル、データの流れ、`packages/domain` の型変更の有無
4. **テスト影響範囲** — 既存テストのうち影響を受けるもの
5. **新規テストケース** — 正常系・境界値の両側・異常系・既存挙動の回帰
6. **実装順** — タスクの順序と、どのタスクをどのモデル・サブエージェントに任せるか
7. **コミット前テスト実行** — 通すコマンド
8. **スコープ外** — 今回やらないことを明記

## 体制の進化

カルタグラフ本体の[進化候補の評価](../concept/index.md#進化候補の評価決着)と同じ型で、開発プロセス自体を更新する。

- **記録（誰でも）** — サイクルの途中で「ルールが足りなかった」「ルールが邪魔だった」「依頼文が通じなかった」「モデルを変えたら回らなくなった」に気づいたら、人間でもAIでも[体制の進化ログ](evolution.md)の候補に追記する。再発は必須条件ではなく裏付け材料。
- **評価（人間が裁定）** — サイクル末の振り返りで人間が採用／却下を決める。スコアリングはせず、観点（他のモデル・ツールでも回るか、SSOTを壊さないか、手間に見合うか）を明文化した自由裁定。
- **反映** — 採用したら `docs/process/` のルール・依頼文・`.claude/` のスキルを更新し、ログに日付と理由を残す。却下も削除せず理由付きで残す。

## モデル・ツールに依存しない基盤

特定のモデル（現在は Claude Fable）や特定のツール（Claude Code）が使えなくなっても回るように、次の原則を守る。

1. **知識はモデルではなくリポジトリに置く。** ルール・チェックリスト・依頼文雛形・プラン・進化ログを文書化し、モデルの賢さに頼らず同じ品質の作業を再現できるようにする。弱いモデルほど、ルールを読ませて手順どおりに動かす。
2. **入口はツール非依存の `AGENTS.md`。** Claude Code・Codex・Cursor など多くのエージェントが読む慣習ファイルを正とし、`CLAUDE.md` はそれを読み込むだけにする。
3. **ツール固有層は薄く、本文は `docs/process/` を指す。** サブエージェント定義・スキルは呼び出し口であり、手順の本文を持たない。
4. **モデルを固定しない。** サブエージェント定義の `model` は `inherit`、設定ファイルで特定モデルを指定しない。モデルの向き不向きはプランの「実装順」で都度割り当てる（調査・定型作業は軽いモデル、設計判断・レビューは強いモデル）。
5. **機械的な安全網を増やす。** 型検査・テスト・ビルドはCIで、lint・フォーマットはコミット前の git フックで必ず回し、モデルの質に依存しない検証を積み上げる。AI に lint 結果を読ませてトークンを使うより、機械で止める。
6. **人間が裁定する点を固定する。** ルールと仕様の矛盾、P0・P1の指摘が3ラウンド循環したとき、プラン外の変更、未解決論点に関わる実装判断は、AIが決めずに人間へ渡す。
7. **サイクルは小さく。** 1サイクル＝1プラン＝1回のpush（またはPR）。弱いモデルでも1サイクルを完走できる粒度に切る。
8. **ツール固有の記憶を正にしない。** Claude Code の自動メモリは他のツールから見えないため、プロジェクトとして残す知識は `docs/` に書く。

これらの原則を段階的に整備する計画は `docs/plans/2026-09-16-dev-process-foundation.md` にある。

## この章の設計原則

1. 開発プロセスも、カルタグラフと同じく「記録→評価→採用／却下」の進化ループで育てる。
2. 正はツール非依存の文書（`AGENTS.md`・`docs/process/`）に置き、ツール固有の設定はそれを呼ぶだけにする。
3. 判定を人間に残す点（矛盾・循環・スコープ外・未決仕様）を明文化し、AIに委ねすぎない。
