# 依頼文サンプル

[開発サイクル](index.md)の各ステップで AI エージェントに渡す依頼文。【】の穴を埋めて使う。どのモデル・どのツールでも同じ依頼ができるように、必要な参照先をすべて依頼文の中に書く。

Claude Code では `/dev-cycle`、`/grilling`、`/tdd`、`/eng-practices`、`/create-pr` のスキルが対応する手順を呼び出すが、依頼文をそのまま貼っても同じ結果になることを前提にする。

## 1. プランドキュメントの作成（インタビュー式）

```text
【機能名】を作りたい。概要：【2〜3行で】
参考：仕様ページ docs/cartagraph/【該当ページ】.md、未解決論点 docs/open-questions.md、関連コード apps/web/src/【ディレクトリ】

まず実装に入らず、プランを書くために必要な質問を私にすること。
技術面・エッジケース・トレードオフについて、答えにくい質問ほど価値がある。
仕様ページに書いてあることは質問せず自分で読む。未解決論点に関わる判断は私に聞く。
書き終えたら、「背景」に挙げた正式仕様の決着と各決定事項を1件ずつ突き合わせ、食い違いがあれば私に確認すること。
質問が尽きたら、プランを docs/plans/【日付-機能名】.md に8項目
（概要・背景・詳細設計・テスト影響範囲・新規テストケース・実装順・コミット前テスト実行・スコープ外）で書き出すこと。
実装順には、どのタスクをどのモデル・サブエージェントに任せるかの割り当てまで書くこと。
```

## 2. プランのAI相互レビュー（観点別）

実装セッションとは別のセッションで。

```text
docs/plans/【プランファイル】.md をレビューすること。私は書いた本人ではない前提で読む。
観点：【設計整合性／仕様整合性／運用 から1つ】
判定の基準：【docs/process/rules/ の該当ルール または docs/cartagraph/ の該当仕様ページ】
指摘は P0（実装前に必ず直す）／P1（推奨）／P2（軽微）に分類し、
プランのどの記述が・どの基準と・なぜずれるのかを1件ずつ示すこと。
```

## 3. テスト網羅のレビュー

```text
docs/plans/【プランファイル】.md の「新規テストケース」だけをレビューすること。
仕様ページ docs/cartagraph/【該当ページ】.md の受け入れ条件と突き合わせ、
[1] 条件に対応するテストが欠けていないか
[2] 境界値の両側・異常系が入っているか
[3] 実装しないと決めたスコープ外がテストに紛れていないか
[4] 人間が補えない進行（GM不在の進行・自動戦闘など）を、画面から最後まで通すテストがあるか
を確認し、足りないテストケースを提案すること。docs/process/rules/testing.md の骨抜き禁止に照らすこと。
```

## 4. 実装

レビュー済みプランを渡すだけにする。

```text
docs/plans/【プランファイル】.md の実装順に従って実装すること。
先に AGENTS.md と docs/process/rules/architecture.md を読むこと。
プランの割り当てどおり、【調査／ユーティリティ】はサブエージェントに任せてよい。
プランにない変更が必要になったら、実装せずに立ち止まって報告すること。
```

## 5. テストの実装と全通過

```text
プランの「新規テストケース」をテストコードに落とすこと。docs/process/rules/testing.md に従う。
各テストは先に実行して失敗（Red）を確認してから実装を直す。
最初から通ってしまったテストは、実装済みか assert が弱いかを判定して報告する。
最後に pnpm web:typecheck && pnpm web:test を実行し、全通過の出力を見せること。
```

## 6. 実装のAI相互レビュー（観点別並列）

```text
実装が終わった。次の3体のサブエージェントを並列で実行し、報告を P0 から P2 に整理して返すこと。
- design-reviewer：プランドキュメントとの整合（不足と過剰）
- edge-case-reviewer：異常系と境界値の抜け
- spec-reviewer：docs/ の正式ページ（SSOT）との整合
P0・P1 があれば修正し、再レビューに戻すこと。3ラウンドを超えたら止めて私に裁定を求めること。
```

Claude Code 以外のツールでは、観点ごとに別セッションを立てて `.claude/agents/` の各ファイル本文をそのまま依頼文にする。

## 7. 人間のレビュー（AIへの壁打ち）

AIに判定させない唯一の型。厚みは機能の重要度で決め、軽微な機能なら省略してよい。

```text
実装した【機能名】について、レビューする私に説明すること。判定はしなくてよい。
0. 説明の前に、変更した画面をブラウザ（pnpm web:dev か Playwright）で通しで操作して確かめ、スクリーンショットを添える。先へ進めない・表示が崩れるなどが見つかったら、説明より先に報告する。
1. 変更の要点を、データの流れ（画面 → queries → MSW ハンドラ → fixtures）がわかる粒度で説明する。
2. 設計判断を3つまで挙げ、それぞれ採らなかった選択肢と併記する。
3. 各判断の根拠が docs/plans/【プランファイル】.md のどこにあるかを引用して示す。プランに書いていないものは「実装時の判断」と明示する。
4. 壊れたときに影響が大きい箇所を、理由とともに挙げる。確認できないものは推測で進めず「不明」と答えること。
```

## 8. テスト駆動リファクタリング

機能単位ではなく定期実行する。安全網の確認から始めさせるのが型。

```text
【対象ディレクトリ】をリファクタリングすること。機能の変更はしない。
先に pnpm web:typecheck && pnpm web:test を実行して全部 Green であることを確認し、
そこから1変更ごとにテストを回して、Green を保ったまま進めること。
観点：1ファイル1責務に反する肥大したファイルの分割、重複した処理の集約、
docs/process/rules/architecture.md との乖離（barrel export など）の解消。
テストが赤くなったら、その変更を巻き戻して報告すること。
```

## 9. 振り返り（体制の進化）

サイクルの最後に。

```text
今回のサイクル（docs/plans/【プランファイル】.md）を振り返ること。
ルールが足りなかった・邪魔だった・依頼文が通じなかった・手戻りが起きた箇所を挙げ、
docs/process/evolution.md の「候補」に追記する文案を提案すること。採用の判断は私がする。
docs/process/ の既存ルールと矛盾する提案は、矛盾として明示すること。
```
