# レビュールール（AI相互レビューと人間の裁定）

## タイミング

- `apps/`・`packages/` の振る舞いを変える変更は、push（PR運用になったらマージ）前に必ず1回、**実装とは別セッションのAI**でレビューする
- `docs/` のみの修正・UI試作は省略してよい（[開発サイクルのライトルート](../index.md#適用範囲フルとライト)）
- P0・P1 の修正後は再レビューに戻す

## レビュー観点

実装の経緯は渡さず、差分（`git diff`）とプランだけを渡して次の観点で読む。

1. **仕様整合** — `docs/` の正式ページ（SSOT）と食い違っていないか。用語・ロール・ゾーン・提案の状態などの意味がずれていないか。未解決論点を勝手に決めていないか
2. **プラン整合** — プランの受け入れ条件・テストケースに対応する変更があるか。プランにない変更が混入していないか
3. **テスト** — 変更に対応するテストの有無。骨抜きテストの検出（[テストルール](testing.md)）
4. **設計** — 1ファイル1責務・境界・barrel 禁止（[アーキテクチャルール](architecture.md)）
5. **異常系** — 境界値の両側、空データ、非同期の失敗経路
6. **セキュリティ** — 現状はフロントのみで重点は低い。バックエンド着手後に認可・インジェクション・秘密値の露出を必須観点に昇格する

Claude Code では観点2を design-reviewer、観点5を edge-case-reviewer、観点1を spec-reviewer のサブエージェントが担当する（`.claude/agents/`）。他のツールでは、この観点ごとに別セッションを立てて同じ依頼をする。

## 指摘の優先度分類

- **P0（必須修正）** — 仕様との矛盾・データ破壊・機能の誤り。push／マージをブロックする
- **P1（推奨修正）** — 深刻なバグの芽・テスト網羅の欠落。合理的理由があればスキップ可
- **P2（軽微）** — スタイル・命名。時間があれば修正。なければ TODO 化し、[既知の問題](../../architecture/known-issues.md)に記録する

各指摘には `file:line` と根拠（どのルール・どの仕様ページとずれるか）を添える。判断に迷う点は「要確認」として分ける。

## 終わりの条件

- P0・P1 がゼロなら合格
- P2 だけなら修正せず push／マージしてよい
- 3ラウンドを超えて指摘が循環したら、**人間が裁定する**（AIどうしで決着させない）

## 静的レビューの限界

- 差分を読むAIレビューでは、表示崩れ・空データの無限ローディング・状態の取り違えといった実行時のバグは捕まらない。UIや実行時の挙動を変えたら、最後は `pnpm web:dev` で自分（人間）が動かして確かめる
- ページ描画テスト（`pages.test.tsx`）は「描画できる」ことしか保証しない。見た目の判断は人間の仕事
