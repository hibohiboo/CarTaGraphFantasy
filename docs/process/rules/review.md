# レビュールール（AI相互レビューと人間の裁定）

## タイミング

- `apps/`・`packages/` の振る舞いを変える変更は、push（PR運用になったらマージ）前に必ず1回、**実装とは別セッションのAI**でレビューする
- `docs/` のみの修正・UI試作・シナリオの JSON（`scenarios/*.json`）・ルールの JSON（`rules/*.json`）の中身だけの修正は省略してよい（[開発サイクルのライトルート](../index.md#適用範囲フルとライト)）
- P0・P1 の修正後は再レビューに戻す

## レビュー観点

実装の経緯は渡さず、差分（`git diff`）とプランだけを渡して次の観点で読む。

1. **仕様整合** — `docs/` の正式ページ（SSOT）と食い違っていないか。用語・ロール・ゾーン・提案の状態などの意味がずれていないか。未解決論点を勝手に決めていないか。差分が書き換えた情報（ディレクトリ構成・コマンド・ルールなど）と同じものを、ほかの文書（README・AGENTS.md・`docs/` の各ページ）が重ねて持っていないか
2. **プラン整合** — プランの受け入れ条件・テストケースに対応する変更があるか。プランにない変更が混入していないか
3. **テスト** — 変更に対応するテストの有無。骨抜きテストの検出（[テストルール](testing.md)）
4. **設計** — 1ファイル1責務・境界・barrel 禁止・React の書き方（[アーキテクチャルール](architecture.md)。React は「React の書き方」の react-best-practices のうち対象のルール）。構造の読みやすさ：ディレクトリとファイルの分け方から、どこに何があるかを読み手が追えるか（何でも置き場のファイル、まとまりがファイル名の頭にしか表れない並び、仕様ページと対応しない分け方が無いか）。今の開発フェーズに対して重すぎないか：バックエンドに着手するまでは、本リリース前・バックエンド未実装で、状態はリロードで消える。旧データの互換・移行、使う場所のまだ無い拡張点・設定は作らない（作っていれば P1 で消すよう指摘する）
5. **異常系** — 境界値の両側、空データ、非同期の失敗経路。モック（MSW）の都合だけで起きる経路や、画面からは届かない入力は P2 にする（バックエンドと共用するスキーマの検査は除く）
6. **セキュリティ** — バックエンドに着手するまでは任意。着手したら必須にして、認可・インジェクション・秘密値の露出を見る（[ロードマップ](../../roadmap.md#backend-1on1)の完成の条件にも書いてある）

Claude Code では観点2・4を design-reviewer、観点5を edge-case-reviewer、観点1を spec-reviewer のサブエージェントが担当する（`.claude/agents/`）。他のツールでは、この観点ごとに別セッションを立てて同じ依頼をする。

担当のモデルの段（[開発プロセス](../index.md#プランドキュメントの8項目)「実装順」）は、設計の判断が要る観点2・4を**強い**、照合と網羅が中心の観点1・5を**標準**にする。プランで別の段を割り当てたときはそれに従う。

## 指摘の優先度分類

- **P0（必須修正）** — 仕様との矛盾・データ破壊・機能の誤り。push／マージをブロックする
- **P1（推奨修正）** — 深刻なバグの芽・テスト網羅の欠落。合理的理由があればスキップ可
- **P2（軽微）** — スタイル・命名・起きにくい経路。その場では直さず、[既知の問題](../../architecture/known-issues.md)「見送った軽微な指摘（P2）」に1行で記録して終わる（2026-10-11。完璧を求めて P2 を直し続けると、サイクルが閉じない。後で同じ箇所を触るときに直す）

各指摘には `file:line` と根拠（どのルール・どの仕様ページとずれるか）を添える。判断に迷う点は「要確認」として分ける。

## 終わりの条件

- P0・P1 がゼロなら合格
- P2 だけなら合格。直さずに記録して push／マージする
- P0・P1 を直した後の再レビューは、P0・P1 を出した観点だけで行う（指摘の無かった観点は回し直さない）。直すために、その観点の外の箇所（別の観点が見ていたところ）にまで手が広がったときは、その観点も回す
- 3ラウンドを超えて指摘が循環したら、**人間が裁定する**（AIどうしで決着させない）

## 静的レビューの限界

- 差分を読むAIレビューでは、表示崩れ・空データの無限ローディング・状態の取り違え・先へ進めなくなる行き止まりといった実行時のバグは捕まらない。UIや実行時の挙動を変えたら、人間レビューの前に**AIが**ブラウザ（`pnpm web:dev` か Playwright）で変更した画面を通しで操作して確かめ、スクリーンショットを添える。最後に人間も動かして確かめる
- ページ描画テスト（`pages.test.tsx`）は「描画できる」ことしか保証しない。見た目の判断は人間の仕事
