# ユースケースの E2E を、1ユースケース1シナリオに分ける

2026-10-18、[ユースケースと E2E の結果を紐づける](usecase-e2e-report.md)の人間レビューで出た要望。

## 背景

- 今のユースケースの E2E（`apps/web/e2e/usecases/`）は、画面の状態がメモリにしか無くリロードで消えるため、「作る→公開→遊ぶ」を1本のテストにしてステップで分けている。`scenario-authoring.test.ts` の1本が SC-1・2・3・5・6・8・PL-2 を担い、1本の役割が大きすぎる
- スクリーンショットはテストの最後の1枚だけで、ユースケースを確かめた様子を後から見る役に立たない
- 結果のページ（`/usecase-report/`）の「確認済」は正常パスだけを指す。分けると、ユースケースごとに何を確かめたかを読みやすく書ける

## 考えていること（プランで詰める）

- 1ユースケース＝1シナリオ（1テスト）。前提の状態は、MSW の fixtures にある公開済みのシナリオ・募集から始めるか、足りない分だけを最初の手順で画面から作る
- 手順ごとにスクリーンショットを撮り、Playwright のレポートに添える
- Gherkin にするなら、Playwright の実行・レポート・タグがそのまま使える playwright-bdd を第一の候補にする（Cucumber 本体は Playwright のレポートと結果のページの仕組みを作り直すことになる）。Playwright のまま分けるだけでもよい
- タグとステップの決まり・検査（`scripts/check-usecase-tags.mjs`）と結果のページ（`scripts/build-usecase-report.mjs`）は、分け方に合わせて見直す（1シナリオ1ユースケースなら、ステップの題の ID は要らなくなる）
