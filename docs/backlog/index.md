# 要望（バックログ）

プロダクトへの要望（PBI）を、1要望1ファイルで置く。まだ詰めていない要望も、状態「未着手」で置く。進み具合と「決めないといけないこと」は、[トップページのダッシュボード](/)が、ここのファイルから自動で組み立てる。

## 1ファイルの書き方

ファイルの先頭（frontmatter）に次を書き、本文に背景・経緯を書く。

```yaml
---
title: ○○ができるようにする
milestone: example-milestone  # どのマイルストーンのための要望か（docs/roadmap.md の id）。無ければ書かない
status: 進行中      # 未着手／検討中／進行中／判断待ち／完了／見送り
summary: PO向けに1〜2文で、何が実現するか
decisions:          # PO が決めないといけないこと（あれば）
  - Aを残すか、Bに替えるか
plans:              # docs/plans/ のプランのファイル名（あれば）
  - 2026-01-01-○○.md
cycles:             # 開発者向け：サイクルごとの状態と PR（あれば）
  - { name: C1 基盤, status: 完了, pr: 1 }
trace:              # アイデアがどこへ届くか（必須）。usecases・screens・rules のリストか、none の理由のどちらか
  usecases: [SC-6]
  screens: [/creator/scenarios/:scenarioId]
  rules: [scenario-flow/シナリオの公開]
updated: 2026-01-01
---
```

- **trace の書き方** — その要望が実現したいことを、どのユースケース（`usecases`：[中核のユースケース](../architecture/use-cases.md)の ID）・画面（`screens`：`routes.ts` のパス。まだ無い画面は導線図の点線のノードのラベル）・ルールの節（`rules`：ルールのテストのタグから `rule:` を除いたもの）で確かめられるかを書く。3つのリストは省略してよい（全部が無いのは不可）。開発の基盤のように、つなぐ先が無い要望は `none: <理由>` を書く（リストとは一緒に書けない）。リストはフロー形式（`[a, b]`）に限り、`#` と引用符は書けない（YAML と読み方が食い違うため）。つなぎ先が実在するか・書き忘れていないかは `pnpm docs:build` が止める（`scripts/check-trace.mjs`）。つなぎ方が正しいかは人間が見る。つながりは[トレースのページ](../architecture/test-report.md)に出る

- **状態の意味** — 未着手＝まだ手を付けていない／検討中＝grilling・プランを作っている／進行中＝実装している／判断待ち＝人間の判断が無いと進めない／完了／見送り
- **更新する人** — 開発サイクルを回す AI が、プランを作ったとき・マージしたときに更新する（[開発プロセス](../process/index.md)）
- **プランとの役割分担** — ここは「何を実現したいか」と進み具合。設計の詳細はプラン（`docs/plans/`、サイトには載せない）に書く
- **既知の問題との役割分担** — 人間の判断を待っているのが「要望（何を実現するか）」なら、この要望ファイルの `decisions` に書き、既知の問題には書かない（ダッシュボードで二重に出るため）。既知の問題の「判断待ち」は、実装上の問題の直し方を人間が決めるものに限る
- **画面ごとの課題との役割分担** — 画面を触って気になった点は、まず [画面ごとの課題](../screens/issues.md) に ID 付きで置く。直すと決めたものを要望にまとめ、本文に課題の ID を書く（課題の表からも要望へリンクする）
- **マイルストーンとの役割分担** — マイルストーンの定義（目的・完成の条件）は [ロードマップ](../roadmap.md) が正。要望ファイルは「どのマイルストーンのためか」だけを持ち、マイルストーンの進み具合はダッシュボードが要望の状態から計算する。基盤整備のように、どのマイルストーンの完成の条件にも当たらない要望は `milestone` を書かない
