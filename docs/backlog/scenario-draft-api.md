# シナリオの下書きの API を分ける

[ロードマップ](../roadmap.md#backend-1on1) backend-1on1（データをバックエンドに置く）の下ごしらえ。

- 2026-10-11、[API ドキュメント](api-docs.md)のプランで、人間の案として出た。下書きのシナリオの保存（`PATCH /api/scenarios/:id`）は、書きかけでも保存できるよう中身を検査しない。そのため `GET /api/scenarios/:id` が、シナリオの形（業務の検査を含む）に通らないものを返すことがあり、API ドキュメントにシナリオの形を書けない
- 案：`/scenarios/:id/draft` で書きかけを読み書きし（形だけを緩く見る）、公開（`POST /scenarios/:id/publish`）で今の公開と同じ検査に通して正式なシナリオにする。`GET /scenarios/:id` はいつも検査済みのシナリオを返す。編集画面・モック・テストが変わるので、API ドキュメントとは別のサイクルにした（人間が決めた）
- （C1 で片づいた）一緒に片づく見込みの既知の問題：「シナリオを非公開にしても、募集・セッションが残り、下書きからも募集を出せる」のうち、下書きからの募集と、下書きの `scenarioType: null` で編集画面が落ちる件（[既知の問題](../architecture/known-issues.md)）
- 2026-10-11、API ドキュメントの実装レビュー（異常系）で、下書きの保存が形の崩れた本文（知らないキー・型違い）もそのまま保存し、一覧と違う形を返すことが分かった。書きかけを読み書きする口で形を検査する（[既知の問題](../architecture/known-issues.md)）
- API ドキュメントでは、それまでの間、下書きを返しうる API の応答を業務の検査を外した形で書いておく（`docs/plans/2026-10-11-APIドキュメント.md` G10）
- 2026-10-11、プランを作り、人間と決めた：公開版と下書きを分ける（保存は下書きだけ、公開し直すで公開版に）、公開版があり一覧に載っているシナリオからだけ新しく始める、非公開は一覧から外して新しく始めるのを止めるだけ、公開し直すと進行中のセッションも次のシーンから新しい版、下書きはファイルに書かない
- 2026-10-11、プランの AI レビューを受けて人間が決めた：セッションはシナリオの更新と無関係にする（開始時のシナリオで進む。仕様のスナップショットどおり）、シナリオからセッションまでの流れを仕様に明示する、他人のシナリオは読むかコピーしかできずコピーは親を辿れる。大きくなったので C1（下書きと公開版）・C2（セッションの独立）・C3（シナリオのコピー）に分けた
