# 不安定な E2E は、いったんスキップにして直す要望を起票する

2026-10-18、[ユースケースと E2E の結果を紐づける](usecase-e2e-report.md)の人間レビュー（D9：`retries` を足さない）で出た要望。

## 背景

- `retries` を足さないので、たまに落ちる E2E があると、PR の CI がそのたびに止まる。`retries` を足すと、不安定なテストが CI を通り、結果のページでも「確認済」に見えてしまう
- 人間の判断：CI を止め続けず、不安定なテストはいったんスキップにし、直す要望を起票する
- 起きた不安定
  - 2026-10-26、[アイデアから実装までをたどれるようにする](trace-report.md)（P5）の実装中に、`gm-session.test.ts` が `Failed to load resource: net::ERR_FAILED` で1度落ちた（単独で流すと通る。アプリは変えていない）
- 今は `scripts/check-usecase-tags.mjs` が `e2e/usecases/` の `test.skip`・`test.fixme` を止めている（スキップしたステップが結果で「確認済」に見えるため）。要望へのリンクを添えたスキップだけを通し、結果のページで「スキップ中」と分けて出す形に変える

## 考えていること（プランで詰める）

- スキップには、直す要望のファイル（`docs/backlog/…`）へのリンクを添える。リンクの無いスキップ・実在しない要望へのリンクは検査で止める
- 結果のページは、スキップしたテストのユースケースを「全スキップ」とし、要望へリンクする（2026-10-27、人間の判断。[トレースのページ](trace-report.md)の人間レビューで、今はスキップだけの UC が「落ちた」と出ることへの答え。ユースケースの結果のページとトレースのページの両方で同じ状態にする）
- [ユースケースの E2E を、1ユースケース1シナリオに分ける](usecase-e2e-per-scenario.md) と同じプランで扱うと、分け方に合わせて検査とページを一度に直せる
- 書き方の正は `docs/process/rules/testing.md`「ユースケースの E2E」に置く
