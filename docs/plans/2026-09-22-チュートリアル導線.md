# プラン：入口からのチュートリアル導線（旅立ちの酒場）

書式は `docs/process/index.md` の「プランドキュメントの8項目」。

## 1. 概要

所持キャラクターが0人のプレイヤーに、ホーム画面から「旅立ちの酒場」というチュートリアル（`/pl/tutorial`）への導線を出す。NPCとの短い問答を進めるうちに、実際にキャラクター（`Character`）が段階的に作られ、最後まで進めると戦闘スキルカードを得て「冒険者」として登録される（この酒場＝宿が、冒険者ギルドを介さず冒険者登録まで行える場という設定）。

**2026-09-22追記（人間の判断・decision 1を上書き）**：当初は「どの段階で切り上げても、その時点のデータがそのまま『旅人』（または『探索者』）として残ってよい」という分岐（訓練ステップ・覚悟ステップでの離脱選択肢）を用意していたが、実際に動かしてみると「名乗っただけで旅立てる」など分量に対して展開が唐突だった。分量的に最後まで一本道で進めても長すぎないため、**訓練ステップ・覚悟ステップの離脱選択肢は廃止し、チュートリアルは常に最後（冒険者登録）まで一本道で進む**方針に変更する。ただし「保存はステップ完了ごと」という実装（decision 5）は変えないため、ブラウザを閉じる等でプレイヤーが途中離脱した場合は、それまでの入力だけが反映された「旅人」または「探索者」のキャラクターが結果的に残る（＝これはNPCが提示する選択肢ではなく、離脱時の副作用として残る点に注意）。

**2026-09-22再追記（訂正）**：上記の実装で訓練ステップ（Step1）を「選択肢なしの台詞だけ」にしたところ、NPCが「腕に覚えはあるかい？」と問いかけているのに返事のカードが一切ない、という会話として不自然な見た目になった（ユーザー指摘）。離脱の選択肢（「身ひとつで旅立つ」）だけを消せばよく、返事のカード自体（「腕試しをしていく」）は単一の選択肢として残す。覚悟ステップ（Step4）も同様に、離脱の選択肢だけを消して「冒険者として登録する」という単一の返事カードにしてある（最初からそうしていた）。つまりNPCの問いかけには必ず1枚以上の返事カードが対応する、という原則を崩さないこと。

## 2. 背景

- ユーザー要望：「入口から初めて入ったプレイヤーがチュートリアルをプレイし、クリアするとキャラクターが1人できている。全部クリアすると冒険者、途中でやめても旅人のままでよい。酒場でNPCと会話するうちにキャラクターができている」
- 事前調査（このプラン作成にあたって確認済み）
  - 旅人・探索者・冒険者は`docs/cartagraph/role-and-scenario.md`で決着済みの概念で、プレイヤーへの明示的な昇格ではなく、`deriveArchetype`（`packages/domain/src/index.ts`）がPCの`abilities`・`deck`（戦闘スキルタグの有無）から都度導出する
  - 既存のセッション開始フロー（`docs/cartagraph/scenario-flow.md`）は人間GM＋既存PCが前提で、チュートリアル（PC未作成・GM不要）とは構造が逆
  - 既存の`CharacterCreatePage`は1回のフォーム送信・CP予算のハード制約（`docs/cartagraph/character-growth.md`）。体技心の初期配分方法自体は`docs/open-questions.md`の「次に詰める候補」で未決
- grillingで決めた方針（2026-09-22、人間の判断）
  1. チュートリアル完了時は実際に能力値・戦闘スキルカードを付与し、既存の`deriveArchetype`がそのまま`'adventurer'`を返す形にする（専用の状態フラグは作らない）
  2. セッションモデルは使わず、独立した専用フロー（新ルート）として作る。既存の`CharacterCreatePage`は2人目以降・玄人プレイヤー向けにそのまま残す
  3. 会話中の選択肢＝カード選択・体技心の割り振りとして扱い、既存のCP予算内に収める。体技心の配分は`CharacterCreatePage`と同じ「合計9を1〜5で配分」という総量ルールを踏襲するが、選ばせ方は自由配分ではなく3択の固定プリセットにする（詳細設計3.参照）。これは`CharacterCreatePage`の仮ルールをそのまま流用するのではなく、チュートリアル固有の別の仮ルールを新設することになるため、`docs/open-questions.md`の論点はこれでも決着させず、`TutorialPage`側にも「配分方法は仮」と画面表示する（最重要ルール4：仮ルールはコード・画面の両方で明示する）
  4. 初回判定ロジックは作らない。所持キャラクターが0人ならホーム画面に常に導線を出す（スキップ可能）
  5. 各ステップの選択が終わるたびにサーバーへ保存する（PATCH）。閉じても、その時点のキャラクターがそのまま残る
  6. UIは既存のプレイ画面の部品（`Table`・`HandDock`・`GameCard`）を流用し、会話専用の新UIは作らない
  7. 入口（`EntrancePage`）は変更しない。導線はホーム画面（`HomePage`）側に置く

## 3. 詳細設計

### 画面遷移

```
HomePage（所持キャラクター0人）
  └─ 「旅立ちの酒場へ」 → /pl/tutorial（TutorialPage）
       Step0 名前を入力 → POST /api/characters（作成。以後はこのidにPATCH）
       Step1 「腕に覚えはあるか」→「腕試しをしていく」（単一の返事カード） → Step2
       Step2 能力値プリセットを選ぶ（3択） → PATCH abilities
       Step3 道具を選ぶ（3択、CP予算内の非戦闘カード） → PATCH deck
       Step4 「冒険者として登録する」（単一の確認カード） → PATCH deck（戦闘スキルカード追加） → 完了画面（冒険者）
       完了画面 → 「キャラクターシートへ」→ /pl/characters/:id
```

2026-09-22追記：Step1・Step4の離脱選択肢（「身ひとつで旅立つ」「まだ早い、今日はここまで」）は廃止した（1.の追記を参照）。ただしNPCの問いかけには返事のカードを残す（1.の再追記を参照）。Step1は「腕試しをしていく」の単一カード、Step4は「冒険者として登録する」の単一カードを選ぶ一本道になる。

### 会話内容（ドラフト。実装時に文言は調整してよい）

「旅立ちの酒場」「酒場の主人」はUI上の演出名であり、`CardKind`の`location`／`npc`カードとしてデータ化するものではない（意図的なスコープ限定の項参照。`TutorialPage.tsx`内の文言・見出しとして扱う）。この酒場（宿）が、冒険者ギルドを介さず冒険者登録まで行える場という設定にする。

| Step | flavor（NPCの台詞） | 選択肢 |
|---|---|---|
| 0 | 「良い夜だ、旅の方。名を聞かせてくれないか」（GMの情景描写で酒場に入る場面を挟んでから） | 名前入力欄＋「名を名乗る」 |
| 1 | 「腕に覚えはあるかい？なんなら少し鍛えてから旅立つのも悪くない」 | 「腕試しをしていく」（単一の返事カード） |
| 2 | 「なら、お前さんの得意はどれだ」（画面に「体技心の配分は仮ルール」と注記を出す） | 「力自慢」(body5/skill2/mind2)／「身軽さ」(body2/skill5/mind2)／「知恵者」(body2/skill2/mind5) |
| 3 | 「旅には何か持たせてやろう」 | 「灯火のランタン」／「解錠具」／「人当たりが良い」（いずれもbasicPoolの既存カード、CP1） |
| 4 | 「腕も荷物も揃ったな。ここいらじゃ、この酒場の元帳が冒険者名簿も兼ねている――名を刻んで、冒険者として旅立つといい」 | 「冒険者として登録する」（→「斬撃」CP2を付与） |

CP消費は最大でもStep3（1）+Step4（2）＝3。既存の`initialCpBudget`（5）内に収まる設計にする。選択肢はすべて予算内の組み合わせだけを提示するため、UI上はCP超過エラーは発生しない想定（サーバー側のPATCHハンドラは念のためPOSTと同じ予算チェックを行う）。

### データ・API

- `packages/domain`の型変更は無し。`Character`（`abilities`・`deck`）だけで3ロールとも表現できる
- 新規：`PATCH /api/characters/:id`（`apps/web/src/mocks/handlers.ts`）。body は `Partial<Pick<Character, 'abilities'>> & { addCardIds?: string[] }` 程度。`abilities`が来たら`hp`を`{current:14,max:14}`にする（既存のPOSTハンドラと同じ規則）。`addCardIds`は`basicPool`・`unlockedPool`から解決して既存の`deck`に追加する。`cp.spent`は「更新後のdeck全体のCP合計」で毎回再計算して`cp`フィールドを上書きする（Step0作成時は`spent:0`、Step3・Step4のPATCH後にそれぞれ再計算）。再計算結果が`cp.total`を超えるなら422を返す（既存のPOSTハンドラの予算チェックと同じ規則）。この累計管理をしないと、チュートリアル経由のPCだけ`cp.spent`が更新されず、`CharacterSheetPage`の「CP残り」表示が`CharacterCreatePage`経由のPCと食い違う
- 新規：`useUpdateCharacter()`（`apps/web/src/lib/queries.ts`）。`useUpdateScenario()`と同じ形（`api.patch`、成功時に`keys.character(id)`と`keys.characters`を更新）
- 既存の`useCreateCharacter()`をStep0でそのまま使う（`abilities: undefined, cardIds: []`）

### ルーティング

- `apps/web/src/app/routes.ts`に追加：`{ path: '/pl/tutorial', title: '旅立ちの酒場', group: 'pl', description: '初めてのプレイヤー向け。NPCとの短い問答を経て最初のキャラクターができる' }`（`nav`は付けない。常設ナビ項目ではなくホーム画面からの導線のため）
- `apps/web/src/app/router.tsx`に`TutorialPage`を追加

### ホーム画面の変更

- `apps/web/src/pages/HomePage.tsx`：既存の`myChars`（`characters.filter(c => c.ownerId === me.data?.id)`、`HomePage.tsx`内で既に絞り込み済みの変数）の件数が0のとき、「旅立ちの酒場へ」の導線パネルを表示する。1件以上あれば表示しない。**`useCharacters()`の全件（他ユーザー含む）ではなく、必ず自分のキャラクターに絞り込んだ件数で判定する**（`useCharacters()`の生の件数で判定すると、モックDBに他ユーザーのキャラクターが常に存在するため、新規プレイヤーでも導線が出ないバグになる）

### 新規ファイル

- `apps/web/src/pages/pl/TutorialPage.tsx`（1ページ1ファイル。既存の`CreatorSceneEditPage.tsx`の分割保留と同じ理由で、単一ファイルに閉じる。`Table`・`HandDock`・`GameCard`・`Panel`・`Button`等を流用したローカルなstateマシン。`Session`は使わない）

### 意図的なスコープ限定（重複の報告）

チュートリアルの会話内容（NPC台詞・選択肢）は`TutorialPage.tsx`内にハードコードし、既存のシナリオ作成の仕組み（`Scenario`・`DeckNode`・GMによる編集）には乗せない。これは意図的な単純化であり、「シナリオ作成の仕組みと表現力が重複している」と気づいた上での判断（grillingの決定2）。チュートリアル自体を製作者が編集可能にする一般化は今回のスコープ外とする。

## 5. 新規テストケース

`apps/web/src/test/pages.test.tsx`に追加する（正常系・異常系）。

2026-09-22追記：離脱選択肢の廃止（1.の追記）に伴い、「旅人のまま完了」「探索者のまま完了」を正規のテストケースとしては扱わない（NPCの選択肢としては到達不能になったため）。常に最後まで進んで「冒険者」になることだけを確認する。

- Step0〜4を全部進める（能力値プリセット→道具→冒険者として登録する）と、キャラクターが「冒険者」になる（`deck`に`戦闘スキル`タグのカードが入り、`ARCHETYPE_LABEL.adventurer`が表示される）

- 異常系：保存に失敗すると次のステップへ進まずエラーを表示する（既存ケースを維持）
