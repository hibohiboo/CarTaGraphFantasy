# ユースケースと E2E の結果を紐づけるページ

要望：[ユースケースと E2E の結果を紐づける](../backlog/usecase-e2e-report.md)

状態：プランを書いた（2026-10-18。D1〜D8 は2026-10-18に人間と確かめた（質問2ラウンド））。次は手順2「プランの AI レビュー」（設計整合と運用。仕様整合は正式仕様を変えないので回さない）と手順3「テスト網羅レビュー」。等級は強い（`opus`）。

## 1. 概要

[中核のユースケース](../architecture/use-cases.md)（SC-1〜8・PL-1〜8 など）ごとに、それを確かめる E2E のテストと、その最新の結果（通った・落ちた・手前で止まった・テストなし）を一覧にするページを作る。デプロイが E2E を流した後に HTML を組み立て、GitHub Pages の `/usecase-report/` に載せ、各テストから Playwright のレポートのそのテストへリンクする。あわせて、ユースケースを通しでなぞる E2E を2本（シナリオを作って GM 不在で遊ぶ／GM が描写と選択肢を配る）足し、今の `web:check:authoring` の確かめを CI の E2E へ移す。

## 2. 背景

- 2026-10-18、人間の要望。ユースケースがどこまで動くかを、テストの結果から見たい
- 正式仕様：[中核のユースケース](../architecture/use-cases.md)（ID の表が業務領域ごとにある。GR・EV は将来）、[テストレポート](../architecture/test-report.md)、[テストルール](../process/rules/testing.md)
- 今の作り
  - CI で回る E2E は `apps/web/e2e/smoke.test.ts`（全ルートが開けるか）だけ。ユースケースの流れをなぞる E2E は無い
  - 通しの確かめは `apps/web/e2e/dev/*.mjs`（`web:check:*`）にあるが、CI で回らず結果も残らない。`scenario-authoring.mjs` は書き込みを閉じた開発サーバーで回る（＝ CI の preview でも回せる）。`scenario-publish.mjs` は書き込みを開いた開発サーバー（ファイルの書き出し・HMR）が要るので preview では回せない
  - デプロイ（`.github/workflows/deploy.yml`）は `build:pages` → E2E（落ちても続ける）→ Vitest → `copy-test-reports-to-pages.mjs` の順。docs のビルドは E2E より先
  - CI（`.github/workflows/ci.yml`）の E2E は落ちると止まる
- **ルールとの食い違い（D1 で決着）**：testing.md の「深いインタラクションシナリオはE2E化しない」。ユースケースの通しだけを E2E に置けるよう書き換える
- 未解決論点・仮ルールには触れない

### 紐づけの書き方（D2）

```ts
test('シナリオを画面だけで作り、GM 不在で結末まで遊ぶ', { tag: ['@SC-1', '@SC-2', '@SC-3', '@SC-5', '@SC-6', '@SC-8', '@PL-2'] }, async ({ page }) => {
  await test.step('SC-1 下書きを作る', async () => { … });
  await test.step('SC-2 シナリオデッキを組む', async () => { … });
  …
});
```

- タグ＝このテストが確かめるつもりのユースケース（テストが手前で落ちても JSON に残る）。ステップ＝実際に通ったか
- ステップの題は `<ID> <自由な説明>`。ID の後ろの文言はユースケースの名前と一致しなくてよい（ページはユースケースの名前を use-cases.md から出す）
- ID の付かない下ごしらえのステップ（募集を出す等、補完の業務領域）は ID を付けずに書いてよい（ページには出ない）

### 検査（D4）：`scripts/check-usecase-tags.mjs`

`pnpm docs:build` の最後に足す（`check-screens.mjs` と同じ型。テストは `scripts/check-usecase-tags.test.mjs`、`pnpm tools:test`）。

- use-cases.md の表の行（`| SC-1 | 下書きを作る | …`）から ID と名前を読む（読む関数は、ページを作るスクリプトと共用する。下の `scripts/usecases.mjs`）
- `apps/web/e2e/**/*.test.ts` から、タグ（`'@XX-n'`）とステップの題の先頭の ID（`test.step('XX-n …'`）を読む
- 止めるもの
  - 表に無い ID のタグ・ステップ
  - 同じファイルの中で、タグにあるのにステップが無い ID／ステップにあるのにタグが無い ID（タグとステップの付け忘れ）
- 止めないもの：テストの無いユースケース（ページで「テストなし」と出す）

### ページの組み立て（D5・D6）：`scripts/build-usecase-report.mjs`

- 入力
  - use-cases.md の表（業務領域の見出しの順に、ID・名前・見出しへのリンク）。GR・EV は見出しの「（将来）」をそのまま出す
  - Playwright の JSON の結果。`playwright.config.ts` の reporter に `['json', { outputFile: 'e2e-results/results.json' }]` を足す（`playwright-report/` は HTML のレポーターが消すので別の場所。`apps/web/e2e-results/` は .gitignore に足す）
- ユースケースごとの状態
  - **通った** — その ID のステップが、どのテストでもすべて通った
  - **落ちた** — その ID のステップのどれかが落ちた
  - **手前で止まった** — その ID をタグに持つテストがあるのに、ステップが走っていない（前のステップで落ちた・skip）
  - **テストなし** — その ID をタグに持つテストが無い
  - JSON が無いとき（E2E が起動できなかった等）は、ページの先頭に「結果がありません」と出し、全件を「結果なし」にする。スクリプトは失敗させない（デプロイを止めない方針。`copy-test-reports-to-pages.mjs` と同じ）
  - retry があるときは最後の結果を使う
- 各ユースケースの行に、テストの題と、そのテストの Playwright のレポートへのリンク（`../e2e-report/#?testId=<id>`）を出す。JSON の test の id が HTML レポートの testId と同じかは、実装順1で確かめる（違えば、レポートの検索 `#?q=<テストの題>` にする）
- 出力は `apps/web/usecase-report/index.html`（1枚。.gitignore に足す）。`copy-test-reports-to-pages.mjs` の表に `['apps/web/usecase-report', 'usecase-report']` を足して dist へ写す
- 生成時刻と、どのコミットの結果か（`GITHUB_SHA` があれば）を出す
- 見た目は、VitePress のサイトから来たときに浮かない程度の素の HTML とインライン CSS（ライト・ダークの両方）。外部のスクリプトは使わない
- `deploy.yml`：E2E の後、copy の前に `node scripts/build-usecase-report.mjs`（`if: always()`）。手元では `pnpm web:e2e && pnpm usecase:report`（ルートの package.json に足す）

### 足す E2E（D3）：`apps/web/e2e/usecases/`

`playwright.config.ts` の `testMatch: '**/*.test.ts'` で拾われる（設定は変えない）。

1. `scenario-authoring.test.ts`（`scenario-authoring.mjs` を移す。確かめる中身は今のものをすべて残す）
   - SC-1 下書きを作る（タイトルで作る、案内の「開く」で概要を入力）
   - SC-2 シナリオデッキを組む（シーンを足す、選択肢と移り先、移り先のシーンは消せない、未保存の確かめ）
   - SC-5 行き止まりを見つける（選択肢を足す前のシーンに、先へ進む選択肢が無い注意が出る → 足すと消える。今の mjs には無い。画面の文言は実装で確かめる。出す場所が無ければ SC-5 は外して止まって報告する）
   - SC-3 結末と結末タグを決める
   - SC-6 シナリオ集へ公開する（公開の前の確かめ「問題はありません」→ 公開中）
   - SC-8 公開した版を読む（GM のシナリオの画面で読み、GM 不在の募集を出す。他人のシナリオは下書きを読めず読むだけ）
   - PL-2 手札のカードをプレイする（GM 不在で選択肢をプレイし、結末に達して結末タグを得る）
   - 最後にコンソールの誤りが無いこと。画面の移動は今の mjs と同じく `location.hash` で行う（`page.goto` は最初の1回だけ）
   - mjs の `waitForTimeout(500)`（未保存の確かめを断った後に留まるか）は、ロケータの自動待機で書き直す（testing.md「テストの独立性」）
   - 書き込みの後始末（`scenarios/` の git の状態）は preview では書き込まないので要らない。代わりに、書き込みが閉じていることを前提にする旨をコメントに書く
2. `gm-session.test.ts`（新規）
   - 下ごしらえ（ID なし）：自分の募集（灰色館の一夜の `rc-mine`）を画面から始め、GM のセッションの画面を開く
   - PL-1 描写を書き、選択肢を配る（描写と、移り先なしの選択肢を送る → 卓の描写と手札に出る。取り下げる）
   - PL-2 手札のカードをプレイする（GM が PL を兼ねてプレイ画面へ移り、配った選択肢をプレイ → GM の描写を待つ）
   - 画面の操作は `pages.test.tsx`「GMのセッション管理：描写と選択肢を配る」と同じ文言を使う。始め方の画面の操作は実装で確かめる
