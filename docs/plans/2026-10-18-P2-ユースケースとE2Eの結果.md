状態：プランの AI レビュー済み（2026-10-18。設計整合・運用・テスト網羅。P0 2件・P1 を反映した。結果は9章）。D1〜D8 は2026-10-18に人間と確かめた（質問2ラウンド）。D9〜D12 はレビューを受けて AI が決めた（人間レビューで確かめる）。手順4〜5の実装・テストと、手順6の実装の AI レビュー（設計・プラン整合／異常系）は済み、P1 を反映した（10章）。次は人間レビュー（手順7。変更した画面は無く、結果のページ `apps/web/usecase-report/index.html` と E2E の結果を確かめる）。

## 1. 概要

[中核のユースケース](../architecture/use-cases.md)（SC-1〜8・PL-1〜8 など）ごとに、それを確かめる E2E のテストと、その最新の結果（通った・落ちた・手前で止まった・テストなし）を一覧にするページを作る。デプロイが E2E を流した後に HTML を組み立て、GitHub Pages の `/usecase-report/` に載せ、各テストから Playwright のレポートのそのテストへリンクする。あわせて、ユースケースを通しでなぞる E2E を2本（シナリオを作って GM 不在で遊ぶ／GM が描写と選択肢を配る）足し、今の `web:check:authoring` の確かめを CI の E2E へ移す。

## 2. 背景

- 2026-10-18、人間の要望。ユースケースがどこまで動くかを、テストの結果から見たい
- 正式仕様：[中核のユースケース](../architecture/use-cases.md)（ID の表が業務領域ごとにある。SC・PL の表は5列、GR・EV（将来）は4列。GR には `### GR-n` の見出しが無い）、[テストレポート](../architecture/test-report.md)、[テストルール](../process/rules/testing.md)
- 今の作り
  - CI で回る E2E は `apps/web/e2e/smoke.test.ts`（全ルートが開けるか）だけ。ユースケースの流れをなぞる E2E は無い
  - 通しの確かめは `apps/web/e2e/dev/*.mjs`（`web:check:*`）にあるが、CI で回らず結果も残らない。`scenario-authoring.mjs` は書き込みを閉じた開発サーバーで回り、preview（4188番で実測）でも14件の check がすべて通る。`scenario-publish.mjs` は書き込みを開いた開発サーバー（ファイルの書き出し・HMR）が要るので preview では回せない
  - デプロイ（`.github/workflows/deploy.yml`）は `build:pages` → E2E（落ちても続ける）→ Vitest → `copy-test-reports-to-pages.mjs`（`if: always()`、元が無くても exit 0）の順。docs のビルドは E2E より先
  - CI（`.github/workflows/ci.yml`）の E2E は落ちると止まる。`playwright.config.ts` に `retries`・`timeout` は無い（既定は retry 0・1テスト30秒）。`reuseExistingServer: !process.env.CI`
- Playwright 1.63 の挙動（レビューで `node_modules/.pnpm/playwright@1.63.0/.../lib/runner/index.js` を読んで確かめた）
  - JSON の `specs[].tags` は先頭の `@` を外して出る（`"SC-1"`）。`specs[].id` は HTML レポートの `#?testId=` と同じ
  - ステップは `test.step` で作ったものだけが入れ子の `{title, duration, error, steps}` で出る。**ステップに status は無い**（合否は `error` の有無）。`expect` は出ない
  - `results[]` は retry の順で、最後が最新。結果の `status`（passed／failed／timedOut／skipped）と、テストの `status`（expected／unexpected／flaky／skipped）がある
  - webServer が起動できなくても JSON は書かれる（`suites` が空か各テストの `results` が空で、トップの `errors` に誤りが入る）
  - HTML のレポーターは `onEnd` で `outputFolder`（`playwright-report/`）を消す。JSON の `outputFile` は設定ファイルのディレクトリ（apps/web）から解決する
- **ルールとの食い違い（D1 で決着）**：testing.md の「深いインタラクションシナリオはE2E化しない」。ユースケースの通しだけを E2E に置けるよう書き換える

### 紐づけの書き方（D2）

```ts
test(
  'シナリオを画面だけで作り、GM 不在で結末まで遊ぶ',
  { tag: ['@SC-1', '@SC-2', '@SC-5', '@SC-3', '@SC-6', '@SC-8', '@PL-2'] },
  async ({ page }) => {
    await test.step('SC-1 下書きを作る', async () => { … });
    await test.step('SC-2 シナリオデッキを組む', async () => { … });
    …
  },
);
```

- タグ＝このテストが確かめるつもりのユースケース（テストが手前で落ちても JSON に残る）。ステップ＝実際に通ったか
- ステップの題は `<ID><空白><自由な説明>`。ID の後ろの文言はユースケースの名前と一致しなくてよい（ページはユースケースの名前を use-cases.md から出す）
- ID の付かない下ごしらえのステップ（補完の業務領域：セッションを始める等）は ID を付けずに書いてよい（ページには出ない）
- テストの最後の確かめ（コンソールの誤りが無いこと）も、最後の ID のステップの中に置く（ステップの外で落ちると、どのユースケースのせいか分からない）
- 書き方の正は testing.md に置く（test-report.md はページの中身とコマンドだけを書き、書き方へリンクする。1ページ1責務）

### 検査（D4・D12）：`scripts/check-usecase-tags.mjs`

`pnpm docs:build` の最後に足す（`check-screens.mjs` と同じ型）。表とテストファイルを読む関数は `scripts/usecases.mjs` に置き、ページを作るスクリプトと共用する。テストは `scripts/usecases.test.mjs`・`scripts/check-usecase-tags.test.mjs`（`pnpm tools:test`）。

自前で書く理由：Playwright のタグの検査は `@` で始まることしか見ない。`playwright test --list --reporter=json` でタグは取れるが、ステップは実行しないと出ない。TypeScript の型にするには use-cases.md から型を作る仕組みが要り、重い。

- use-cases.md の表の行から ID・名前・業務領域（`## ` の見出し。「（将来）」の有無も）を読む。5列・4列の両方を読み、ヘッダと区切りの行は読まない。**1件も読めない・同じ ID が2回出る**ときは誤り（表の形が変わって黙って空のページになるのを止める）
- `apps/web/e2e/**/*.test.ts` から、`tag:` に書いたタグと、`test.step(` の最初の引数の題の先頭の ID を読む。コメントアウトした行は読まない
- 止めるもの
  - 表に無い ID のタグ・ステップ
  - ID の形に似ているが形の違うタグ（小文字 `@sc-1`）。ID でないタグ（`@slow` など）は無視する
  - `e2e/usecases/` で：タグとステップの付け忘れ（タグにあってステップに無い ID／その逆）、`test.step` の最初の引数が文字列の直書きでない（テンプレート文字列・変数）、題の中のタグ（`test('… @SC-1')`）・`test.describe` へのタグ（静的に読まないので禁じる）、`test.skip`・`test.fixme`・`test.step.skip`・`expect.soft`（skip したステップは JSON で `error` 無し＝「通った」に見えるため）、1ファイルに `test(` が2本以上（D12）
- 止めないもの：テストの無いユースケース（ページで「テストなし」と出す）
- デプロイの `build:pages` の中の docs:build もこの検査で止まる。タグの誤りは CI（docs:build）と pre-push が先に止めるので、main に入ってデプロイが止まることは起きにくい（デプロイを止めない方針とはぶつからない）

### ページの組み立て（D5・D6）：`scripts/build-usecase-report.mjs`

- 入力
  - use-cases.md の表（`scripts/usecases.mjs`）
  - Playwright の JSON の結果。`playwright.config.ts` の reporter に `['json', { outputFile: 'e2e-results/results.json' }]` を足す（`apps/web/e2e-results/` は .gitignore に足す）
- **結果なし（ページ全体）** — 次のどれかなら、ページの先頭に「E2E の結果がありません（E2E が起動できなかった等）」と出し、全件を「結果なし」にする。スクリプトは失敗させない
  - JSON が無い・壊れている
  - トップの `errors` が空でなく、spec が1件も無いか、すべてのテストの `results` が空
- ユースケースごとの状態は、テスト（spec）ごとに最後の結果（`results` の最後）を見て決める
  1. ステップを再帰でたどり、題が `^([A-Z]{2}-\d+)\s` に当たるものを ID のステップとする（ID の無い親の下の ID のステップも拾う）
  2. ID のステップは、`error` が無く `duration >= 0` なら通った、`error` があれば落ちた
  3. 結果の `status` が passed でないのに、ID のステップがどれも落ちていないとき（ステップの外で落ちた・時間切れで走りかけのステップに `error` が付かなかった）は、最後に記録された ID のステップを落ちた扱いにする（それも無ければ、タグの最初の ID を落ちた扱いにする）
  4. タグにあるのにステップが記録されていない ID は手前で止まった
  5. ユースケースの状態は、そのタグを持つすべてのテスト・同じ ID のすべてのステップのうち、**落ちた ＞ 手前で止まった ＞ 通った** の順で強いもの。タグを持つテストが無ければテストなし
- 各ユースケースの行に出すもの：ID・名前（use-cases.md の見出しへのリンク）・状態・テストの題と、そのテストの Playwright のレポートへのリンク（`../e2e-report/#?testId=<spec の id>`）
- 見出しへのリンクは、ビルド後の `docs/.vitepress/dist/architecture/use-cases.html` に実在する id から引く（`check-doc-anchors.mjs` の `idsOf` と同じやり方。`cleanUrls` が無いので `.html` 付き、base は `/CarTaGraphFantasy/`）。その ID の見出しが無い（GR-n）ときは業務領域の見出しへ、dist が無い（手元）ときは見出しへのリンクを付けない
- 生成時刻・E2E の開始時刻（JSON の `stats.startTime`。手元で古い JSON を読んだと気づけるように）・どのコミットの結果か（`GITHUB_SHA` があれば）を出す
- テストの題などの文字は HTML としてエスケープする
- 出力は `apps/web/usecase-report/index.html`（1枚。.gitignore に足す）。`copy-test-reports-to-pages.mjs` の表に `['apps/web/usecase-report', 'usecase-report']` を足して dist へ写す
- 見た目は、VitePress のサイトから来たときに浮かない程度の素の HTML とインライン CSS（ライト・ダークの両方）。外部のスクリプトは使わない
- `deploy.yml`：E2E の後、copy の前に `node scripts/build-usecase-report.mjs`（`if: always()` と `continue-on-error: true`。想定外の例外でもデプロイを止めない）
- 手元では `pnpm web:e2e; pnpm usecase:report`（ルートの package.json に足す。`&&` にすると E2E が落ちたとき＝ページを見たいときに作られない）

### 足す E2E（D3）：`apps/web/e2e/usecases/`

`playwright.config.ts` の `testMatch: '**/*.test.ts'` で拾われる（設定は変えない）。tsconfig の include に `e2e` があるので型検査に入り、Vitest は `**/e2e/**` を外しているので拾わない。両方とも、`page.goto` は最初の1回だけにし、あとは画面内のリンクか `location.hash` で移る（メモリの状態が消えるため）。画面を移ったことは、移った先にしか無い要素を待って確かめる（testing.md「テストの独立性」）。

1. `scenario-authoring.test.ts`（`scenario-authoring.mjs` を移す。mjs の14件の check のうち13件を移し、「scenarios/ の git の状態が始める前と同じ」の1件は意図して外す（preview は書き込まない）。書き込みが閉じていることは、公開したときの「デモのため保存されません」の表示で確かめる）
   - SC-1 下書きを作る（タイトルで作る、案内の「開く」で概要を入力）
   - SC-2 シナリオデッキを組む（シーンを足す、選択肢と移り先、移り先のシーンは消せない、未保存の確かめ）
     - mjs の `waitForTimeout(500)`（確かめを断った後に留まるか）は、`page.waitForEvent('dialog')` で受けて断り、編集の画面にしか無い要素（タイトルの欄が「（編集中）」のまま）が残り、一覧の画面にしか無い `getByPlaceholder('シナリオのタイトル')` が0件であることで確かめる。確かめの回数を数える仕組みは残す
   - SC-5 行き止まりを見つける（シーン編集の `region "このシーンの注意"` で両側を確かめる：(a) 選択肢が無いと「先へ進む選択肢がありません」が出る、(b) 選択肢を足しても移り先が空ならまだ出る、(c) 移り先を選ぶと消える（(a) を待ってから `toHaveCount(0)`）。シナリオ編集の `region "公開の前の確かめ"` にも、行き止まりがある間は出る。部分一致で両方の画面に当たらないよう、区画に絞ってから探す）
   - SC-3 結末と結末タグを決める
   - SC-6 シナリオ集へ公開する（公開の前の確かめ「問題はありません」→ 公開中）
   - SC-8 公開した版を読む（GM のシナリオの画面で読み、GM 不在の募集を出す。他人のシナリオは下書きを読めず読むだけ。読み取り専用のつながりのリンクで他のシーンへ移れることは、移った先のシーンの見出しを待って確かめる）。募集の画面の「先へ進む選択肢の無いシーンがあります」が出ないことはここで確かめるが、出ない側しか見られないので、出る側は Vitest（`gmlessHelpers.ts` の `DEAD_END`）が守る、とコメントに書く
   - PL-2 手札のカードをプレイする（GM 不在で、(a) 説明文付き・移り先なしの選択肢をプレイすると説明文が描写として返り、そのカードだけが手札から消え、「GMの描写を待っている」が出ない、(b) 移り先のある選択肢で結末に達し、結末タグを得て、その場で終わる）。(a) のために、SC-2 でシーンに説明文付き・移り先なしの選択肢を1枚足す（SC-5 の (b) の「移り先が空でもまだ出る」と両立させる）。最後にコンソールの誤りが無いこと
2. `gm-session.test.ts`（新規。preview で実測済み：`/gm/sessions` の「自分の募集」（灰色館の一夜、`rc-mine`）から画面だけで始められる）
   - 下ごしらえ（ID なし）：自分の募集を画面から始め、GM のセッションの画面を開く
   - PL-1 描写を書き、選択肢を配る・取り下げる（描写と、移り先なしの選択肢を2枚送る → 1枚を取り下げる）
   - PL-2 手札のカードをプレイする（GM が PL を兼ねてプレイ画面へ移る。プレイ画面にしか無い `link 'GMの画面へ'` を待ってから、描写と、残した1枚が手札にあり、取り下げた1枚が無いことを確かめる。手札は名前をそのまま指定して探す（「選択肢＋新たな選択肢を提案」も「選択肢」で始まる）。残した1枚をプレイすると「GMの描写を待っている」になる）。最後にコンソールの誤りが無いこと
   - `pages.test.tsx` の通しのテストから写すとき、提案と裁定（PL-3・PL-4）は持ち込まない（スコープ外）
   - 「募集を出す」は authoring では GM 不在の募集を出すのが SC-8（読んでから募集を出す）の主な流れなので SC-8 の中、gm-session では既にある募集から始めるだけ（セッション運営）なので ID なし

**AI レビュー（design-reviewer `opus`・edge-case-reviewer `sonnet`）の P1 と対応**

- 同じ ID のステップが複数あると、走らなかったステップが結果に記録されず「通った」に見える → 同じ ID のステップを1本に1つだけとし（検査で止める）、authoring のステップの並びを組み直した（SC-1 → SC-3 → SC-5 → SC-2 → SC-6 → SC-8 → PL-2）。それに伴い、SC-5 の (c) は「行き止まりの注意が消える」で確かめる（経路は後の SC-2 で作るため「届きません」は残る）

## 11. PR 下書き

**課題**：ユースケース（[中核のユースケース](../architecture/use-cases.md)）がどこまで動くかを、テストの結果から見たい（要望：[ユースケースと E2E の結果を紐づける](../backlog/usecase-e2e-report.md)）。CI の E2E は全ルートの描画だけで、通しの確かめは CI で回らず結果も残らなかった。

**解決策**
- E2E にユースケースの ID のタグ（`@SC-1`）とステップ（`test.step('SC-1 …')`）を付けた通しを2本足し（`e2e/usecases/`）、デプロイが E2E の後に `/usecase-report/` を作る（ユースケースごとに通った・落ちた・手前で止まった・テストなし・結果なし、各テストの Playwright レポートへのリンク）
- タグ・ステップと use-cases.md の表の食い違いは `pnpm docs:build` の `check-usecase-tags.mjs` が止める
- `web:check:authoring` は同じ確かめを2か所に置かないよう E2E へ移して消した。トレードオフ：`retries` は足さない（不安定なテストが「通った」に見えるため）、「通った」は主な流れだけの意味（D9・D11）

**テスト**：`scripts/` の T1〜T17（`pnpm tools:test`、169件）、E2E 2本（authoring 2.9秒・gm-session 1.0秒）。骨抜きの確かめ（T20）6件はすべて E2E が落ちた。`web:check:authoring` の check 13件を E2E に移した（`scenarios/` の git の状態の1件は preview が書かないので意図して外した）。ページは描画して確かめた（T21）。

**レビュー観点**
- 実装の AI レビューの P1 は反映済み（10章）。P2 は記録のみ（`save()` の待ち、flaky の表示など）
- プランからのずれ：UI に説明文の入力欄が無く、PL-2 の「説明文付き」は定型の描写で確かめている
- 検査は TS を正規表現で静的に読む（誤検知は止まる側に倒れる）。デプロイは `continue-on-error` で止めない
