# シナリオの公開で JSON に書き込む（C1）

要望：[シナリオ製作者がシナリオを作って公開する](../backlog/scenario-publish.md)（2サイクルのうち C1。C2 は「選択肢の行き先と結末の編集」で、別のプランにする）

## 1. 概要

シナリオ製作者が「共有ライブラリへ公開」すると、ローカルの開発サーバー（`pnpm web:dev`）では `scenarios/<id>.json` に書き込まれ、リロード後も遊べるシナリオとして残るようにする。公開中のシナリオを保存（シーン編集を含む）したときは書き直し、「非公開にする」と `libraryStatus: draft` で書き直す。GitHub Pages のデモ（静的）は書き込まず、メモリ上だけで動き、画面でそれを知らせる。書き込めるのは自分が作者のシナリオだけ。

## 2. 背景

- [ロードマップ](../roadmap.md) M1 の完成の条件2（シナリオ製作者がシナリオを作って公開できる。ローカルの開発サーバーで公開すると JSON として保存され、遊べるシナリオになる。GitHub Pages のデモは保存せずメモリ上だけ）
- 前提の [シナリオを JSON でリポジトリ管理する](../backlog/scenario-json.md) は完了済み。検査（形・ファイル名と id・参照の整合）は `packages/domain/src/scenario/file.ts` の `parseScenarioFile`
- 関わる仕様：[シナリオの構造とセッション開始までの流れ](../cartagraph/scenario-flow.md)「シナリオの入手元」（GM は共有ライブラリから選ぶ。シナリオ製作者が作る）。公開＝共有ライブラリに載る（GM のシナリオ一覧に出る）は今の実装どおりで、変えない。未解決論点に関わる判断は無い
- 要望ファイルの申し送り「村はずれの一歩が `draft`」は、GM 不在の募集（PR #16）で `published` に変わり解消済み。要望ファイルから消した
- 関わる既知の問題：「シナリオの JSON の検査が、数値の範囲と結末・導入の構造を見ていない」（直すときの目安に「公開で書き込む前に入れたい」）と「シナリオの JSON が1本でも壊れていると、アプリが起動しない」。どちらも今回は直さない（D3。書き込む前に今の検査を必ず通すので、壊れた JSON は書かない）。「セッションのスナップショットが無い（開始後にシナリオを直すと進行中のセッションも変わる）」は、公開中の保存がファイルにも残るようになるので追記する
- **ルールの書き換え（D2 に伴う。人間の決定 2026-10-06）**：`docs/process/rules/architecture.md`「構造」と5、`docs/architecture/web-app.md`「シナリオの JSON」は、`scenarios/` を「遊べるシナリオの JSON」、下書きのデモデータは `fixtures.ts` と書いている。D2 で非公開にしたシナリオ（下書き）が `scenarios/` に残るので、「`scenarios/` は公開したことのあるシナリオの JSON（非公開にしたものは draft のまま残る）。デモ用の下書き・テスト専用は `fixtures.ts`」に書き換える
- **重複・分散の報告（最重要ルール3）**：「共有ライブラリ」が仕様の中で2つの意味に使われている。`graph.md`「正史グラフの共有ライブラリ化」・`concept/index.md` とアプリの `/api/library` は格上げしたカード・関係性のテンプレート。`scenario-flow.md`「シナリオの入手元」とシナリオの公開ボタンはシナリオの公開先。用語集に項目は無い。今回は画面の文言を今のまま使い、統合はしない（人間に報告する）

## 3. 詳細設計

### 決定事項（grilling とプランレビューの結果、人間が決定）

| # | 決定 | 採らなかった選択肢 |
|---|---|---|
| D1 | 書き込むのは公開中のシナリオだけ。「共有ライブラリへ公開」で初めて書き、公開中のシナリオを保存したとき（シナリオ編集・シーン編集）も書き直す。下書きはこれまでどおりメモリだけで、リロードで消える | 下書きの保存でも書く／公開の瞬間だけ書く |
| D2 | 公開中のシナリオを「非公開にする」と、ファイルは残し `libraryStatus: draft` で書き直す。ファイルを消すかは人間が git で決める | ファイルを消す／非公開にできなくする |
| D3 | 書き込む前の検査は今の検査（形・ファイル名と id・参照の整合）のまま強めない（数値の範囲・構造の検査は既知の問題に残す） | 範囲だけ足す／範囲と構造 |
| D4 | カード画像（`portraitUrl` の `data:` で始まる URL）は JSON に書かない。メモリ上には残し、画像はこれまでどおりそのブラウザの localStorage だけ | そのまま書く／画像付きは公開を止める |
| D5 | 画面で知らせる。開発サーバーで書き込んだら「scenarios/<id>.json に保存しました」、デモでは「デモのため保存されません（リロードで消えます）」 | 何も出さない |
| D6 | サイクルを2つに分ける。C1（このプラン）：公開で JSON に書き込む。C2：選択肢カードの行き先（シーン・結末のノードだけ）、導入・結末ノードの編集、「結末を追加」で結末タグと結末ノードを対で作る。C2 の最後に「画面だけで作る→公開→GM 不在で結末まで」を通す | 1サイクルにまとめる／編集を先に |
| D7 | `fixtures.ts` にしか無いシナリオ（デモの下書き `sc-draft-well`、テスト専用の `sc-village-always-win`・`sc-exam-*` など）は公開できない。公開・非公開は `422`「デモ用のシナリオは公開・非公開を変えられません」。メモリ上でも公開しない（デモと開発サーバーで同じ振る舞い）。公開しないので書き込みも起きない | メモリだけ公開する／涸れ井戸を JSON に移す |
| D8 | 書き込み（公開・非公開・保存）は、作者（`authorId`）がログイン中の自分（`fx.me`）のシナリオだけ。他人・`system` のシナリオは `403`「製作者でないため変更できません」。`PATCH` は公開中か下書きかに関わらず作者を確かめる（他人のシナリオを編集画面で保存できなくなる）。結果として、既存4本のうち書き換えられるのは作者が `u-me` のガレオンだけ | 止めずに既知の問題に書く |
| D9 | 非公開にしても、既にある募集・セッションは残す（非公開は共有ライブラリの一覧から外すだけ）。下書きから募集を出せる経路（GM の詳細画面を URL で開く、`POST /api/scenarios/:id/recruitments` が公開状態を見ない）も今回は止めない。両方を既知の問題に記録する | 下書きからの募集を止める |
| D10 | エージェントの確認用の開発サーバー（`pnpm web:dev:agent`、5174番）は、既定で書き込みの口を閉じ、デモと同じ「保存されません」にする。書き込みを確かめるときだけ環境変数（`CARTAGRAPH_WRITE_SCENARIOS=1`）で開く。人間用の `pnpm web:dev`（5173番）は書く。追跡済みの `scenarios/*.json` が、別のサイクルの確認で黙って書き換わり、コミットに紛れるのを仕組みで止めるため | 停止時に差分を警告／入れない |

### その他の設計判断（AI が決めたもの）

#### 書き込みの口（Vite のプラグイン、開発サーバー専用）

- `apps/web/vite/scenarioFilePlugin.ts` に置き、`vite.config.ts` の `plugins` に足す。`apps/web/tsconfig.json` の `include` に `"vite"` を足す
- 適用の条件：プラグインは常に入れ、`config` フックで口を開くか（`scenarioFileWriteOpen`）を決める。`serve` で `isPreview` でなく `VITEST` でないときだけ開く（`apply: 'serve'` だけだと Vitest（内部で serve のサーバーを作る）でも入るため）。閉じていれば `configureServer` で口を登録しない。`vite preview` と `vite build`（Playwright の E2E は preview）・Vitest には口が無い（実装で `apply` をやめた：下の define を build・Vitest でも `false` で入れるため）
- 口を開くかどうか：開発サーバーのポートが 5174（`web:dev:agent`）なら、`CARTAGRAPH_WRITE_SCENARIOS=1` が無い限り口を登録しない（D10）。口が無いとき、ブラウザ側は「保存されません」になる（下の「保存先の差し込み」）
- **`@cartagraph/domain` も `@/` も静的に import しない。** Vite は設定ファイルを束ねるとき、`.` で始まらない import を外部扱いにし、Node がそのまま読む。domain の中の import は拡張子を省いているので、Node では解決できず、設定の読み込みで落ちる（`vite dev`・`build`・`preview`・Vitest のすべてが起動しなくなる）。プラグインは domain の検査を `configureServer` の中で `server.ssrLoadModule('@cartagraph/domain/scenario/file')` で読む（Vite に解決させる）。プラグインの中で使うのは `node:` の標準モジュールだけ
- 口の処理は、Vite のサーバーに依らない関数 `handleScenarioPut({ method, contentType, id, body, remoteAddress, scenariosDir, check, format })` に切り出す（テストできるように）。`scenariosDir`・`check`・`format` は必須の引数で、既定値を持たせない（テストが誤ってリポジトリへ書く経路を作らない）。リポジトリのパスは、プラグインを組み立てるところで `import.meta.url` から求める（`process.cwd()` は使わない）
  - `PUT /__dev/scenarios/:id`、本文はシナリオの JSON。`PUT` 以外は `405`。`Content-Type` が `application/json` でなければ `415`（`PUT` と JSON の型で、別のサイトからはプリフライトが要る＝既定の CORS で止まる。`OPTIONS` には応答しない）
  - 応答は成功で `204`、検査の誤りで `422`（本文に誤りの文）、`:id` の誤り・JSON でない本文で `400`、ループバック以外で `403`、整形・書き込みの失敗で `500`
  - `:id` は domain の `scenarioFileIdPattern`（`/^[a-z0-9-]+$/`。下の「domain に足すもの」）で確かめる（`..`・`/`・URL エンコードでリポジトリの外へ書かせない）。書く先は `scenariosDir/<id>.json` に固定
  - 接続元がループバック（`127.0.0.1`・`::1`・`::ffff:127.0.0.1`）でなければ `403`。`server.host: '0.0.0.0'` で LAN に開いているので、別の端末からリポジトリへ書かせない。LAN の IP で開いた画面から公開すると `500`（誤りの文に「localhost で開いてください」）になる。web-app.md に書く
  - 書く前に `check(path, body)`（domain の `safeParseScenarioFile`）をかける。MSW 側でも検査するが、口として単独でも壊れた JSON を書かない
  - 整形は Biome（JSON の整形の正）。`JSON.stringify(scenario, null, 2)` を `biome format --stdin-file-path=scenarios/<id>.json` の標準入力に渡し、標準出力を受け取る。`--stdin-file-path` は常にリポジトリからの相対パス `scenarios/<id>.json`（書き込み先の `scenariosDir` とは切り離す。別のパスを渡すと、Biome は終了コード0のまま違う設定で整形する）、cwd はリポジトリ直下。Biome は `require.resolve('@biomejs/biome/bin/biome')` を `process.execPath` で非同期に起動する（シェルを使わない。開発サーバーを止めない）。`@biomejs/biome` はリポジトリ直下の devDependency（apps/web の依存ではない）。字下げ2の stringify を Biome に通すと、今ある4本と一致することをレビューで確かめ済み
  - 書き込みは原子的にする。同じディレクトリの `.<id>.json.tmp` に書いてから rename で置き換える（書いている途中で開発サーバーが止まっても、途中で切れた JSON を残さない。一時ファイルは `.json` で終わらないので glob に拾われない）
  - ログは `server.config.logger` を使う（Biome の `noConsole`）
- **書いても画面はリロードさせない。** `scenarios/` を監視に足さない（今は glob がディレクトリを監視していないので、新しいファイルでは HMR が起きない。足すと、Vite の glob の処理が新しいファイルで `scenarioFiles.ts` を更新の対象にし、受け取り手が無いので全体リロードになる）
  - 新しいファイル（新規の公開）：書いた後に、`server.environments.client.moduleGraph` で `src/mocks/scenarioFiles.ts` のモジュールを `invalidateModule` する。次に手でリロードしたとき glob が作り直され、新しいファイルを拾う
  - 既にあるファイル（読み込み済みで監視されている）の書き直し：Vite がモジュールを無効化してから HMR を始めるので、`hotUpdate: { order: 'post', handler }` で、口が書いたファイル（`normalizePath` したパスで記録）なら空配列を返して全体リロードを止める。記録は1回で消さず、短い時間（2秒）で消す（Windows では change が2回届くことがある）。`handleHotUpdate`（Vite 7 では非推奨）は使わない
  - web-app.md にある「起動中に足したファイルは再起動で拾う」は、この口で書いたファイルについては不要になる（手で足したファイルは今までどおり）

#### MSW 側

- **保存先の差し込み。** `handlers.ts` に `ScenarioFileStore`（`write(scenario: Scenario): Promise<void>`）と `setScenarioFileStore(store | null)` を置く。既定は `null`（＝書き込まない、デモ）
  - `browser.ts`：口が開いているとき（下の `__SCENARIO_FILE_WRITE__`）だけ、保存先を差し込む。保存先は、`fetch` を差し込める関数 `createDevScenarioFileStore(fetchFn)`（`mocks/devScenarioFileStore.ts`）で作る。`PUT /__dev/scenarios/<id>`（`BASE_URL` を付けない絶対パス）に JSON を送り、`204` なら解決、それ以外は本文を誤りの文として失敗にする。`/__dev/*` には MSW のハンドラが無く `onUnhandledRequest: 'bypass'` で通るが、念のため `bypass()` で包む
  - D10 で口が閉じているとき（`web:dev:agent`）：`PUT` は Vite の SPA のフォールバックで `404` などになり「保存されません」と区別がつかない。そこで、口の有無をプラグインの `config` フックの `define: { __SCENARIO_FILE_WRITE__: JSON.stringify(口を開くか) }`（真偽値のグローバル。型は `src/vite-env.d.ts`）で渡し、`browser.ts` はそれが `true` のときだけ保存先を差し込む（閉じていれば `null`＝デモと同じ。実装で `import.meta.env` の define から変えた）
  - テスト：`setup.ts` の `afterEach` で `null` に戻す。書き込みを確かめるテストだけ、呼ばれたシナリオを記録する偽の保存先を差し込む
- **API**
  - 新規 `POST /api/scenarios/:id/publish`・`POST /api/scenarios/:id/unpublish`。応答は `{ scenario: Scenario; file: ScenarioFileResult }`。`ScenarioFileResult = { saved: true; path: string } | { saved: false } | null`（`null` は書き込みの対象外＝下書きの保存）。応答の型は `entities/scenario/api/types.ts` に置き、`handlers.ts` から `@/entities/scenario/api/types` で import する（層の外の mocks は層を import できる。逆はできない）
  - `PATCH /api/scenarios/:id` も同じ応答の形にする。本文の `libraryStatus` は無視する（公開・非公開は上の2つだけで変える。いまは `PATCH` で直接変えている）
  - 順序：(1) 存在しなければ `404` → (2) 作者が `fx.me` でなければ `403`（D8。`PATCH` も） → (3) 公開・非公開で、`fixtures` 由来（`scenarioFiles` にも無く、`POST /api/scenarios` で作ったものでもない）なら `422`（D7） → (4) 反映後のシナリオを組み立てる（`updatedAt` を今に） → 書き込みの対象（公開・非公開・公開中の保存）なら (5) `toScenarioFile`（D4） → (6) `safeParseScenarioFile` で検査（失敗は `422`、誤りの文を `message` に。デモでもかける） → (7) 保存先があれば `write`（失敗は `500`、`message` に口の誤りの文） → (8) メモリへ反映。どこかで失敗したらメモリは変えない
  - 「`fixtures` 由来か」は、`fixtures.ts` が持つシナリオの id の集合（`scenarioFiles` に無いもの）を `handlers.ts` で求め、`POST` で作った id は含まない
  - 公開中を `publish`・下書きを `unpublish` しても誤りにせず、そのまま書き直す（ボタンの二度押しで失敗させない）
  - 下書きの `PATCH` は検査も書き込みもしない（書きかけで参照が切れたシナリオも保存できる。今の振る舞い）
- **新規作成の id を、既にある id と重ねない。** `POST /api/scenarios` の id は `nextId('sc')`（`sc-1001` など、リロードで数え直す）なので、書き込んだ `sc-1001.json` があると、リロード後に同じ id を作れてしまい、公開で上書きする。重ならない id を選ぶ処理を純粋関数 `nextFreeId(gen: () => string, isTaken: (id) => boolean)`（`handlers.ts` の中、テストのために export）に切り出し、`db.scenarios` に無い id になるまで進める

#### domain に足すもの（`packages/domain/src/scenario/file.ts`）

`Scenario` のスキーマ・フィールドは変えない。足すのは関数と定数だけ。

- `scenarioFileIdPattern = /^[a-z0-9-]+$/`：ファイルにできるシナリオの id。`safeParseScenarioFile` でも確かめる（MSW 側の検査と口の検査をそろえる。そろえないと、MSW の検査を通って口で落ち、`500` になる）。今ある id（`sc-corridor-after` など）と `nextId` の形（`sc-1001`）は合う
- `safeParseScenarioFile(path: string, raw: unknown): { ok: true; scenario: Scenario } | { ok: false; message: string }`：今の `parseScenarioFile` と同じ検査（形・ファイル名と id・参照の整合）＋ id の形。`message` は今の例外の文と同じ（見出しと path を含む）。`parseScenarioFile` はこれを包むだけにする
- `toScenarioFile(scenario: Scenario): Scenario`：`JSON.parse(JSON.stringify(scenario, replacer))` で深く複製し、キーが `portraitUrl` で値が `data:` で始まる文字列なら落とす（`portraitUrl` は `cardDefSchema` にだけあるキーなので、カードがどこにあっても落ちる。`soloStarter.cards` などの数え漏れが起きない）。`data:` 以外の `portraitUrl` は残す。引数は変えない

#### キーの順

zod の `strictObject` は出力のキーをスキーマの順に並べる。MSW のメモリは zod を通した順なので、書き直すとスキーマの順で書かれる。今ある4本のうち `sc-village-start.json` だけ、`soloGrowth` の位置（と `soloEffect` の中の `consumeTag` の位置4か所）がスキーマと違う。**このサイクルで `sc-village-start.json` のキーをスキーマの順に並べ替える**（中身は変えない。`scenarioFiles.test.ts` の「parse した値が生の JSON と `toEqual`」で確かめる）。書き直しでキーの並べ替えだけの差分が出ないようにするため。今後のために、「4本とも、読み込み→`toScenarioFile`→整形がファイルとバイト列で一致する」をテストで固定する

#### 画面

- `entities/scenario/api/mutations.ts`：`usePublishScenario`・`useUnpublishScenario` を足し、`useUpdateScenario` の応答の型を変える（キャッシュには `scenario` を入れる）
- `CreatorScenarioEditPage.tsx`：「共有ライブラリへ公開／非公開にする」を新しいフックに替える。編集中（`dirty`）は公開・非公開のボタンを押せなくし、「保存してから公開」と添える（いまは編集中に押すと、保存前の内容が公開される）。D5 の知らせは、`Editor` の外（ページ側）で、最後に成功したミューテーションの `data.file` から出す（`Editor` は `key={updatedAt}` で保存のたびに作り直されるので、中に置くと消える）。`saved: true` なら「scenarios/<id>.json に保存しました」、`saved: false` なら「デモのため保存されません（リロードで消えます）」、`null` なら出さない。誤り（`403`・`422`・`500`）は `ErrorNote` で出す

## PR 下書き

**タイトル**：シナリオをシナリオ集へ公開すると、開発サーバーでは scenarios/<id>.json に書き込む

### 課題

[ロードマップ](../roadmap.md) M1 の完成の条件2（シナリオ製作者がシナリオを作って公開できる。ローカルの開発サーバーで公開すると JSON として保存され、遊べるシナリオになる。GitHub Pages のデモは保存しない）に当たる。要望は [シナリオ製作者がシナリオを作って公開する](../backlog/scenario-publish.md) の C1、プランはこのファイル。これまで公開はメモリ上の `libraryStatus` を書き換えるだけで、リロードで消えていた。

### 解決策

- 開発サーバー専用の書き込みの口（`apps/web/vite/scenarioFilePlugin.ts`、`PUT /__dev/scenarios/:id`）を足した。検査（`safeParseScenarioFile`）→ Biome で整形 → 一時ファイルに書いて rename。ループバックからだけ受け付ける。書いても画面はリロードさせず、次のリロードで読む
- MSW に `publish`・`unpublish` を足し、`PATCH` は公開中のときだけファイルに書く（下書きはメモリだけ）。保存先は差し込み（`setScenarioFileStore`）で、デモ・テストでは無し。応答に書き込みの結果（`file`）を返し、画面で「scenarios/<id>.json に保存しました」「デモのため保存されません」と知らせる
- 書けるのは製作者が自分のシナリオだけ（403）。fixtures にしか無いデモ・テスト用のシナリオは公開・非公開を変えられない（422）。カード画像の data URL はファイルに書かない
- エージェント用の開発サーバー（`pnpm web:dev:agent`）は既定で口を閉じる（`CARTAGRAPH_WRITE_SCENARIOS=1` で開く）。確認の操作で追跡済みの JSON が書き換わり、コミットに紛れるのを止めるため
- 書き直しでキーの並べ替えの差分が出ないよう、`sc-village-start.json` のキーをスキーマの順に並べ替えた（中身は同じ）。`scenarioFiles.test.ts` はファイルの数を固定しない形にし、公開した JSON をそのままコミットできるようにした
- 人間レビューで足したもの：「共有ライブラリ」を「シナリオ集」（シナリオの公開先）と「共有設定」（格上げしたカード・設定）に分け、「シナリオ作成者／制作者／作者」を「シナリオ製作者」にそろえた（仕様・ノート・画面・用語集）。AGENTS.md の最重要ルール3を「重複・分散は見つけ次第直して報告する」に書き換えた
- トレードオフ：口は Vite のプラグインで、`vite.config.ts` から domain を静的に import できない（Node が解決できない）ため、検査は `ssrLoadModule` で読む
