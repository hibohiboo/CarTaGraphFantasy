# docs にも「1ファイル1責務」を広げる

要望：体制の進化ログの候補「docs にも『1ファイル1責務』を広げる」（[docs/process/evolution.md](../process/evolution.md)）

状態：実装順の1〜3は完了（2026-10-14。1はコミット 5aec1da、2は末尾の「洗い出しの結果」、3は末尾の「ページごとの決定」）。Q1〜Q11 は 2026-10-14 に grilling で、R1〜R8 は実装順の3で人間と決めた。次は実装順の4（標準のモデルの新しいセッションで、「ページごとの決定」のとおりに直す）

## 1. 概要

docs のページは、1つのページが1つの問いに答えるようにする。問いの種類は定義・状態と進捗・優先順位・経緯・未決の5つで、1つのページにこれらを混ぜない。ルールのページ `docs/process/rules/doc-responsibility.md` を新しく作り、既存のページの混ざっている箇所を洗い出して直す。

## 2. 背景

- 2026-09-28、ロードマップを作るときに、AI が「ゴールとマイルストーンの定義」「状態と進捗」「今・次・いつか（優先順位）」を1ファイルに混ぜる案を出し、人間の指摘で分けた（進化ログの候補、参考：tabifuda の ADR 0007「SSOT と単一責務」）
- いまの「1ファイル1責務」は[アーキテクチャルール](../process/rules/architecture.md)「1ファイル1責務」にあり、対象は `apps/`・`packages/` のコードだけ
- docs は、すでに一部が分かれている
  - 定義と経緯：仕様（`cartagraph/`）とデザイナーノート（`notes/`）。[仕様のページの書き方](../process/rules/spec-writing.md)「いまのルールだけを書く」
  - 定義と進捗・優先順位：[ロードマップ](../roadmap.md)（定義、並び順が優先順位）と、要望の状態から計算するダッシュボード
  - 未決：[未解決論点](../open-questions.md)と[仮ルール](../provisional/index.md)
- 混ざっている例（grilling の前に見出しを見て気づいたもの。網羅は実装順の2で行う）
  - `roadmap.md` の adventurer-only の節に経緯（「ティザーを見て…分かった」「git のタグ `before-adventurer-only`」）
  - `architecture/index.md` に定義（「（決着）」の節）と「将来の拡張候補」
  - `architecture/prototype-handover.md` に経緯・定義（デザインシステム）・未決（「未解決・要検討事項」）・推奨
- 未解決論点には関わらない

## 3. 詳細設計

### 決定事項（人間が決定。2026-10-14、grilling）

- **Q1 責務の種類** — 次の5つ。手順（how-to）は定義に含める
  - **定義** — いまどうなっているか（仕様・構成・決まり・手順）
  - **状態と進捗** — どこまで進んだか
  - **優先順位** — 次に何をやるか
  - **経緯** — なぜそう決めたか（理由・採らなかった案・将来の候補）
  - **未決** — まだ決まっていないこと（未解決論点・仮ルールの消し方）
- **Q2 範囲** — `concept/`・`cartagraph/`・`architecture/`・`process/`（ルール）・`screens/`・`roadmap.md`・`backlog/`・`provisional/`・`open-questions.md`・`glossary.md`。対象外は次のとおり
  - `interviews/`：一次資料
  - `plans/`：作業単位の設計書で、混ざるのが本来の形
  - `process/evolution.md`・`process/evolution/`・`process/timeline.md`：経緯そのもの
  - `cartagraph/auto-combat-simulation.md`：生成ページ
  - `notes/`：経緯の置き場そのもの
- **Q3 線引き** — 定義のページには、決まりの目的を述べる一句（「〜のため」）まで書いてよい。経緯の置き場へ移すのは次の3つ。ほかの種類へは1行のリンクだけを置く
  - いつ・誰の指摘で・どの案から選んだか
  - 採らなかった案
  - 将来の候補
- **Q4 経緯の置き場** — ゲームの仕様以外も `notes/` に置く（仕様とノートの1対1を広げる）。`process/` の経緯は、今までどおり進化ログに置く
- **Q5 backlog は例外** — 1要望のファイルは「この要望は何で、いまどうなっているか」に答える1枚のカードとみなし、先頭（frontmatter）の状態と本文の背景・経緯を分けない
- **Q6 機械で止めない** — 今回はルールだけにする（[開発プロセス](../process/index.md)「仕組みにするのは2回目から」）
- **Q7 ルールの置き場** — 新しく `docs/process/rules/doc-responsibility.md` を作り、frontmatter の `paths` に Q2 の範囲を書く。spec-writing.md の「いまのルールだけを書く」のうち、docs 全体に通じる部分（定義のページに経緯を書かない）は新しいページへの1行のリンクにする。仕様とノートの1対1の決まりなど、仕様のページに固有の部分は spec-writing.md に残す
- **Q8 レビューの観点に足さない** — `paths` によって docs のファイルを開くとルールが自動で読み込まれるのを歯止めにする
- **Q9 同じプランで既存のページを直す** — 洗い出し → 人間と決める → 修正、まで行う
- **Q10 ノートのパス** — ゲームの仕様のノートは今の位置（`notes/<名前>.md`）のまま動かさない。`architecture/` のノートは `notes/architecture/<同じ名前>.md`、docs 直下のページのノートは `notes/<同じ名前>.md`（例：`notes/roadmap.md`）。ノートは移すものがあるページにだけ作り、空のノートは作らない
- **Q11 採用日の印は許す** — 「（2026-10-11）」のように、決まりに付けた採用日は進化ログを引く目印として残してよい。経緯の本文だけを移す

### ルールのページ（`doc-responsibility.md`）に書くこと

- 対象（Q2 の範囲と対象外）
- 1ページ1つの問い。5つの種類（Q1）と、それぞれの置き場の表
  - 定義 → 仕様・`architecture/`・`process/` のルール・`glossary.md`・`roadmap.md`（ゴールとマイルストーンの定義）・`screens/index.md`
  - 状態と進捗 → 要望の frontmatter（ダッシュボードが計算する）・既知の問題・画面ごとの課題
  - 優先順位 → `roadmap.md` の frontmatter の並び・未解決論点の「次に詰める候補」
  - 経緯 → `notes/`（Q4・Q10）・進化ログ（`process/`）
  - 未決 → `open-questions.md`・`provisional/`
  - 上の置き場の割り当ては、実装順の2の洗い出しで食い違いが見つかれば、実装順の3で人間と直す
- 線引き（Q3・Q11）と、ほかの種類へはリンク1行だけにすること
- 例外：要望の1ファイル（Q5）
- 機械では止めていないこと（Q6）

## 4. テスト影響範囲

## 5. 新規テストケース

なし（Q6 で、機械の検査は作らない）。

## 6. 実装順

| 順 | 作業 | 担当 | 段 |
|---|---|---|---|
| 1 | ルールのページを作り、関連するページを直す（上の「触るファイル」）。`pnpm docs:build` を通してコミットする | 次のセッションのメイン | **標準** |
| 2 | 範囲内のページの責務を洗い出し、このプランの「洗い出しの結果」に表を書く。ディレクトリごとに並列で読む | 次のセッションのサブエージェント | **軽い** |
| 3 | 洗い出しの結果を人間と見て、ページごとに分ける・移す・そのままにするを決め、このプランに書く | 新しいセッション | **強い**＋人間 |
| 4 | 決めたとおりに移し、ノートを作り、リンクを張り替える。`pnpm docs:build` を通してコミットする | 新しいセッション | **標準** |

1・2 は同じセッションで行い、2 が終わったらこのプランを更新してセッションを閉じる。3 は強いモデルのセッション、4 は標準のモデルのセッションで行う。
