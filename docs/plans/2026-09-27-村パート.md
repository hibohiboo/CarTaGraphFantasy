# プラン：村パート（村スタート冒険者キャンペーン C3）

書式は `docs/process/index.md` の「プランドキュメントの8項目」。親プラン [村スタート冒険者キャンペーン](2026-09-23-村スタート冒険者キャンペーン.md) の C3 の詳細設計を、C2（[自動戦闘エンジン](2026-09-23-自動戦闘エンジン.md)）と同じ扱いで個別プランに切り出したもの。全体構想・決定事項1〜13は親プランが正で、ここでは C3 固有の決定だけを書く。C3 の決定で親プランの記述を上書きした箇所は、親プラン側にも反映する（実装順タスク1、3-1 の「親プランへの注記」）。

## 1. 概要

GM不在のソロシナリオ `sc-village-start` に村パートを足す。PLは「村の広場」から好きな順に3つの依頼を選び、体・技・心のどれで解決するかを選ぶ。選んだ能力値が上がり、依頼人から引換カード（「〇〇からの報酬」）を受け取る。お店では引換カード1枚を戦闘スキル1枚と交換できる。キャラクターは旅人から始まり、最初の依頼で能力値と HP を得て探索者に、最初の戦闘スキルで行動値を得て冒険者になる。どこまで進んだかは、GM専用ゾーンに置く**達成カード**と、選択肢カードの**配る条件・使える条件**で表す。開始時に戦闘スキルを配っていた `soloStarter` は、このシナリオから外す。

## 2. 背景

### 経緯

C2（PR #6）が 2026-09-27 にマージされ、`sc-village-start` は「導入→冒険者試験→結末」まで遊べるようになった。C3 着手時の `grilling`（2026-09-27）で、親プランが C3 に積み残していた論点（依頼の内容、能力値の上限、お店の実現方法、`soloStarter` の置き換え）を人間が決めた。その後のプランのAIレビュー（設計整合・仕様整合・テスト網羅）の指摘を受けて、人間の判断で一部を決め直した。決定は本ページ末尾の「決定事項（C3）」、レビューの記録は「プランレビューの記録」。

### C3 着手時の調査で判明した前提

- **判定（能力値＋2d6）は未実装。** `CheckSpec`・`CardDef.check` は型だけで、処理はどこにもない
- **能力値を増やす操作が、基本操作セットに無い。** 基本操作1〜8（`play-and-field.md`）はカードとシーンの操作だけで、`Character.abilities` はカードではない。キャラクターデッキからカードを手放す操作、HP・行動値を与える操作も無い
- **ソロ開始のキャラクターは、`soloStarter` で開始直後から冒険者になる。** `sc-village-start` の `soloStarter` は HP20・行動値10と、斬撃・渾身の一撃・応急手当を配る。親プランの境界値「村パート直後は探索者」は、これを外すまで成り立たない（C2 で注記済み）
- **シーン遷移は手札の選択肢カードを遷移先ノードのもので配り直す**（`planTransition`）。ただし、ソロ開始（`buildSoloSession`、handlers.ts）と自動戦闘の勝利時の配布（handlers.ts の auto-combat、`node.cards` を直接配る）は `planTransition` を通っていない。済んだ依頼を配らない仕組みは無い
- **村のシーンには敵が出ない。** 既知の問題「同じ自動戦闘のシーンに戻ると、敵カードが場に増える」は、自動戦闘のノードに戻ったときだけ起きる。村パートでシーンを行き来しても起きない
- **既存の `canFight`（autoCombat.ts）は、回復カードしか持たないキャラクターも「戦える」とみなす。** 応急手当だけを習って試験に入ると、勝てず、試験から戻る手段も無い
- **既存カード「炎の剣」（`c-flame-sword`）はタグ `報酬` を持つ。** 正式仕様の「報酬カード」（`character-growth.md`）は物語に密着した成長そのもので、お店で手放すものとは別物
- **`VillageStartPage.tsx` はシナリオID `sc-village-start` を固定で開始する。** テスト専用シナリオは名乗る画面から始められない
- **`scripts/simulate-auto-combat.ts` は `sc-village-start` の `soloStarter` を読む。** 外すとシミュレーションが動かなくなる。このスクリプトは型検査・CI の対象外（既知の問題）

**仮ルールの中身（solo-village.md に書く）**：

1. **適用範囲** — 人間GMのいないセッション（ダミーGM）だけ。人間GMのセッションでは、下の条件・効果はどれも機械的には働かない（GM が目安にするかは決めない）
2. **達成カード** — 依頼などを片づけたことを示す、セッションの進行の記録。種別は情報カード（`info`）で、タグ `達成` と、何を片づけたかのタグ（例：`達成:猪`）を持つ。基本操作1で、セッションの場の GM専用ゾーンに置く。PLはその存在を知らず、プレイ画面・feed・描写・選べない理由のどこにも出ない。情報カードの本来の役割（伏せておき条件成立で表にする）とは違い、ずっと公開しない。キャラクターへは持ち帰らない
3. **配る条件** — 選択肢カードは「キャラクターデッキのカードと、GM専用ゾーンの達成カード」のタグ・IDについての条件を持てる。満たさなければ、そのカードは配らない（手札に出さない）。判定するのはシーンに入ったとき（ソロ開始、次のシーンへ進む、自動戦闘の勝利で配るとき）
4. **使える条件** — 同じ形の条件で、満たさなければ手札に出すが選べない。画面では選べない理由（「『引換』のカードが必要」など）を出す。`unlock.md` の「ハードロックにしない」からの、GM不在の自動進行に限った逸脱（先例：auto-combat.md の「戦える状態でなければ自動戦闘のシーンへ進めない」）。達成カードのタグは使える条件に使わない（理由の表示で GM専用ゾーンの存在が漏れるため）
5. **能力値の上がり方** — 能力値を持たないキャラクターが初めて能力値を上げると、体・技・心を各1で持ち、選んだ能力値に＋1する。1回の効果で＋1、上限は5（上限なら上がらない）。足し算なので、依頼を解決する順番によらず同じ結果になる
6. **HP・行動値** — 効果を適用した結果、能力値か戦闘スキルを持つのに HP が無ければ、シナリオが決めた HP を持つ（探索者になったとき）。戦闘スキルを持つのに行動値が無ければ、シナリオが決めた行動値を持つ（冒険者になったとき）。すでに持っていれば変えない。役割の定義（`role-and-scenario.md`：探索者＝能力値・HP、冒険者＝戦闘スキル・行動値）どおり
7. **引換カード** — 依頼を解決すると、依頼人から引換カード（アイテムカード、タグ `引換`、名前は「〇〇からの報酬」）を1枚、無償で受け取る。`character-growth.md` の報酬カード（セッションクリア時に得る、物語に密着した成長）とは別物で、セッションの途中で得て途中で手放す
8. **お店** — 引換カード1枚を手放して、並んだ戦闘スキルから1枚を習う。引換カードの出どころは問わない。すでに持っているスキルは並ばない。CP 予算とは別の、数量固定の交換
9. **解決の描写** — 成長の効果を持つ選択肢カードを選ぶと、そのカードの説明文と、効果の文（「体が1上がった（体 2）」「『農家のおばさんからの報酬』を受け取った」など）を描写にする。次のシーンへ進むカードでも、遷移の定型文で上書きしない。遷移しないカード（お店で習うカード）は、「GMレスセッションでの選択肢の描写」どおり、選んだ1枚だけを手札から消して同じシーンに留まる
10. **即時反映** — これらはすべてセッション中にキャラクターへ反映する（ソロでは所有者＝ドライバー。`party-and-session.md` の例外）

### 3-2. ドメイン型（`packages/domain/src/index.ts`、型変更あり）

親プラン決定事項3「新しいカード種別・データ構造は増やさない」を上書きする（C3-15）。カード種別は増やさないが、次のフィールドと型を足す。

```ts
/** 配る条件・使える条件（docs/cartagraph/solo-village.md、仮ルール）。すべての項目を満たせば真 */
export interface CardCondition {
  /** これらのタグのカードをすべて持っている */
  hasTags?: string[];
  /** これらのタグのカードを1枚も持っていない */
  lacksTags?: string[];
  /** これらのIDのカードを持っていない（お店で習ったスキルを並べないため） */
  lacksCards?: string[];
}

/** GM不在のソロで、選択肢カードをプレイしたときの成長の効果（仮ルール） */
export interface SoloEffect {
  raiseAbility?: keyof Abilities;
  /** キャラクターデッキへ加える（引換カード・習ったスキル）。ID はそのまま保ち、オブジェクトだけ複製する */
  gainCards?: CardDef[];
  /** このタグのカードをキャラクターデッキから1枚手放す（引換カード） */
  consumeTag?: string;
  /** GM専用ゾーンに置く達成カード */
  achievement?: CardDef;
}

CardDef に追加:
  dealWhen?: CardCondition;
  playWhen?: CardCondition;
  soloEffect?: SoloEffect;

Scenario に追加:
  /** GM不在のソロの成長で与える HP（探索者になったとき）と基本行動値（冒険者になったとき）。solo-village.md、仮ルール */
  soloGrowth?: { hp: number; baseActionValue: number };
```

`soloStarter` は型もフィールドも残す（テスト専用の試験シナリオ `sc-exam-*` だけが使う）。新フィールドはすべて optional で、既存の fixture には足さない。

### 3-3. 村パートの計算（`packages/domain/src/soloVillage.ts`、新規・純粋関数）

`package.json` の exports に `"./soloVillage"` を足す（barrel export にしない）。

```ts
/** 条件の判定に使うカード：キャラクターデッキと、GM専用ゾーンのうちタグ「達成」を持つもの */
export function heldCards(character: Pick<Character, 'deck'>, field: Session['field']): CardDef[];
export function meetsCondition(cond: CardCondition | undefined, held: CardDef[]): boolean;
/** 使える条件を満たさない理由（満たすか条件が無ければ null）。例：「『引換』のカードが必要」 */
export function unplayableReason(card: CardDef, held: CardDef[]): string | null;
/**
 * 効果を適用した後のキャラクターと、描写・feed に出す文を返す。入力は書き換えない。
 * lines には達成カードを書かない。consumeTag のカードが無ければ { ok: false }
 */
export function applySoloEffect(
  character: Character,
  effect: SoloEffect,
  growth: Scenario['soloGrowth'],
): { ok: true; character: Character; lines: string[] } | { ok: false; error: string };
```

- 「戦闘スキルを持つ」の判定は `deriveArchetype` と同じ `tags.includes('戦闘スキル')` を使う（判定を1か所にそろえるため、`index.ts` に小さな関数を切り出して `deriveArchetype` からも使う）
- 5 のまま上げようとしたときの `lines` は「体はこれ以上上がらない（体 5）」
- `sceneTransition.ts` に `dealChoices(node, held, session)` を切り出す。ノードの選択肢カードを返し、GM不在のセッション（`gmId === SYSTEM_GM_ID`）なら `dealWhen` で絞る。人間GMのセッションでは絞らない。`planTransition` は引数 `held` を受け取ってこれを呼ぶ。`buildSoloSession` の導入の手札と、自動戦闘の勝利時の配布（handlers.ts）もこれを呼ぶように直す

### 3-4. API（`apps/web/src/mocks/handlers.ts`）

`POST /sessions/:id/play` を拡張する（新しいAPIは作らない。C3-6）。GM不在のセッションでだけ、次の順に処理する（人間GMのセッションでは `playWhen`・`soloEffect` を無視し、従来どおり）。

1. `playWhen` を検査する（**実装レビューで補足**：手放すタグのカードをデッキに持っていないときも、同じく選べない理由で 422。`unplayableReason` が見る）。満たさなければ 422（本文は `unplayableReason` の文）。自動戦闘のシーンへ進むカードでも、`canFight` より先に検査する
2. `soloEffect` があれば `applySoloEffect` で効果適用後のキャラクターと `lines` を**計算する**（まだ書き込まない）。`ok: false` なら 422
3. `nextNodeId` があれば、**効果適用後の**キャラクターと「GM専用ゾーン＋新しい達成カード」から `held` を作り、`planTransition(…, held)` を呼ぶ。自動戦闘のシーンへ進むなら `canFight` も効果適用後のキャラクターで判定する。失敗なら 422
4. ここまですべて通ったら書き込む：キャラクターを差し替え、達成カードを複製して `field.gmOnly` に置き、feed に `lines` を1件ずつ記録し、遷移を適用する
5. 卓上の描写は、カードの説明文＋`lines`。遷移を伴うときも `applyTransition` の定型文（「〇〇へ進んだ。」）で上書きしない（`applyTransition` に描写を渡す引数を足す）。遷移しないカードは、既存の「選んだ1枚だけを手札から消して留まる」分岐で、描写だけを説明文＋`lines` にする

どこかで失敗したら、セッション・キャラクターは一切変わらない。`start-solo` は変えない（`soloStarter` が無ければ空のキャラクター＝旅人）。

## 決定事項（C3、2026-09-27、grilling とプランレビュー後の人間の判断）

1. **村パートは `sc-village-start` に直接組み込む**。C4 は旧チュートリアルの置き換えと街道に絞る
2. **村パートはハブ型**。「村の広場」から好きな順に依頼を選ぶ
3. **依頼の解決に判定は使わない**。解決方法を選べば確定で解決し、その能力値が上がる（親プラン決定事項8のまま）
4. **能力値の加算は、GM不在のソロの仮ルールとして別ページに書く**。基本操作セットには足さない（初期配分が未解決論点のため）
5. **開始時は能力値なし（旅人）。最初に能力値を上げるとき体・技・心を各1で持ち、選んだものに＋1。1件で＋1、上限5**
