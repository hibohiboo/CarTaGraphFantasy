# apps/web のディレクトリ構成を Feature-Sliced Design に従わせる

要望：[apps/web のディレクトリ構成を Feature-Sliced Design に従わせる](../backlog/web-fsd.md)

## 1. 概要

`apps/web/src` を [Feature-Sliced Design](https://feature-sliced.design/ja)（FSD）の層（`app / pages / widgets / features / entities / shared`）・スライス・セグメントに並べ替える。層の依存の向きは Biome の `noRestrictedImports` で機械的に止める。**振る舞いは変えない**（ファイルの移動・分割と import の書き換えだけ。関数・コンポーネントの中身は変えない）。

## 2. 背景

- 人間の要望（2026-10-03）：「apps/web のディレクトリ構成は FSD に従うようにしたい。何も無いのは問題で、練られたパターンがあるなら従っておくのがよい」。いまのアーキテクチャルール「依存の向き」は、apps/web の中のディレクトリ間の向きを決めていない
- M1 の残り（シナリオの公開、GM の募集と開始、GM が PL を兼ねる）はどれも画面を大きく作るので、その前に構成を決める
- 関わるルール：[アーキテクチャルール](../process/rules/architecture.md)（構造・依存の向き・境界の barrel 禁止・React の書き方・副作用の分離）、[テストルール](../process/rules/testing.md)。正式仕様（`docs/cartagraph/`）の変更は無い。未解決論点に関わる判断は無い
- 進化ログの未評価の候補「肥大化した1ページ1ファイルの分割先が未定義」（2026-09-21）は、FSD のスライスとセグメント（`pages/<ロール>/<ページ>/ui/` に部品を置ける）で解決する見込み。候補を閉じるかは、振り返りで人間が裁定する
- 規模：`apps/web/src` の65ファイルの移動・分割と、テスト・mocks・設定・文書を合わせて約80ファイル。基盤の原則7（サイクルは小さく）の目安を超えるが、層を途中で半分だけ FSD にした状態を作らないため、人間の判断（D7）で1サイクルにする。中身を変えない機械的な移動が大半で、コミットを分けて読めるようにする

### bulletproof-react との比較（要望で決めた方針）

正は FSD の1つにし、[bulletproof-react](https://github.com/alan2207/bulletproof-react) は比較として読んだ（2026-10-03）。

| | FSD | bulletproof-react |
|---|---|---|
| 構成 | 6層（app・pages・widgets・features・entities・shared）、スライス、セグメント | 3段（app・features・shared） |
| 依存 | 下の層だけ。同じ層のスライスどうしは禁止 | shared → features → app の一方向。features どうしは禁止 |
| 入口 | 公開 API が基本だが index は必須でない | barrel を避けて直接 import |

- **構成として採らなかった理由** — 3段だと、カードの見た目（GameCard）やエンティティの取得のような「複数の機能から使う業務の部品」の置き場所が shared か features かで揺れる。FSD は entities 層でこれを決めている。また、FSD は用語と規則が文書になっていて（日本語もある）、ルールの正にしやすい
- **参考にする点** — barrel を避けて直接 import する（D1 と同じ）。API 層・テスト・状態管理の指針は、M1 の残りで画面を作るときに読む

## 3. 詳細設計

### 決定事項（grilling の結果、2026-10-03）

| # | 決定 | 採らなかった選択肢 |
|---|---|---|
| D1 | 公開 API の index.ts は作らない。スライスの外からはファイルを直接 import する（いまの barrel 禁止のまま。FSD も index を必須としておらず、react-best-practices の `bundle-barrel-imports` とも合う）。apps/web にも Biome の `noBarrelFile`・`noReExportAll` を広げる | スライスごとに名前付きの再エクスポートの index を許す |
| D2 | 層の依存の向きは Biome（`style/noRestrictedImports`）で止める。スライスの外は `@/<層>/…` のエイリアス、スライスの中は相対パスで import する（FSD の推奨と同じ） | Steiger（FSD 公式。ベータ版で、index 前提のルールを止める必要がある）／両方 |
| D3 | pages はロールのフォルダで束ね、その下に1ページ1スライス（`pages/gm/session-manage/`）。ロールのフォルダには共有コードを置かない（FSD のスライスのまとめ方） | フラットに並べる（`pages/gm-session-manage/`） |
| D4 | `src/mocks/`（MSW）・`src/test/`・`src/main.tsx`（エントリ）は FSD の層の外に置く。**層の外のファイルは層を import してよい。層は層の外を import しない** | shared に入れる |
| D5 | `lib/queries.ts` の取得・変更のフックは、対象のエンティティの `api` セグメントに置く（取得は `api/queries.ts`、変更は `api/mutations.ts` に分ける。FSD の React Query の頁が、取得と変更を混ぜないよう勧めているため）。features は UI と対になった利用者の操作だけにする | 変更ごとに features のスライスを作る |
| D6 | `components/ui.tsx` は1ファイルのまま shared/ui に移す。部品ごとの分割は既知の問題に記録して次に回す | 部品ごとに分ける |
| D7 | 1サイクル・1PR。コミットは「移動だけ」→「層ごとの書き換え」の順に区切る | 2サイクルに分ける |
| D8 | ルート一覧 `routes.ts`（ナビとサイトマップの唯一の情報源）は `shared/routes/routes.ts` に移す。pages（ホーム・サイトマップ）が使うので、app に置くと上の層への依存になる。FSD の公式もルート定数を shared のセグメントの例に挙げている。`router.tsx`（ページを並べる）は app に残す | app に残し、pages からの import を例外にする |

### その他の設計判断（AI が決めたもの）

- **クエリキーは shared** — `keys`（クエリキーの一覧）を `shared/api/queryKeys.ts` に置く。セッションの変更がキャラクターのキャッシュも無効化するなど、エンティティをまたぐ無効化があり、キーをエンティティに置くとエンティティどうしの import（FSD で禁止）になるため。FSD の React Query の頁も、キーを shared に置く例を挙げている。採らなかった選択肢：FSD の `@x`（エンティティどうしの交差 import の記法）。今回の無効化はキーだけで足りるので使わない
- **ページ共通のスタイルは shared** — `pages/pages.module.css`（20ページと `NameProposal` が使う）を `shared/ui/page.module.css` に移す。いまは `NameProposal`（widgets になる）が pages の CSS を読んでいて、上の層への依存になっている（[既知の問題](../architecture/known-issues.md)「共通部品 NameProposal が、ページ側の CSS を読んでいる」が解消する）
- **一度しか使わないものは、使う側に置く**（FSD の原則）— `PlayMat`（チュートリアルだけ）と `AutoCombatPanel`（プレイ画面だけ）は、そのページのスライスの `ui` に置く。`cardImageStorage.ts`（シーン編集だけ。localStorage を扱う副作用）は、シーン編集のスライスの `api` に置く
- **エンティティの分け方は packages/domain に合わせる** — 募集（Recruitment）は domain と同じく session に置く。解放済みカードプール（`useCardPool`。基本カード・解放済みカード・CP の予算を返す）は、domain で `user/` が持つ（用語集「解放済みカードプール」はプレイヤー単位）ので user に置く
- **domain と web で、エンティティの依存の規則が違う** — domain の中は決まった向きならディレクトリをまたげる（例：`scenario → card`）。web の entities は FSD に従って、エンティティどうしの import を禁止する。複数のエンティティを組み合わせる UI（例：シナリオのデッキにカードの見た目を並べる）は、widgets か pages で組み合わせる。この違いを architecture.md に書く
- **ルールブックの本文** — `content/rulebook.ts`（docs の要約。ルールブックの目次と節のページが使う）は、処理を持たない静的な内容なので `shared/content/rulebook.ts` に置く
- **名前** — スライス名は、ページ・部品の役割を英語のケバブケースで付ける（ルートのパスとは揃えない。例：`/pl/sessions` は `session-browse`）。ルールブックの目次は `toc`（`index` は barrel の index.ts と紛らわしい）。プレイ画面の部品の widget は `play-screen`（用語集の「プレイ」はカードを出す操作の意味なので、そのままの `play` は避ける）
- **スライスの直下にファイルを置かない** — スライスの中は必ずセグメント（`ui`・`api`・`lib`・`model`）に分ける。スライスの直下にファイルを置くと、`../` だけで別のスライスに届き、Biome の検査をすり抜けるため（下の「依存の向き」）。architecture.md の規則にする
- **app 層** — FSD の app 層はセグメントだけの層だが、いまの `AppShell.tsx`・`router.tsx` は層の直下に置いたままにする（app は一番上の層で、すり抜けの心配が無い）。`styles/` だけをセグメントにする
- **エイリアス** — `tsconfig.json` には `@/*` → `src/*` があるが、Vite の設定に無い（いまは使われていない）。`vite.config.ts` の `resolve.alias` に `'@': fileURLToPath(new URL('./src', import.meta.url))` を足す（Vitest も同じ設定を使う。`node:url` の型は vite の型が読み込む Node の型で解決される。手順0の直後に `pnpm web:typecheck` と `pnpm web:build` で確かめ、通らなければ止めて報告する）。Playwright は tsconfig の `paths` を読む
- **層の外からの import** — mocks・test・main.tsx から層を import するときは `@/` を使う

### 依存の向き（D2）

```text
app → pages → widgets → features → entities → shared
（mocks・test・main.tsx は層の外。層の外は層を import してよい。層は層の外を import しない）
```

`biome.json` の `overrides` に、`apps/web/src/<層>/**` ごとに `style/noRestrictedImports` の禁止パターンを置く。禁止パターンの正は `biome.json`、理由と考え方の正は architecture.md（packages/domain と同じ分担）。

- 上の層：`@/<上の層>` と `@/<上の層>/**`（サブパス無しも書く）
- 同じ層の別スライス：`@/<自分の層>` と `@/<自分の層>/**`（スライスの中は相対パスで import するので、エイリアスで同じ層を指すのは別スライスだけ）
- スライスの外へ出る相対パス：`../../**` と `./../../**`（Biome は import の文字列を正規化しないので両方書く。セグメントの直下にファイルを置くので、`ui/` から `../../` はスライスの外）
- 層の外：`@/mocks`・`@/mocks/**`・`@/test`・`@/test/**`
- shared：すべての層（`@/app`〜`@/entities`）と、`@/shared/**`（shared の中は相対パスで import する）、`../../**`・`./../../**`（層の外へ出る）
- app：層の外（`@/mocks/**`・`@/test/**`、相対の `../**`・`./../**`）だけを禁止。ほかの層はすべて許す
- 層ごとの override に共通の禁止（層の外）も繰り返して書く（Biome は、重なる override の同じルールのオプションを後のもので置き換えるため、全体用の override には `noRestrictedImports` を入れない）
- `apps/web/src/**` 全体の override に `performance/noBarrelFile`・`noReExportAll`（D1）。層ごとの override より前に置く
- `@cartagraph/domain/*` と外部パッケージは、どの層からも許す
- 循環は既存の `suspicious/noImportCycles`（最上位で有効）。`@/` を通した循環も検出できることを確かめる
- 止めると害の無い過剰な検出：同じスライスへ外から戻るパス（`../../../entities/card/lib/x`）も止まる。スライスの中は相対で短く書けばよいので、それでよい

止められないもの：

- スライスの直下に置いたファイルから `../` で別スライスへ届く import（「スライスの直下にファイルを置かない」の規則で防ぐ）
- エイリアスの途中に `..` を入れる書き方（`@/shared/../pages/x`）。そう書く理由が無いので規則として「エイリアスに `..` を入れない」を書く

## 5. 新規テストケース

振る舞いを変えないので、新規の単体・画面のテストは足さない。代わりに、機械の検査が効くことと、振る舞いが変わっていないことを確かめる。

### Biome の層の検査（実ファイルに一時的に入れて確かめ、戻す）

判定は `pnpm exec biome lint <ファイル> --only=style/noRestrictedImports`（またはルール名と、層ごとのメッセージの文言）で行う。違反の import は「使っていない import」でも落ちるので、ルール名で判定しないと、層の検査が効いていなくても止まったように見える。入れた後は `git diff` で1行入ったことを、戻した後は差分が空になったことを確かめる（testing.md「骨抜き禁止」）。

| # | 対象ファイル | 入れる import | 期待 |
|---|---|---|---|
| 1 | shared/ui/ui.tsx | `@/entities/card/ui/GameCard` | 止まる（shared → entities） |
| 2 | shared/ui/ui.tsx | `@/shared/lib/format` | 止まる（shared の中はエイリアスを使わない） |

### 振る舞いを変えていないこと

- **テスト名の突き合わせ** — 手順0で `pnpm --filter @cartagraph/web exec vitest run --reporter=json --outputFile=<スクラッチパッド>` を記録し、移した後と比べる。比べるのは各テストの「ファイル名・describe・it」の組（ファイル名は新しいパスへの対応で読み替える）と結果。件数、skipped・todo が0件であることも比べる。差分が空になることで判定する
- **型検査**：`pnpm web:typecheck`
- **ビルドのチャンク**：移す前後で `pnpm web:build` の `dist/assets` のチャンク名を比べ、lazy の5ページのチャンクが残っていることを確かめる。ビルドのログに「dynamic import will not move module into another chunk」の警告が出ないこと
- **CSS**：`pnpm web:build` の出力の CSS に、トークン（`--` で始まる変数）とページ共通のスタイルが入っていること
- **ブラウザでの通しの操作**（手順9）
- **docs**：`pnpm docs:build`（check-doc-anchors が rulebook を読めること）

### 仕組みにしない理由

上の層の検査の確かめ方は、一度きりの手作業。Biome の設定に対する固定のテスト（違反を書いた見本のファイルに lint をかけて、止まることを確かめるスクリプト）を作れば回帰を防げるが、今回は入れない。Biome の設定はコミット前のフックと CI で全ファイルにかかり、設定を壊したときは「既存のコードの違反が出ない」ことしか分からない、という弱さは残る。振り返りで、進化ログの候補として出す。

## 実装中の追記（2026-10-03）

- ビルドのチャンクが1つ増えた（`mutations.js`、436 バイト）。中身はシナリオの作成・更新のフック（`entities/scenario/api/mutations.ts`）で、使うのは遅延読み込みの制作者の3ページだけ。もとの `lib/queries.ts` では本体のチャンクに入っていたものが、ファイルを分けたことで制作者のページ側へ移った。振る舞いは変わらず、本体のチャンクが少し小さくなっただけなので許容した。lazy の5ページのチャンクは残っており、dynamic import の警告も出ていない
