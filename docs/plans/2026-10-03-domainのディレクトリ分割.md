# packages/domain をドメインごとのディレクトリに分ける

要望：[packages/domain をドメインごとのディレクトリに分ける](../backlog/domain-structure.md)

## 1. 概要

`packages/domain/src/` の直下に並んだファイルと、型を全部持つ `index.ts` を、仕様ページに合わせたドメインごとのディレクトリ（`check/`・`card/`・`character/`・`autoCombat/`・`scenario/`・`session/`・`soloVillage/`・`user/`・`library/`）に分ける。`index.ts` は廃止し、利用側は実ファイルを直接 import する。ディレクトリ間の依存の向きを表で決め、テストで機械的に守る。**振る舞いは変えない**（型・関数の中身はそのまま移す。export するものが増えるだけ）。

## 2. 背景

- PR #11 の人間のコードレビューで「`packages/domain` の配下がフラットで読みづらい」と指摘があった。案を比べて指針を決めた（要望ファイル、2026-10-03）
- いまの `index.ts`（344行）はユーザー・カード・キャラクター・シナリオ・募集・セッション・ライブラリの型の置き場で、まとまりはファイル名の頭（`scenario*`）にしか表れていない。次の要望（シナリオの公開、ルールとカードプールの JSON 化）でファイルが増える前に分ける
- 関わるルール：[アーキテクチャルール](../process/rules/architecture.md)「構造」「境界」（barrel 禁止、`packages/domain` の型と用語は docs に対応させる）。指針はこのサイクルでアーキテクチャルールに書く
- 関わる仕様：用語・型の意味は変えないので、仕様ページの変更は無い。ディレクトリの分け方は仕様ページに合わせる（下表）。未解決論点に関わる判断は無い
- **要望ファイルの指針からの変更（2026-10-03、人間が確認済み）**：D3（ファイル名は `model.ts`。要望の例は `scenario/schema`）、D4（`check/` を `card/` の下に足す。要望は `card/` が土台）、D5（募集は `session/`。要望は `scenario/`）。プランレビュー（仕様整合）で「募集の持ち主は scenario-flow.md」と指摘があり、人間にあらためて確認して `session/` に決まった

## 3. 詳細設計

### 決定事項

| # | 決定 | 採らなかった選択肢 |
|---|---|---|
| D1 | ドメインごとのディレクトリに、型（zod スキーマを含む）・ロジック・テストを同居させる。分け方は仕様ページに合わせる（例外は下の「仕様ページに合わせる、の例外」） | フラットのまま／技術の種類ごと（`types/`・`schemas/`）／パッケージ分割 |

| D5 | `UserRole`・`CurrentUser` は `user/`、`LibraryEntry` は `library/`、募集（`Recruitment`）は `session/` | 募集を `scenario/` に／`user/` にまとめる |
| D6 | 依存の向きを表で固定し、テストで守る（下の「依存の向き」） | ルールに書くだけ |

### 仕様ページに合わせる、の例外

ルール（architecture.md）にも同じ例外を書く。

1. **カードが持つ属性の型は `card/`** — `CombatEffect`・`DiceExpr`（出典は auto-combat.md）、`CardCondition`・`SoloEffect`（出典は solo-village.md）は `CardDef` の属性で、`cardDefSchema` と `soloEffectSchema` が getter で互いを参照するので、同じ `card/model.ts` に置く。それを使うロジック（`resolveAutoCombat`・`applySoloEffect`）は各ドメインに置く
2. **カードの条件の判定も `card/`** — 配る条件・使える条件の判定（`meetsCondition`・`conditionFailure`）は、セッションの遷移（`session/transition.ts`）と村のルール（`soloVillage/rules.ts`）の両方が使う。`soloVillage/` に置くと session との間で循環するので `card/condition.ts` に置く。仮ルール（solo-village.md）であることはファイル冒頭に書く
3. **判定（`CheckSpec`）は `check/`** — カードの属性だが、持ち主は exploration-check.md なので `check/` に置く（例外1より D4 を優先する）
4. **募集は `session/`** — 募集→応募→確定は scenario-flow.md が決着として書いているが、募集は GM がシナリオからセッションを立てる手続きで、シナリオの定義そのものではないので `session/` に置く（人間の判断、2026-10-03）

### 依存の向き（D6）

各ディレクトリが import してよい先（同じディレクトリの中は自由）。この表をそのまま `layers.test.ts` のデータにし、architecture.md にも書く。

| ディレクトリ | import してよい先 |
|---|---|
| `check/` | なし |
| `user/` | なし |
| `card/` | `check/` |
| `library/` | `card/`・`check/` |
| `character/` | `card/`・`check/` |
| `autoCombat/` | `character/`・`card/`・`check/` |
| `scenario/` | `autoCombat/`・`character/`・`card/`・`check/` |
| `session/` | `scenario/`・`autoCombat/`・`character/`・`card/`・`check/` |
| `soloVillage/` | `session/`・`scenario/`・`autoCombat/`・`character/`・`card/`・`check/` |

- `user/`・`library/` はいま domain の中のどこからも import されない。必要になったら表に足す
- `autoCombat/` が `character/` に依存するのは、`canFight` がキャラクターの HP・行動値・デッキを見るため。`session/` が `scenario/` に依存するのは、`proposalHandling`・`SpaceModel`・遷移の計算のため

### 機械的な検査（`packages/domain/src/layers.test.ts`）

- 判定関数 `layerViolations(files: Record<string, string>): string[]`（キーは `src/` からの posix の相対パス、値はソース）を同じファイルに置き、テストする
- 見る import：`import … from`・`import type … from`・`export … from`・副作用だけの `import '…'`・動的な `import('…')`（`typeof import('…')` を含む）。複数行にまたがる import も見る。引用符は一重・二重の両方
- 違反とするもの
  - 表に反するディレクトリへの相対 import（パスは正規化してから判定する。`./../x`・`../card/../scenario/x` もすり抜けない）
  - `src/` の外へ出る相対 import
  - 自分のパッケージ名での import（`@cartagraph/domain/…`）
  - 表に無いディレクトリのファイル
  - `src/` 直下の `.ts`（`layers.test.ts` 自身を除く）
  - 名前が `index.ts` のファイル（どの深さでも。barrel 禁止）
- 違反としないもの：外部パッケージ（`zod`・`vitest`・`node:fs` など）、同じディレクトリの中、表で許した先
- 実ファイルの走査：`import.meta.url` を基準に `src/` を探し、`layers.test.ts` 自身は走査から外す（テストデータに違反の文字列を持つため）

### パッケージの入口（D2）と依存の追加（D7）

- `packages/domain/package.json`：`main`・`types` と、`exports` の個別の行を消し、`"exports": { "./*": "./src/*.ts" }` にする。devDependencies に `@types/node` を足す。`pnpm-lock.yaml` も一緒にコミットする（CI は `--frozen-lockfile`）
- 利用側の import を書き換える：`apps/web`（`@cartagraph/domain` からの import 28ファイル）、`scripts/simulate-auto-combat.ts`（相対パス）。書き換えは、名前→移す先の対応表を持つ一回限りのスクリプト（スクラッチパッド、コミットしない）で行い、型名ごとに正しいファイルから import する

### コミットの分け方

`git` は rename を内容の類似度で推定するので、移動と中身の書き換えを分ける。

1. `layers.test.ts`（Red）
2. **移動だけ**：`git mv` で丸ごと移せるファイルを移す（autoCombat.ts → autoCombat/resolve.ts、sceneTransition.ts → session/transition.ts、soloVillage.ts → soloVillage/rules.ts、scenarioRefs.ts → scenario/refs.ts、scenarioFile.ts → scenario/file.ts、各テスト）。中身は変えない（このコミットでは型検査が落ちてよい。pre-push は HEAD だけを検査する）
3. **中身の書き換え**：`index.ts`・`scenarioSchema.ts` を各 `model.ts` へ分解して削除、`card/condition.ts`、import の書き換え、`package.json`
4. ドキュメント

分解して消える `index.ts`・`scenarioSchema.ts` の履歴は、`git log --follow` や `git blame -C -C` で追う。

## 4. テスト影響範囲

- `packages/domain` の既存テスト6ファイル（autoCombat・sceneTransition・soloVillage・scenarioSchema・scenarioRefs・scenarioFile）：移動と import の書き換えのみ。いまの `it` の数は autoCombat 53・sceneTransition 17・soloVillage 30・scenarioSchema 9・scenarioRefs 12・scenarioFile 5（実装レビューの指摘で訂正）
- `apps/web` のテスト：import の書き換えのみ
- **振る舞いを変えていないことの確かめ方**：実装を始める前に `vitest run --reporter=json` で domain と web のテスト名（describe と it をつないだ名前）の一覧を記録し、移した後の一覧（`layers.test.ts` を除く）と並べ替えて突き合わせる。件数だけでなく名前で一致すること
- `scripts/simulate-auto-combat.ts`：どの tsconfig にも入らず、tsx は型を見ないので、一度だけ `tsc --noEmit` を scripts に向けて型の import の取り違えを確かめる。回して、表が生成日以外変わらないことを確かめ、生成日だけの差分は戻す
- exports のワイルドカードで `@cartagraph/domain/scenario/model` のような2段のパスが解決できることは、`web:typecheck`（TS の bundler 解決）・`web:test`（Vite）・CI の `build:pages` と E2E で担保する

## 5. 新規テストケース

### `layerViolations`（判定関数）

違反の報告は、ファイル・import 先・理由を含む文字列の配列を `toEqual` で固定する。

- 境界の両側
  - 許す：同じディレクトリ（`./model`）、隣の下（`session/` → `../scenario/model`）、層を飛ばした下（`soloVillage/` → `../check/model`）、`library/` → `../card/model`
  - 違反：隣の上（`session/` → `../soloVillage/rules`）、`card/` → `../library/model`、`check/` → `../user/model`、`user/` → `../card/model`、`library/` → `../user/model`
- 書き方のゆれ（すべて違反として拾う）：`import type { X } from`、`import { type X } from`、複数行の import、`export { x } from`・`export * from`・`export type { X } from`、`import '…'`、`import('…')`、`typeof import('…')`、拡張子付き（`'../scenario/model.ts'`）、ディレクトリだけ（`'../scenario'`）、二重引用符
- パス：`./../scenario/model`、`../card/../scenario/model` は違反。`src/` の外（`../../../apps/web/x`）は違反。`@cartagraph/domain/scenario/model` は違反。`zod`・`node:fs` は違反にしない
- ファイルの置き場所：表に無いディレクトリ（`misc/x.ts`）は違反、直下の `x.ts` は違反、`card/index.ts` は違反
- 誤りが複数あれば、すべて報告する

### 実ファイルの検査

- `src/` 配下の全ファイルの違反が `toEqual([])`
- 前置きの確認（何も読めていないのに通ることを防ぐ）：走査したファイルに `card/condition.ts`・`session/transition.ts`・`scenario/model.ts` が含まれる。見つけた相対 import が0件でない。`soloVillage/rules.ts` が `../card/condition` を import していると判定できている
- 骨抜きの確認（実装順4）：移した後に、実在のファイル（`card/model.ts`）へ `import type {} from '../scenario/model';` を一時的に入れ、`git diff` で入ったことを確かめてから、このテストが落ちることを見て戻す

### 振る舞いを変えていないこと（既存テストで担保）

- 4. の「テスト名の一覧の突き合わせ」、型検査、シミュレーション
