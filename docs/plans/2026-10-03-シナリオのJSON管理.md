# シナリオを JSON でリポジトリ管理する

要望：[シナリオを JSON でリポジトリ管理する](../backlog/scenario-json.md)

## 1. 概要

遊べる4本のシナリオ（「村はずれの一歩」「灰色館の一夜」「鉄鎖のガレオン船」「灯りの回廊・後日談」）を、`apps/web/src/mocks/fixtures.ts` のコードから、リポジトリ直下の `scenarios/<id>.json` へ移す。MSW は起動時に JSON を読み込み、`packages/domain` の zod スキーマと参照の整合の検査を通してから、これまでどおり `/api/scenarios` で返す。シナリオの型は zod スキーマを正にする。

## 2. 背景

- [ロードマップ](../roadmap.md) M1 の完成の条件2（シナリオを JSON でリポジトリ（`scenarios/`）で管理し、MSW 経由で取得する）と5（GM 不在のシナリオ（村はずれの一歩）も、シナリオの JSON から結末まで遊べる）
- 次の要望 [シナリオ製作者がシナリオを作って公開する](../backlog/scenario-publish.md) の前提。公開すると `scenarios/<id>.json` に書き込むので、書き込む前に同じ検査をかけられるよう、検査（形・参照の整合・ファイル名との一致）は `packages/domain` の純粋関数に置く
- 置き場所をリポジトリ直下にするのは、将来バックエンド（[技術スタック](../architecture/index.md)）ができたときに、同じ JSON を投入データとして使うため（要望ファイル）
- 関わる仕様：[シナリオの構造とセッション開始までの流れ](../cartagraph/scenario-flow.md)、[GM不在のソロ（村パート）](../cartagraph/solo-village.md)、[自動戦闘](../cartagraph/auto-combat.md)。シナリオの中身・ルールは変えない（今回はデータの置き場所と検査だけ）。未解決論点に関わる判断は無い
- 関わるルール：[アーキテクチャルール](../process/rules/architecture.md)「構造」と[テストルール](../process/rules/testing.md)「シードデータ（MSW）」の「`mocks/fixtures.ts`（モックデータ＝唯一のシード／1箇所に集約）」は、ロードマップの「`scenarios/` で管理」と食い違う。**ルールの方を書き換えることを人間が承認済み（2026-10-03）**

### その他の設計判断（AI が決めたもの）

- **ファイル名は `scenarios/<シナリオid>.json`**、1ファイル1シナリオ。ファイル名と `id` が食い違ったら読み込みで失敗させる
- **スキーマは厳格（`z.strictObject`）にする。** 知らないキー（`nextNodeID` のような書き間違い）を黙って捨てると、JSON を手で直したときに気づけないため。入れ子・再帰の中でも厳格にする
- **省略可能な項目に `null` は書けない**（キーごと省く）。`spaceModel` のように型で `null` を許すものだけ `null` を書ける
- **`updatedAt` は固定の日時（ISO 8601 の日時。`z.iso.datetime()` で検査）を書く。** いまは「今」からの相対（`ago()`）で作っているが、JSON には書けない。画面の相対表示（「3日前」など）は時間とともに増えていく。値は現在の相対値に近い日付（2026-10-03 から数えて同じ日数前）にする
- **村はずれの一歩の `libraryStatus` は今の値（`draft`）のまま、`authorId` も `system` のまま移す。** 振る舞いを変えないため（共有ライブラリの一覧に出ない現状を保つ）。`scenarios/` に `draft` が混ざることは、公開の要望（scenario-publish）へ申し送る（「公開＝JSON に書き込む」との関係はそこで決める）
- **一覧の並び順** — 読み込んだ JSON を id 順に並べ替え（glob の返す順に頼らない）→ 下書き → テスト専用 の順にする。いまの並びから変わるが、並び順は仕様ではない。調査では並び順に頼ったテストは無い
- **JSON の整形の正は Biome**（`biome.json` の対象に `scenarios/` も入っている）。書き出したら `pnpm exec biome format --write scenarios/` をかける
- **zod は本番のバンドルにも入る**（GitHub Pages でも MSW を起動し、起動時に検査するため）。今の規模なら問題ないので `manualChunks` は変えない
- **開発サーバーの起動中に `scenarios/` へファイルを足しても拾われないことがある**（Vite の監視はプロジェクトのルート配下）。既存ファイルの編集は反映される。web-app.md に書く

### (a) zod スキーマと検査関数（`packages/domain`）— コミット1

- `pnpm --filter @cartagraph/domain add zod@^4` で `dependencies` に追加し、`pnpm-lock.yaml` も一緒にコミットする（CI は `--frozen-lockfile`）
- `packages/domain/package.json` の `exports` に `"./scenarioSchema"`・`"./scenarioRefs"`・`"./scenarioFile"` を足す
- 新規 `packages/domain/src/scenarioSchema.ts`：Scenario とそれが含む型のスキーマを置く。zod 以外に依存しない（`index.ts` を import しない）
  - 列挙：`cardKindSchema`・`deckNodeKindSchema`・`hpConditionSchema`・`spaceModelSchema`・`proposalHandlingSchema`・能力値のキー（`abilityKeySchema`）
  - オブジェクト：`checkSpecSchema`・`diceExprSchema`・`combatEffectSchema`・`cardConditionSchema`・`soloEffectSchema`・`cardDefSchema`・`priorityEntrySchema`・`autoCombatEnemySchema`・`deckNodeSchema`・`endingDefSchema`・`scenarioSchema`
  - 再帰する辺は3つ：`CardDef.soloEffect.gainCards: CardDef[]`、`CardDef.soloEffect.achievement: CardDef`、`DeckNode.children: DeckNode[]`。zod v4 の getter で書き、型検査が通らなければ getter の戻り値に zod の型注釈を付ける
  - `$comment`（D8）：`scenarioSchema`・`deckNodeSchema`・`cardDefSchema`・`autoCombatEnemySchema` に `'$comment': z.string().optional()`
  - 各フィールドの説明（いまの JSDoc。仮ルールの注記を含む）は、shape のキーの上に JSDoc で書く（`.describe()` は TS のホバーに出ないため使わない）。`z.infer` を通してもホバーで出ることを確かめる
- `packages/domain/src/index.ts`：上の型（`CardKind`・`CheckSpec`・`CardDef`・`CardCondition`・`SoloEffect`・`DiceExpr`・`CombatEffect`・`HpCondition`・`PriorityEntry`・`AutoCombatEnemy`・`DeckNodeKind`・`DeckNode`・`EndingDef`・`SpaceModel`・`ProposalHandling`・`Scenario`）を `export type X = z.infer<typeof xSchema>` の型エイリアスに置き換える（`import type` で読み、循環させない）。型名と import 先は変えないので、利用側の import は直さない。型そのものに付いた説明（`ProposalHandling` の「'auto-resolve' は意図的な逸脱」、`HpCondition` など）は型エイリアスの JSDoc に残す。`Abilities` は Character でも使うので interface のまま残し、能力値のキーの列挙と型テストで両方向の一致を確かめる。ラベル（`CARD_KIND_LABEL` など）は `index.ts` に残す
- 新規 `packages/domain/src/scenarioRefs.ts`：`findScenarioRefErrors(scenario: Scenario): string[]`（空配列なら整合）。純粋関数
  - ノードを集める範囲は `children` まで含める（`findDeckNode` と同じ）
  - 検査するカードは「ノード（`children` を含む）直下の `cards`」。`soloEffect.gainCards`・`soloEffect.achievement`・自動戦闘の敵のカード・`priority[].card` は、id の重複の検査にも `nextNodeId` の検査にも含めない（キャラクターのカードと同じ id を使うため。遷移はノード直下の選択肢カードで起きる）
  - 検査項目：`nextNodeId` が実在のノードを指す／`endingId` が `endings` にある／ノード id の重複なし／カード id の重複なし（同じノード内・別ノード間）／`endings` の id の重複なし。誤りは全部報告し、それぞれに関係する id を含める
- 新規 `packages/domain/src/scenarioFile.ts`：`parseScenarioFile(path: string, raw: unknown): Scenario`。`scenarioSchema` で検査し、ファイル名（パスの最後の部分から `.json` を除いたもの）と `id` の一致、`findScenarioRefErrors` を確かめる。失敗したらファイルのパスと誤りの内容（zod の誤りは `z.prettifyError` で整形）を含めて例外を投げる。apps/web とシミュレーションのスクリプトの両方がこれを呼ぶ（apps/web から zod を直接 import しない）

### (b) データの移行（`apps/web`・`scenarios/`）— コミット2

- 新規 `scenarios/` に4ファイル。作り方は、いまの `fixtures.ts` の `scenarios` から該当4本を `JSON.stringify` で書き出す一回限りのスクリプト（スクラッチパッドに置き、コミットしない）。`updatedAt` だけ固定値に直し、`$comment` を手で足し（D8）、Biome で整形する。整形後のファイルを parse した値と、書き出し前のシナリオが一致すること（`updatedAt`・`$comment` 以外）をスクリプトで確かめる
- `$comment` に移す注記（fixtures のコメントから）：
  - シナリオ：`spaceModel: null`（自動戦闘は空間モデルを使わない）、`proposalHandling: 'auto-resolve'`（GMレス・ソロ用）
  - 引換カード：character-growth.md の報酬カードとは別物
  - 「街の冒険者ギルドへ向かう」：`playWhen: { hasTags: ['攻撃'] }` の理由（街道から村へは戻れず、攻撃の手段が無いと試験に勝てない）

  - 試験官：優先順位は条件を付けず、すべて「いつでも」。数値は自動戦闘エンジンのプランのシミュレーションで選んだ目安

  - `sc-village-always-win` は D4 の方法で作る
  - セッション `ss-village-human-gm` の `nodeId: 'vw-quest-0'` と `villageCards('sc-village-always-win', ['vw-quest-0-body', 'vw-learn-c-slash', 'vw-to-shop'])` を `vs-` に直す（直さないと `villageCards` が読み込み時に例外を投げる）

- `scripts/simulate-auto-combat.ts`：`import.meta.glob` は tsx で動かないので、`fixtures` から読むのをやめ、`scenarios/sc-village-start.json` を `node:fs` で読んで `parseScenarioFile` にかける。冒頭コメントの `fixtures.ts` への言及も直す

## 5. 新規テストケース

既存の実装で最初から通る回帰テストは、守る条件を一時的に外して（JSON の値を1つ変えるなど）落ちることを確かめる。件数・中身を見るテストは `toContain` ではなく配列全体の `toEqual` で固定する。

### `packages/domain/src/scenarioSchema.test.ts`

- 正常系：必須項目だけの最小のシナリオが通る
- 正常系：任意項目をすべて持つシナリオ（`soloStarter`・`soloGrowth`・`autoCombat`・`dealWhen`/`playWhen`/`soloEffect`（`gainCards`・`achievement`）・`children`・`$comment`）が通り、`parse` の結果が入力と `toEqual`（項目を落とさない・足さない）
- 異常系：`kind` が列挙に無い値（カード・ノードそれぞれ）だと失敗する
- 異常系：必須項目（`id`・`deck`・`endings` など）が無いと失敗する
- 異常系：知らないキーがあると失敗する。シナリオ・ノード・カード・`autoCombat.enemy`・`priority[].card`・`soloEffect`・再帰の中（`gainCards[]` のカード、`achievement`、`children[]` のノード）のそれぞれで
- 異常系：入れ子の中の誤り（`soloEffect.gainCards` の中のカードの `kind`、`soloEffect.achievement` の `kind`、`children` の中のノード、`autoCombat.enemy.priority[].when`）も失敗する（再帰が効いている）
- 境界：`spaceModel: null` は通り、`spaceModel` のキーが無いと失敗する。省略可能な項目（`description` など）はキーが無ければ通り、`null` なら失敗する
