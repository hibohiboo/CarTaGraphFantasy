# API ドキュメント（応答のスキーマと OpenAPI・Redoc）

要望：[API ドキュメントを、応答のスキーマから作って公開する](../backlog/api-docs.md)（[ロードマップ](../roadmap.md#backend-1on1) backend-1on1 の下ごしらえ）

状態：完了（PR #23）。D1〜D6 は2026-10-11に人間と確かめた。プランの AI レビュー（設計整合性・運用・テスト網羅）の P0・P1 を反映した

## 1. 概要

API の一覧（メソッド・パス・リクエストの本文・クエリ・応答の状態コードごとの形）を `packages/schemas` に zod で置き、そこから OpenAPI 3.1 の文書を作って、Redoc の HTML 1枚で GitHub Pages（`/api-docs/`）に公開する。サイドバーの「開発」の、テストレポートの次から開く。一覧と MSW のハンドラが1対1か、MSW が実際に返した応答が一覧のとおりかを、Vitest で止める。文書の生成と `redocly lint` は CI と pre-push でも流す。

## 2. 背景

- 人間の要望（2026-10-11）：テストレポートの次に API ドキュメントが欲しい。MSW から OpenAPI を出して Redoc で公開する仕組みはないか
- MSW のハンドラ（`apps/web/src/mocks/handlers.ts`、30本）が持つのはメソッドとパスだけで、本文と応答の形はハンドラの中のコードにしか無い。MSW から OpenAPI を直接は作れないので、形の出どころを zod にする
- [API のリクエストのスキーマの共用](2026-10-10-APIスキーマの共用.md)（PR #22）で、リクエストの本文（16本）は `packages/schemas` の zod になった。応答のスキーマは「バックエンドに着手するときに別の要望で足す」とした（同プラン D2）。この要望がそれに当たる
- 応答の形の多くは、`packages/domain` の `interface`（`Session`・`SessionStatus`・`Recruitment`・`Participant`・`Proposal`・`FeedItem`・`Character`・`Abilities`・`LibraryEntry`・`CurrentUser`・`CombatLogEntry`・`CombatRecord`・`AutoCombatState`）。`Scenario`・`CardDef` などシナリオの JSON に書くものは、すでに zod が正で型は `z.infer`（`card/model.ts` の冒頭の方針）。`extends`・宣言の併合・`Readonly<>`・型の付け替え・関数の項目は無い（プランレビューで grep した）。`exactOptionalPropertyTypes` は無効
- domain に無い応答の型が `apps/web` に2つある：`ScenarioSaveResult`・`ScenarioFileResult`（`entities/scenario/api/types.ts`。MSW もこの型で応答する）と、`/card-pool` の応答（`entities/user/api/queries.ts` の `api.get<{…}>` に直書き）
- 失敗の応答はどれも `{ message: string }`。状態コードは 200・201・403・404・409・422・500（500 は開発サーバーでシナリオのファイルに書けなかったときだけ）。204 と `HttpResponse.error()` は使っていない
- 下書きのシナリオ（`libraryStatus: 'draft'`）の保存（`PATCH /scenarios/:id`）は、書きかけでも保存できるよう中身を検査しない（前回のプランの D5）。そのため下書きは `scenarioSchema` の業務の検査（`endingDefSchema` の superRefine：再挑戦不可の結末には結末タグが要る）に通らないことがある
- 既存の web のテスト（21ファイル・509件）を応答の記録つきで流した実測（プランレビュー）：30本の API はどれも1回以上呼ばれる。API × 状態コードの組は約80で、うち11組は一度も返らない（`GET /characters/:id`・`GET /sessions/:id`・`GET /scenarios/:id`・`PATCH /characters/:id`・`POST /sessions/:id/proposals`・`…/approve`・`…/reject`・`/mode`・`/end`・`POST /scenarios/:id/recruitments` の 404、`POST /recruitments/:id/apply` の 409）。jsdom の origin は `http://localhost:3000`。クエリ付きの URL は `/api/scenarios?mine=1` だけ
- 正式仕様（`docs/cartagraph/`）は API の形を決めていない。API とモックの仕組みの正は `docs/architecture/web-app.md`。ゲームの用語・振る舞いは変えない

## 3. 詳細設計

### 決定事項（人間が決定。2026-10-11）

- **D1 出どころ** — MSW ではなく `packages/schemas` の zod から OpenAPI を作る。公開は Redoc。サイドバーの「開発」の、テストレポートの次
- **D2 応答の形は domain の interface を zod に変える** — 上に挙げた domain の `interface` を zod のスキーマにし、型は `z.infer` で導く（`Scenario` と同じやり方）。使う側の型の名前は変わらない。`packages/schemas` に同じ形を書き写さない
- **D3 MSW の応答を検査する** — web の Vitest の中で、MSW が返した状態コードと本文を一覧と突き合わせ、ずれたらそのテストを落とす
- **D4 失敗の応答** — API ごとに返しうる状態コードを一覧に書く。本文は共通の `{ message }`。一覧に無い状態コードが返ったら、D3 の検査で落とす
- **D5 Redoc の HTML** — `@redocly/cli` の `build-docs` で作る。できる HTML は Redoc の本体を `cdn.redocly.com` から読む（同梱できない）ことを受け入れる。Google Fonts は読まない（`--disableGoogleFont`）。テレメトリと更新の確認は環境変数で止める
- **D6 下書きは仮の形で書き、分離は次のサイクル** — 人間の案：下書きの保存用の API を分ける（`/scenarios/:id/draft` で書きかけを読み書きし、公開で検査済みの `Scenario` にする）。編集の流れと画面が変わるので、別の要望（[シナリオの下書きの API を分ける](../backlog/scenario-draft-api.md)）にして次のサイクルで行う。今回は、下書きを返しうる API の応答を「業務の検査を外した形」（G10）で書き、説明に「下書きは業務の検査を通っていないことがある。下書きの API を分けたら直す」と書く
- **D7 形の崩れた下書きの保存は、説明に書いて次のサイクルで直す**（実装の AI レビュー（異常系）を受けて人間が決めた）— 下書きの保存は本文の形も検査しないので、知らないキー・型違いの本文でも 200 で保存し、一覧と違う形を返す。振る舞いは変えず、`PATCH /scenarios/:id` の説明と既知の問題に書き、下書きの API を分けるときに直す
- **D8 仕様とずれたモックの振る舞いは、説明に「仕様とずれている」と書く**（実装の AI レビュー（仕様整合）を受けて人間が決めた）— `Session` の無反応の中断（`suspendAt`・`inactivity`）と、再開の権限（モックはドライバーだけ）。振る舞いは変えず、型と API の説明に、仕様とのずれと直す要望（`docs/backlog/gm-resume-suspended.md`）を書く

### AI が決めた設計（プランの AI レビューを反映）

- **G1 domain の zod 化** — D2 の型を `z.strictObject` で書き、`export type X = z.infer<typeof xSchema>`。入れ子のオブジェクト（`partySize`・`hp`・`cp`・`currentScene`・`field`・`applicants`・`lastResult` など）も `z.strictObject`。方針は `card/model.ts` の冒頭（知らないキーを捨てない・省略可能な項目は `.optional()` で `null` を書かない）に合わせ、今 `null` を持つ項目（`Recruitment.spaceModel` など）は `.nullable()`。リテラルの和（`ParticipantRole`・`ProposalStatus`・`AutoCombatOutcome`・`UserRole`・`Recruitment.status`・`Session.status`・`suspendedFor`・`AutoCombatState.status`・`CombatLogEntry.actor` など）は `z.enum` にし、型は `z.infer`。`SessionStatus` は `sessionStatusSchema`（`z.enum`）に変え、`Session.status` はそれを使う。ラベルの表（`PARTICIPANT_ROLE_LABEL` など）はそのまま。項目の JSDoc はスキーマの側に移す。置き場所は今の `model.ts`（ディレクトリの依存の向きは変わらない）。`card/model.ts` の冒頭のコメント（zod が正なのはシナリオの JSON に書くもの）を「API の応答の型も」に直す
  - **型の意味が変わらないことの確かめ**：書き換えの間だけ、`git show main:<パス>` で取った元の interface を一時ファイルに置き、`expectTypeOf<z.infer<typeof xSchema>>().toEqualTypeOf<旧X>()` を全型で通してから消す（コミットに残さない）。結果をこのプランに記録する
  - **結果（2026-10-11）**：16の型（`Abilities`・`UserRole`・`CurrentUser`・`LibraryEntry`・`Character`・`CombatLogEntry`・`AutoCombatOutcome`・`CombatRecord`・`AutoCombatState`・`Recruitment`・`ParticipantRole`・`Participant`・`ProposalStatus`・`Proposal`・`FeedItem`・`Session`）がすべて等しかった。確かめが効くことも、`Recruitment.status` を `z.string()` に、`AutoCombatState.enemyCardId` を `.nullish()` に変えて型検査が落ちることで確かめた。`SessionStatus` は `sessionStatusSchema` に置き換えた（使う所は無かった）
- **G2 一覧の置き場所** — `packages/schemas/src/` に次を足す（URL の最初の区切りごとのディレクトリという今の決まりのまま。ディレクトリの名前は区切りと同じ）
  - `endpoint/define.ts` … `defineEndpoint({ method, path, summary, description?, body?, query?, responses })`。`path` は `/sessions/:id/play` の形（MSW と同じ書き方。`/api` は付けない）。`body` は `defineBody` の戻り値（リクエストの本文の検査と同じものを使う）。`responses` は「3桁の状態コード → `{ description, schema }`」で、空にできない（型で止める）。失敗の本文 `errorBodySchema`（`z.strictObject({ message: z.string() })`）もここ
  - `endpoint/check.ts` … 純粋な関数 `checkResponse(endpoint, status, body)`：状態コードが `responses` に無い、本文がスキーマに通らない、のどちらかなら、メソッド・パス・状態コード・zod の誤りの場所を入れた文の配列を返す（G7 が使う。将来のバックエンドの契約テストにも使える。`apps/web` は zod を直接使わないので、誤りの整形もここで行う）
  - 各ディレクトリの `endpoints.ts` … そのディレクトリの API の一覧（配列）。今ある `characters/`・`recruitments/`・`sessions/`・`scenarios/` に加え、`me/`・`library/`・`card-pool/` を作る
  - 各ディレクトリの `response.ts` … domain に無い応答の形だけ。`scenarios/response.ts` に `scenarioSaveResultSchema`（`ScenarioSaveResult`・`ScenarioFileResult` を `apps/web` から移す）と G10 の下書きの形、`card-pool/response.ts` に `/card-pool` の応答
  - `api/endpoints.ts` … 全ディレクトリの一覧を1本にまとめる。`api/openapi.ts` … そこから OpenAPI の文書（オブジェクト）を作る純粋な関数（G3）
  - 依存の向き：`api/` → 各ディレクトリ・`endpoint/`・`body/`、各ディレクトリ → `endpoint/`・`body/`、`endpoint/` → `body/`、`body/` はどこにも依存しない（許可する先は推移的なものも列挙する。domain と同じ）。Biome の `packages/schemas/src/**` の override（否定のパターンで許可）と、`architecture.md`「packages/schemas の中の置き場所」を一緒に直す。新しいディレクトリを override の `includes` に書き漏らしても、全体の override が `../**` を禁止しているので lint で止まる
- **G3 OpenAPI の組み立て（zod 4 の組み込みで作る）** — zod 4.6.5 の `z.toJSONSchema` を使う（OpenAPI 3.1 は JSON Schema 2020-12。プランレビューでスクラッチで確かめた）。次の決まりで作る
  - 名前の付いた型（`Session`・`Character`・`Recruitment`・`Scenario`・`CardDef`・`DeckNode` など）は、`packages/schemas` の側の `z.registry` に id を付けて登録する（domain に OpenAPI の id を書かない）。**循環するスキーマ（`CardDef`・`DeckNode` の getter）は必ず登録する**（登録しないと `__shared`・`__schema0` という壊れた参照になる）
  - リクエストの本文は `io: 'input'`（受け取る側は知らないキーを捨てるので `additionalProperties: false` を付けない）、応答は `io: 'output'` で変換する
  - 変換の結果の `$schema`・断片だけの `$id` を取り除き、`$defs` の参照を `#/components/schemas/<id>` に書き換え、同じ id の定義は1回だけ `components.schemas` に出す
  - パスは `/sessions/{id}/play` に直し、パスの引数を `parameters`（path・必須）に出す。`operationId` はメソッドとパスから作る。タグは最初の区切りで、タグごとに説明を書く。`servers` は `/api` で、説明に「モック（MSW）。バックエンドは未実装」と書く。`info` にライセンスは書かない（lint の設定で止める。G4）
  - 仮ルールの型（`AutoCombatState`・`CombatRecord`・`/card-pool` の `abilities`・`initialHp`・`initialBaseActionValue`）は、型ごとの `description` に「仮ルール」と、どの仮ルールのページかを書く（architecture.md「境界」の「仮」の明示。項目ごとの説明は G9 でスコープ外）
  - ライブラリ（`zod-openapi`・`@asteasolutions/zod-to-openapi`）は使わない（組み込みで作れることをプランレビューで確かめた）。作れないと分かったら止めて報告する
- **G4 HTML を作るコマンド** — `scripts/build-api-docs.ts`（`tsx` で流す。`simulate-auto-combat.ts` と同じく型検査の対象外なので薄く保つ。中身は `api/openapi.ts`）が、文書を作って `docs/.vitepress/dist/api-docs/openapi.json` に書き（無ければディレクトリを作る）、`@redocly/cli` の `lint` と `build-docs --disableGoogleFont`（`index.html` 1枚）を流す
  - 呼び方：`spawnSync(process.execPath, [require.resolve('@redocly/cli/bin/cli.js'), …])`（Windows で `.cmd` のシムを shell 無しで起動できないため）。環境に `REDOCLY_TELEMETRY=off`・`REDOCLY_SUPPRESS_UPDATE_NOTICE=true` を付ける。引数のパスは `/` で始めない（Git Bash の書き換え）
  - `redocly.yaml`（ルート）：`recommended-strict`（警告も誤りにする）を基に、使わないものだけ止める（`security-defined`（認証はまだ無い）・`info-license`・`operation-4xx-response`（`GET /me` などは失敗を返さない））。止めた理由は `docs/architecture/web-app.md` に書く。誤りが1件でもあれば `api:docs` は失敗する
  - `@redocly/cli` はルートの devDependencies（依存を同梱しており、install script は無い。`pnpm-lock.yaml` を同じコミットに入れる）
  - ルートの `package.json` に `api:docs`。`build:pages` の最後に足す（dist は `docs:build` が作り直すので、その後に流す）。**`ci.yml` の `docs:build` の後と、`.githooks/pre-push` の最後にも足す**（壊れた文書が main に入ってデプロイだけが落ちるのを防ぐ）。`openapi.json` もそのまま公開する
- **G5 サイドバーと手元での見方** — 「開発」のテストレポートの次に `{ text: 'API ドキュメント', link: '/api-docs/', target: '_self' }`（`/app/` と同じく base が付く。`pnpm docs:dev` では 404 になるのも同じ）。手元で見るときは `pnpm docs:build && pnpm api:docs && pnpm docs:preview --port 4175 --strictPort`（4173 は E2E、4174 はエージェントの preview が使う。`pnpm web:dev:agent:stop` では止まらないので、起動したターミナル・タスクを止める）を `docs/architecture/web-app.md` に書く。markdown から `/api-docs/` へリンクするときは絶対の URL で書く（VitePress のリンク切れ検査）
- **G6 一覧と MSW のハンドラの1対1** — `apps/web/src/test/apiEndpoints.test.ts`：`handlers` の各ハンドラの `info.method`・`info.path`（`/api` を外す）の組と、一覧の組が、重複なく同じ集合になる。`info.path` が文字列でないハンドラは誤りにする。比べるときはパスの引数の名前を正規化する（`:id` と `:sid` は同じルート）
- **G7 応答の検査（D3・D4）** — `apps/web/src/test/responseCheck.ts` に、照合と貯めることだけを置く（検査そのものは G2 の `checkResponse`）
  - `server.events.on('request:start', …)` で `requestId` とその時点のテスト名（`expect.getState().currentTestName`）を対応づけ、`server.events.on('response:mocked', …)` で、リクエストのメソッドと URL に当たる一覧の項目を MSW の `matchRequestUrl`（基準は `location.origin`）で探し、本文を読んで `checkResponse` に渡す（MSW 2.15 は応答を複製して渡すので `clone()` は要らない）。項目が見つからない・本文が JSON でない・読む途中や検査の中で例外が出た、も誤りとして貯める（未処理の reject にしない）。誤りの文にはリクエストを出したテストの名前を付ける
  - `setup.ts` の既存の `afterEach` の中で、処理中の検査を待ってから、後片付け（`cleanup`・`resetHandlers`・`resetDb` など）を `finally` で必ず行い、そのあとで貯まった誤りを取り出して空にし、あれば投げる（後片付けが飛んで次のテストが連鎖して落ちるのを防ぐ）。`afterAll` でも残りを確かめて投げる（ファイルの最後のテストの後に届いた応答を黙って捨てない）
  - 誤りを取り出して空にする口 `takeResponseErrors()` を置く（T7 が自分で起こした誤りを取り出すため）
  - テストの中で `server.use` で差し替えた応答も同じく検査する（差し替えも一覧どおりであるべき）
  - 既存のツールで代わりにならないか（プランレビューで確かめた）：MSW・Vitest・Biome に応答を契約と照らす機能は無い。生成した OpenAPI を ajv で検査する案は、zod と二重の正になるので採らない。`HttpResponse.json<T>` の型引数は実行時の余分なキーと状態コードを止められない。1対1（G6）をなくすには一覧からハンドラを作る必要があり、スコープ外
- **G8 画面の型** — `entities/*/api` の `api.get<T>` の `T` は、domain の型（D2 で `z.infer` になったもの）と、schemas の応答の型を使う。`entities/scenario/api/types.ts` は残し、中身を schemas の型の別名にする（`import type { ScenarioSaveResult as R } from '@cartagraph/schemas/scenarios/response'; export type ScenarioSaveResult = R;`。再エクスポート（barrel）ではない）。pages は schemas を import できないので、pages・テスト・`ScenarioFileNote.tsx` の import はそのまま。`/card-pool` の応答の型も同じく entities の別名にする。画面で応答を実行時に検査はしない
- **G9 一覧に書く文** — `summary` は画面の操作の言葉で短く（例：「カードをプレイする」）。状態コードごとの意味（例：422「戦闘中・終了済み・本文の形の誤り」）を `responses` の `description` に書く。項目ごとの説明（JSDoc を OpenAPI の `description` に出すこと）はスコープ外
- **G10 下書きを返しうる API の応答（D6）** — `scenarios/response.ts` に `scenarioDraftSchema`：`scenarioSchema` から業務の検査（superRefine）だけを外した形（domain の `endingDefSchema` を、形だけの `endingDefShapeSchema` と、それに superRefine を付けたものに分け、`scenarioSchema.extend({ endings: z.array(endingDefShapeSchema) })`。domain の振る舞いは変えない）。使うのは下書きを返しうる API：`GET /scenarios`（`mine=1` は下書きを含む）・`GET /scenarios/:id`・`POST /scenarios`・`PATCH /scenarios/:id` の `scenario`。公開・非公開（`publish`・`unpublish`）は公開のファイルの検査を通った後なので `Scenario`。G7 で下書きの形のずれ（形そのものが崩れた下書き）が見つかったら、止めて報告する
