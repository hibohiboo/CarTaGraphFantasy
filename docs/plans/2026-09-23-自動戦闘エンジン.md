# プラン：自動戦闘エンジン（村スタート冒険者キャンペーン C2）

書式は `docs/process/index.md` の「プランドキュメントの8項目」。親プラン [村スタート冒険者キャンペーン](2026-09-23-村スタート冒険者キャンペーン.md) の C2 の詳細設計を、`dev-process-foundation.md` の C4（E2E導入）と同じ扱いで個別プランに切り出したもの。全体構想・決定事項1〜13は親プランが正で、ここでは C2 固有の決定だけを書く。C2 の決定で親プランの記述を上書きした箇所は、親プラン側にも反映する（実装順タスク1）。

## 1. 概要

GMレスのソロセッションで、PLが事前に並べた**優先順位リスト**に従い、[戦闘ルール](../cartagraph/combat.md)のカウント制を**自動実行**して1対1の戦闘を決着させるエンジンを `packages/domain` に作る。あわせて、選択肢カードの効果として「次のシーンへ進む」を基本操作セットに正式追加し、検証用シナリオ `sc-village-start` を「導入→冒険者試験→エンディング」まで通して遊べるようにする。

## 2. 背景

### 経緯

親プランの C1（GMレス基盤）が 2026-09-23 に PR #5 でマージされた。C2 着手時の `grilling`（2026-09-23）で、親プラン「3. 詳細設計／自動戦闘エンジン」に積み残していた論点を人間が決めた。さらにプランのAIレビュー（設計整合・仕様整合・テスト網羅の3観点）で、決着済み仕様との矛盾（P0）を含む指摘を受け、人間の判断で決め直した。決定は本ページ末尾の「決定事項（C2）」。

### C2 着手時の調査で判明した前提

- **シーンを進める仕組みが存在しない。** `POST /api/sessions/:id/play` は、カードIDごとにハードコードした `playScript`（`apps/web/src/mocks/handlers.ts`）で卓上の描写を変えるだけで、`Scenario.deck` の導入→シーン→エンディングを辿る処理がない。親プランの C1 設計にある「冒険者試験シーンに入ったら〜、エンディングに入ったら `useEndSession`」は、遷移の仕組みがないため C1 では実装されていない
- **ソロ開始で作られるキャラクターは空。** `buildSoloCharacter` は `deck: []`・HPなし・行動値なしのキャラクターを作る。C2 の試験に必要な戦闘スキルカード・HP・行動値の入手元が要る
- **ダメージ・回復量を表すフィールドがない。** `CardDef` には `actionCost`・`range` しかない。`actionCost` は optional
- **状態タグは `CardDef.tags` で表現済み。** 既存のエネミー fixture が `tags: ['弱点未判明']` のように状態タグを `tags` に入れている。「戦闘不能」も同じく `tags` に足す
- **`packages/domain` の exports は `"."`（`index.ts`）だけ。** `architecture.md` は barrel export の新設を禁じているため、新しいファイルは `package.json` の exports にサブパスを足して直接 import する
- **`packages/domain` にはテストも型検査の実行口もない。** CI・pre-push の型検査は `web:typecheck` だけで、domain のテストファイルはどこからも型検査されない

**auto-combat.md に明記する combat.md との差分**（仕様整合レビュー P0・P1・P2 への回答）：

1. カード宣言のタイミング：逐次選択ではなく、事前の優先順位リストで自動選択する
2. モード：濃密モードにせず、軽量モードのまま行う（C2-4）
3. **使えるカード：残り行動値 ≥ コストのカードだけ**（C2-12）。したがって自動戦闘では行動値がマイナスにならず、**マイナスの持ち越しは発生しない**。「今すぐ強い一撃か、手数を稼ぐか」の駆け引きは、優先順位の並べ方（払えなくなったら軽い攻撃に落とす等）で表す
4. 使えるカードがなければ、そのラウンドの行動を終える（combat.md にない自動戦闘だけの規則）
5. ラウンド開始時に行動値が同じなら PL が先（combat.md のスタック規則はラウンド開始時の同値を決めない）
6. HP0：敵には「戦闘不能」状態タグを付ける（カードは場に残す）。**PLには付けない**。PLは敗れると即座に傷を癒して再挑戦するため、付与と同時に解除するのと等価であり、PLのキャラクターカードは場に出していない（C2-13）
7. ラウンド上限を超えたら PL の敗北と同じ扱い（C2-3）
8. 敗北時の「再挑戦の記憶」は、所有者＝ドライバーのソロなので、セッション終了を待たずキャラクターデッキへ即時反映する（party-and-session.md の例外）。何度負けても1枚（C2-8）
9. 補助・移動カード、射程、空間モデルは使わない

### 3-2. ドメイン型（`packages/domain/src/index.ts`、型変更あり）

/** 自動戦闘（docs/cartagraph/auto-combat.md、仮ルール）でカードが持つ効果 */

export interface CombatLogEntry {

  actor: 'pl' | 'enemy'; actorName: string;

}
/** 手番を終えた記録（使えるカードが無くラウンドの行動を終えた）も同じ配列に入れる場合は

### 3-3. 自動戦闘エンジン（`packages/domain/src/autoCombat.ts`、新規・純粋関数）

```ts
export interface Combatant { name: string; hp: number; maxHp: number; baseActionValue: number; priority: CardDef[] }
export type Rng = () => number; // [0, 1)
export function rollDice(d: DiceExpr, rng: Rng): { rolls: number[]; total: number }; // ダイス1個ごとに rng を1回呼ぶ
export function pickCard(self: { hp: number; maxHp: number; actionValue: number }, priority: CardDef[]): CardDef | null;
export function validatePriority(cards: CardDef[]): string | null; // エラーメッセージ or null
export function resolveAutoCombat(input: { pl: Combatant; enemy: Combatant; maxRounds: number; rng: Rng }):
  { outcome: 'win' | 'lose' | 'timeout'; rounds: number; log: CombatLogEntry[] };
```

`validatePriority` のエラー条件：0件／`combatEffect` を持たないカード／**`actionCost` が未設定または1未満**（コスト0だと同じカウントで行動し続け、1ラウンドが終わらない）／同じカードIDの重複。`resolveAutoCombat` は入口で両者の優先順位に `validatePriority` をかけ、敵の fixture の誤りも含めて不正なら例外を投げる（ハンドラは500相当ではなく、呼ぶ前に PL 側を検証して422を返す）。`baseActionValue` が1未満・`maxRounds` が1未満も例外。

アルゴリズム（`auto-combat.md` に同じ内容を書く）：

1. **ラウンド開始**：各自の現在行動値＝基本行動値（持ち越しは発生しない。3-1 差分3）。HPは試行ごとに双方とも最大値から始める（再挑戦時も敵は全快）
2. **カウント**：両者の現在行動値の最大値から始め、1まで1ずつ減らす。0になったらラウンド終了
3. **行動**：現在行動値＝カウントの者が行動する。同じ値が複数いればスタック解決（最後にその値になった者から）。ラウンド開始時に同値なら PL が先
4. **カード選択**：優先順位リストの先頭から、使えるカードのうち最初の1枚。**使える＝残り行動値 ≥ コスト、かつ（回復なら）自分のHPが最大未満**。1枚も使えなければ、そのラウンドの行動を終える（現在行動値を0にする）
5. **解決**：コスト分だけ現在行動値を減らす。攻撃はダイスの合計でダメージ（相手HPから減算、下限0）、回復はダイスの合計で回復（最大HPで頭打ち）。命中判定・回避はない
6. **決着判定**：行動のたびに判定し、相手HPが0になった時点で即座に終わる。1手ずつ逐次に解決し、自分へのダメージを与える効果がないため、**両者同時にHP0になることは構造上起きない**（親プランの境界ケース「同時HP0」への回答）
7. **ラウンド上限**：`maxRounds` ラウンドを終えても決着しなければ `timeout`

乱数は引数 `rng` で受け取る（Functional Core）。`Math.random` は MSW ハンドラ側（Imperative Shell）で渡す。

### 3-4. シーン遷移（`packages/domain/src/sceneTransition.ts`、新規・純粋関数）

設計整合レビューの指摘（遷移の可否・状態計算はハンドラではなく Functional Core に置く）を受けて、ドメインに切り出す。

```ts
export function findDeckNode(deck: DeckNode[], id: string): { node: DeckNode; topIndex: number; path: DeckNode[] } | null;
export function planTransition(scenario: Scenario, session: Session, nextNodeId: string):
  | { ok: false; error: string }
  | { ok: true; currentScene: Session['currentScene']; hand: CardDef[]; enterAutoCombat?: AutoCombatEnemy; ended: boolean };
```

- `currentScene`：`index` は遷移先の**トップレベルの祖先**の添字、`total` は `scenario.deck.length`（既存の `buildSoloSession` と同じ）、`path` は祖先から遷移先までの名前を「 › 」でつないだもの、`name` は遷移先の名前、`nodeId` は遷移先のID
- `hand`：遷移先ノードの選択肢カード。ただし `autoCombat` を持つノードでは空（勝利後に配る）
- `ended`：遷移先が `ending` かつ人間GMのいないセッション（`gmId === SYSTEM_GM_ID`。定数は domain へ移す）のとき true
- ハンドラ（Imperative Shell）は結果を適用するだけ：`currentScene`・手札の選択肢カードの差し替え、feed「〇〇へ進んだ」、`enterAutoCombat` ならエネミーカードをコピーして `field.plVisible` に出し `Session.autoCombat` を作る、そうでなければ `Session.autoCombat` を削除、`ended` なら `status: 'ended'` と feed に結末名

### 3-5. API（`apps/web/src/mocks/handlers.ts`）

- **`POST /sessions/:id/play`（既存の拡張）**
  - `autoCombat.status === 'awaiting-priority'` の間は 422（試験中はプレイ不可。C2-14）
  - 選択肢カードに `nextNodeId` があれば `planTransition` を呼んで適用する。`ok: false` なら 422 を返し、セッションは一切変更しない
  - `nextNodeId` を持たないカードは従来どおり `playScript` で処理する（既存の人間GMセッションに回帰なし）
- **`POST /sessions/:id/proposals`（既存の拡張）**：`awaiting-priority` の間は 422（C2-14）
- **`POST /sessions/:id/auto-combat`（新規）** 本文 `{ priority: string[] }`（ドライバーのキャラクターデッキのカードID）
  - 404：セッションがない
  - 422：自動戦闘ノードにいない／既に勝利済み／キャラクターに HP・行動値が無い／`priority` が `validatePriority` を通らない（0件・`combatEffect` なし・コスト不正・重複）／キャラクターのデッキにないIDを含む。**422 の場合、`attempts`・feed・デッキは変わらない**
  - 解決：`resolveAutoCombat` を `Math.random` で実行。`attempts` を1増やし、`lastResult` に保存。feed には試行ごとの要約1件（「〇〇と試験官の戦い：3ラウンドで勝利」など）だけを記録し、1手ごとの詳細は `lastResult.log` に置く（feed が数十件で埋まるのを避ける）
  - **勝利**：場のエネミーカード（`enemyCardId`）の `tags` に「戦闘不能」を追加（カードは場に残す）、`status: 'won'`、手札に試験ノードの選択肢カード（`nextNodeId` → エンディング）を配る
  - **敗北・時間切れ**：feed に敗北とナレーション（`auto-combat.md` の定型文）を記録し、キャラクターデッキに特徴カード「再挑戦の記憶」（仮）を追加（**同名の特徴カードを既に持っていれば追加しない**）して `awaiting-priority` のまま。PLには状態タグを付けない（3-1 差分6）
  - 戦闘中のHPはキャラクターの最大HPから始め、戦闘後もキャラクターの `hp` は変更しない（負傷の持ち越しはスコープ外）
- **`POST /scenarios/:id/start-solo`（既存の拡張）**：シナリオが `soloStarter` を持っていれば、`buildSoloCharacter` がその HP・行動値・カードをキャラクターに持たせる

  - エンディングノード（既存 `vs-end`）
- **数値（PL の HP・行動値、ダイス、試験官の HP・行動値・行動）は実装タスク3で決める**。エンジン完成後に、スクラッチパッドのスクリプトで「素直な優先順位（斬撃のみ／渾身の一撃→斬撃／応急手当→斬撃）」ごとに数千回試し、**決着ラウンドの中央値が3〜5、勝率がおおむね6〜8割**になる値を選び、結果をプランに追記する。PR のレビュー観点に「数値はプレイテスト前の目安」と書く。balance.md の「1攻撃で2〜3割」は、1ラウンドの行動回数との両立が未決（2.の未解決論点）のため、ラウンド数の目安を優先する

## 5. 新規テストケース

### ドメイン単体：`packages/domain/src/autoCombat.test.ts`（乱数は固定の列を返す `rng` を注入）

- `rollDice`：`rng` が常に0なら `count + bonus`、常に0.999なら `count × sides + bonus`（両端）／列 [0, 0.999] で 2d6+b が `rolls: [1, 6]`・合計 7+b（ダイスごとに rng を呼ぶ）／0.5 → 4（中間値）
- `pickCard`：
  - 先頭が使えればそれ
  - 残り行動値 = コストなら使える／コスト−1なら使えず次の候補（境界の両側）
  - HP最大のとき回復を飛ばして次の攻撃／HP最大−1なら回復を選ぶ（境界の両側）
  - 使えるものがなければ `null`／空リストで `null`
- `validatePriority`：0件はエラー／1件ちょうどで `null`／`combatEffect` のないカード・`actionCost` 未設定・0のカード・同じIDの重複はエラー
- `resolveAutoCombat` の入口：敵の優先順位にコスト0のカード、`baseActionValue` 0、`maxRounds` 0 を渡すと例外（ループしない）
- カウント制：行動値13・コスト5なら同ラウンドで8のときに再行動する／1ラウンドの行動列がログ全体で固定される（例：PL@12 → 敵@10 → PL@9 …）
- 払えないカード：残り行動値2で先頭がコスト5なら、次の候補（コスト2）を使う。候補が尽きたらそのラウンドの行動を終え、相手だけが行動する。**次のラウンドは基本行動値から始まる**（持ち越しなし）
- 同値：ラウンド開始時に同値ならPLが先／ラウンド途中で同値になったら、後からその値になった側が先（スタック）
- 決着：敵HPがちょうど0で `win`、1残れば継続／PLのHPが0で `lose`／決着した手の後はログが続かない
- 「同時HP0」（親プランの境界値に対応）：互いに一撃で倒せる状況でラウンド開始時に同値 → PLが先に動いて `win`、敵は行動しない
- ラウンド上限：`maxRounds` ちょうどのラウンドで決着すれば `win`、決着しなければ `timeout`（上限の両側）
- 回復はHP最大で頭打ち、ダメージはHP0で下限。回復してHP最大に戻ったら、同じラウンドの次の行動では攻撃を選ぶ
- 決定性：同じ `rng` 列なら同じ結果・同じログ

## 決定事項（C2、2026-09-23、grilling とプランレビュー後の人間の判断）

1. **自動戦闘の時間軸は `combat.md` のカウント制をそのまま自動実行する**（交互に1手ずつの簡易モデルにはしない）。`actionCost`・`baseActionValue` は combat.md と同じ意味で再利用する。違いは auto-combat.md の「combat.md との差分」に列挙する
2. **ダメージ量はダイスで決める**（combat.md の判定に合わせる）。乱数は引数で注入し、テストでは固定値を渡す
3. **ラウンド上限に達したら、PLの敗北と同じ扱い**。上限は20ラウンド
4. **自動戦闘は `dense` フラグを流用せず `DeckNode.autoCombat` を新設し、セッションの `mode` も軽量のまま**。カウント制は「濃密モード専用」と決着済みのため、combat.md・party-and-session.md・role-and-scenario.md・glossary に「自動戦闘（仮ルール）は例外」と相互リンクを足して整合させる（プランレビュー P0 を受けて人間が判断）
5. **「次のシーンへ進む」を基本操作セット（`play-and-field.md`）に8項目目として決着として追加する**。遷移は人間GMのセッションを含む全体で使えるが、**結末ノードへの遷移でセッションが自動終了するのは人間GMのいないセッションだけ**（プランレビュー P1 を受けて人間が判断。「終了はGMが宣言する」「人間の裁量を優先する」との整合）
6. **自動戦闘のルールは新ページ `docs/cartagraph/auto-combat.md` に仮ルールとして書く**。数値はプレイテスト前のため決着にしない
7. **C2 の自動戦闘で使える効果は攻撃・回復のみ**。補助・移動は優先順位リストに入れられない。**ラウンド開始時に行動値が同じならPLが先**
8. **「再挑戦の記憶」は何度負けても1枚**（同名の特徴カードを既に持っていれば追加しない）。親プランの「無条件で1枚追加」を上書きする（プランレビュー後に人間が判断）
9. **戦闘の経過は一括で解決し、試行ごとの要約を feed に、1手ずつの行動を `lastResult.log` に記録して一覧表示する**。1手ずつの再生演出は C4 以降
10. **ドメインの単体テストは `packages/domain` に Vitest を整えて置く**（`testing.md` の種別表どおり）。型検査とあわせて pre-push・CI から実行する
