# シナリオ製作の導線を分かりやすくする

要望：[シナリオ製作の導線を分かりやすくする](../backlog/creator-flow-clarity.md)（[ロードマップ](../roadmap.md#local-flow) local-flow の残り）

状態：プランの AI レビュー済み（2026-10-17。設計整合・仕様整合・テスト網羅。P0・P1 を反映した。結果は9章）。D1〜D11 は2026-10-17に人間と確かめた（質問4ラウンド）。H1〜H3 は2026-10-17に人間が案のとおり認めた。手順2「docs（G1）」は済み（2026-10-17。画面のルートは `routes.ts` に合わせて `:sceneId`）。手順3「domain（G2）」も済み（2026-10-17。`readiness.ts`・`scenarioContentSections` の切り出し・T1〜T4・T1/T3 の骨抜きの確かめ。`EDITABLE_KINDS` は `editableSceneNodes` に置き換えた）。次は手順4「保存前の確かめ（G6）」（新しいセッション・**標準**）

## 1. 概要

シナリオ製作者が、タイトル → シーン → 選択肢で結末までつなぐ → 公開の前に決めること（概要・想定人数など）→ 公開、の順に迷わず進めるようにする。シナリオ編集の画面はデッキ構造と結末を主役にし、メタデータは畳んだ「公開の前に決めること」へ移して1行の要約で見せる。初めて公開するまでは「次にすること」の案内を出し、公開の前に、公開を止める誤りと止めない注意を画面に出す。シーン編集（結末のノードの編集を含む）はカードの配置を主役にし、前後のシーンへ移る導線とこのシーンの注意を足す。どちらの編集画面も、保存していない編集があるときは画面内の移動の前に確かめる。

## 2. 背景

- 2026-10-14、シナリオの下書きの API の C2 の人間レビューで PO が指摘した（[要望](../backlog/creator-flow-clarity.md)）。メタ情報がずっと表示されていてビジーで、導線が分かりにくい
- 正式仕様：[シナリオの構造とセッション開始までの流れ](../cartagraph/scenario-flow.md)「シナリオのメタデータ」「シナリオの公開」（下書きは書きかけでもよい。公開の検査に通らなければ公開できない）。シーンの移り方は[次のシーンへ進む](../cartagraph/play-and-field.md#次のシーンへ進む)（選択肢カードの効果で移る。GM不在で遊ばせたいシナリオの製作者は、各シーンに先へ進む選択肢を用意する）。共有設定は[グラフの役割](../cartagraph/graph.md#正史グラフの共有設定への格上げ)で「新しく作るシナリオが土台として選べるテンプレート」と定義されている（実装は無い）
- 未解決論点には触れない。仮ルールは scene-objective（目的・終了条件）を畳むだけで、画面の「未決の仮ルール」の表示は畳んだ中に残す
- 今の作り
  - シナリオ編集（`pages/creator/scenario-edit/ui/CreatorScenarioEditPage.tsx`）は2段組で、左にメタデータ（タイトル・概要・シナリオタイプ・前提タグ・想定人数・空間モデル・推奨CP・基本CP）を常に開いて出し、右にデッキ構造と結末を出す。`Editor` は `key={view.draft.updatedAt}` で保存のたびに作り直される
  - 公開の検査は MSW の `writeScenarioFile` が `safeParseScenarioFile`（`packages/domain/src/scenario/file.ts`）を通す。順は、形（失敗したらそこで返す）→ ファイル名と id → id の文字 → 参照（`findScenarioRefErrors`）とシナリオタイプ（`findScenarioTypeErrors`）を見出しごとに `<path> の<見出し>:\n- …` でまとめる。開発サーバーの口（`vite/scenarioFilePlugin.ts`）も同じ関数を使う。誤りは押してから 422 で知る。画面の操作では、移り先に指されているノードを消せないので、参照の誤りはほぼ起きない
  - 先へ進む選択肢の無いシーンの判定 `deadEndNodes`（`scenario/deadEnd.ts`）は、GM 不在の募集の注意（`RecruitForm.tsx`。GM 不在の募集のときだけ出し、提案の扱い方に応じた抜け方を添える）だけが使っている
  - `walk`（`scenario/deck.ts`）は入れ子と、プール用のノード（npc・info・enemy・location）も並べる。シーン編集で開けるのは、最上位の導入・シーン・結末だけ（`CreatorSceneEditPage.tsx` の `EDITABLE_KINDS`）。実データにもプール用のノードが最上位にある（`sc-gray-mansion` とその写し `sc-mansion-mine` の「館の老従者」）
  - 新規作成（`CreatorScenarioListPage.tsx`）はタイトルだけで作り、導入と結末「結末」を対で置く（`handlers.ts` の `POST /scenarios`。提案の扱い方は常に gm-required）。説明文「共有設定をテンプレートとして使える」は、今は使えない
  - シーン編集（`CreatorSceneEditPage.tsx`）は、シーン情報・ロケーション・配置されているカードの順に並ぶ。結末のノードは `EndingNodeEditor.tsx` が描き、自分の `dirty` を持つ。`SceneEditor` は `` key={`${sc.updatedAt}-${scene.id}`} `` で作り直される。他のシーンへ移るには、シナリオ編集へ戻る
  - どちらの編集画面も、保存していない編集があっても、リンクで移ると黙って消える。ルーターは `createHashRouter`（データルーター。テストも `createMemoryRouter`）なので `useBlocker` が使える
  - 「コピーして編集」は、コピーの API が成功してから `navigate` する
  - シードの多く（`sc-galleon`・`sc-gray-mansion` など GM が進める作り）は、選択肢に移り先が無く、ほぼ全部のシーンが行き止まり・届かないと判定される

## 3. 詳細設計

### 決定事項（人間が決定、2026-10-17）

- **D1 1画面のまま、デッキが主役** — シナリオ編集は1画面のまま、デッキ構造と結末を主役に置く。メタデータは畳んだ「公開の前に決めること」へ移し、今の値を1行の要約で見せる（例：冒険・2〜4人・推奨CP 3・空間なし）。タブ・ステップ・別画面には分けない
- **D2 範囲** — シナリオ編集の組み替えに加え、次にすることの案内・公開の検査の結果を前もって出す・一覧から作るときの流れ・シーン編集の画面を含む
- **D3 検査の結果は、止める誤りと止めない注意** — 今の公開の検査（通らないと公開できない）を公開ボタンの前に出す。あわせて、公開を止めない注意を出す。公開の条件は変えない
- **D4 止めない注意は3つ** — 先へ進む選択肢の無いシーン（`deadEndNodes` と同じ判定）、導入から届かないシーン・結末のノード（プール用のノードは対象外。レビューで明確にした）、概要が空。カードが0枚のシーンは注意にしない
- **D5 案内は初めて公開するまで** — 一度も公開していない下書き（`publication` が `none`。コピーした下書きも含む）にだけ出す
- **D6 案内の「済み」は中身から判定する** — ①タイトルを付ける＝タイトルが空白だけでない ②シーンを作る＝導入以外のシーン（`kind: 'scene'`）が1つ以上 ③選択肢で結末までつなぐ＝導入から選択肢でどれかの結末のノードまで辿れる ④公開の前に決めること＝概要が空白だけでない ⑤シナリオ集へ公開。済みに印を付け、最初の未済みを「次にすること」として目立たせる。印が無くても公開はいつでも押せる（止めるのは D3 の誤りだけ）
- **D7 タイトルは上、概要は公開の前** — タイトルは画面の一番上で直せる。概要は想定人数などと一緒に「公開の前に決めること」に入れる
- **D8 読み取り専用では、メタデータを開いて出し、案内・注意は出さない** — 製作者でない人には、想定人数などが大事なので畳まずに出す
- **D9 一覧から作るときは、タイトルだけで作り案内へつなぐ** — 今は使えない説明（共有設定のテンプレート）を外し、作った後の流れを短く言う。作成の API の初期値は変えない
- **D10 シーン編集** — カードの配置を主役にし、ロケーション・目的・終了条件（仮）は畳む。前後へ移る導線として「選択肢の移り先」「ここへ来るシーン」「デッキの並びの前・次」を出す。このシーンに当たる注意（D4 のうちシーンのもの）を出す。結末のノードの編集も同じ扱いにする（レビューで明確にした）。画面の課題は[画面ごとの課題](../screens/issues.md)に ID 付きで洗い出す
- **D11 保存していない編集があれば、画面内の移動の前に確かめる** — シナリオ編集とシーン編集（結末のノードを含む）。react-router の `useBlocker` で止め、確かめて「移る」なら移る

### 人間に確かめたこと（プランの AI レビューで出た、仕様の文面に関わる案。2026-10-17、3件とも案のとおり認められた）

- **H1 「概要」を仕様のメタデータに足す** — 仕様の「シナリオのメタデータ」（`scenario-flow.md`）の属性に概要が無い（タイトルも無い）。コードには `summary`・`title` がある（`packages/domain/src/scenario/model.ts` の `title: z.string()`・`summary: z.string()`）。注意「概要が空」・案内④・要約がこの語に乗るので、メタデータに「**概要** — GM がシナリオを選ぶときに読む、シナリオの紹介文」を足す案
- **H2 注意は「GM 不在で遊ぶと」の前提で出す** — 行き止まり・届かないシーンは、GM のいるセッションでは GM が移り先を付けた選択肢カードを配って抜けられ（`play-and-field.md`「次のシーンへ進む」）、シードの GM 向けのシナリオはほぼ全部のシーンが該当する。仕様の根拠は「GM不在で遊ばせたいシナリオの製作者は、各シーンに先へ進む選択肢を用意する」。注意の文面を「GM 不在で遊ぶと、ここで先へ進めません」「GM 不在で遊ぶと、導入から届きません」に寄せる案（`RecruitForm.tsx` の注意と意味をそろえる）。止めない理由も、仕様とノートにこの形で書く（「GM が裁定で抜ける」とは書かない。「裁定」は提案への返答の語）
- **H3 共有設定のテンプレートは仕様を正にし、未実装として既知の問題に置く** — 仕様（`graph.md`・用語集）は今のルールとして定義している。画面の説明文だけを外し、`docs/notes/scenario-flow.md` の「将来の拡張候補」には置かず、`docs/architecture/known-issues.md` に「共有設定から作れない（仕様はあるが実装が無い）」を1件置く案（ノートに将来の候補として置くと、仕様の定義と食い違う）

- **G2 domain（`packages/domain/src/scenario/readiness.ts`、新規）** — 公開の前の確かめの純粋関数。シナリオ編集とシーン編集の両方が使うので domain に置く

  - `reachableNodeIds(deck): Set<string>`：導入（`kind: 'intro'`）から、選択肢カード（`kind: 'choice'`）の `nextNodeId` を辿って届くノードの id（導入を含む。入れ子の `children` も `walk` で見る。選択肢カード以外の `nextNodeId` は辿らない＝ `deadEndNodes` と同じ考え方）

  - `publishErrors(raw: unknown): { title: string; errors: string[] }[]`：止める誤り。形（`scenarioSchema`）が通らなければ形の節だけを返し、通れば参照とシナリオタイプの節を返す。参照とシナリオタイプの部分は `file.ts` から `scenarioContentSections(s: Scenario): { title: string; errors: string[] }[]`（見出しは今の「参照に誤りがある」「シナリオタイプと中身が食い違っている」）として切り出し、`safeParseScenarioFile` もそれを使う（サーバーと画面で検査が食い違わないように）。`safeParseScenarioFile` の検査の順（形 → ファイル名と id → id の文字 → 参照・タイプ）と返す文面は変えない（形の検査は `safeParseScenarioFile` に残す）。ファイル名と id の検査は画面では要らないので `publishErrors` に含めない。誤りの文は今の文面のまま出す（内部の id が混ざる。製作者向けに書き直すのは範囲外）
  - 「ここへ来るシーン」は既存の `choiceReferrers(deck, [nodeId])`（`scenario/edit.ts`）を使う（新しく作らない）

  - 読み取り専用では案内と公開の前の確かめを出さない（D8）

## 5. 新規テストケース

domain（`packages/domain/src/scenario/readiness.test.ts`）

- **T1 届くノード**：導入 → A → 結末の一本道は全部届く。どこからも指されないシーン B は unreachable。導入から切れた島（B → C）では、C は指されているが届かない。導入から切れた輪（X → Y → X）では X も Y も届かない。入れ子の `children` のノードも、指されていれば届き、指されなければ届かない。選択肢でないカード（情報カードなど）の `nextNodeId` は辿らない。輪（導入 → A → B → A）でも止まる。導入が無いデッキは何も届かない（導入以外のシーン・結末のノードがすべて unreachable）。届かない npc・info・enemy・location のノードは `unreachableNodes` に出ず、届かない結末のノードは出る。導入は出ない
- **T2 結末に届くか**：届く結末のノードがあれば真。結末のノードが届かない所（届かないシーンからしか指されない）にだけあるなら偽。結末のノードが無ければ偽
- **T3 注意**：deadEnd・unreachable・noSummary が D4 のとおりに出て、並びが決まっている（同じノードが行き止まりかつ届かないときは両方が deadEnd → unreachable の順。デッキが [導入, B, A] のように辿る順と並びが違っても、ノードはデッキの並び順）。概要が空白だけ・全角の空白だけでも noSummary、1文字なら出ない。カードが0枚のシーンは、それだけでは注意にならない（deadEnd としては出る）。プール用のノードは注意にならない
- **T4 止める誤り**：参照の誤り（存在しないノードを指す選択肢）とシナリオタイプの食い違い（戦闘なしで空間モデルあり）を節ごとに返す。形の誤り（想定人数が数でない）は形の節だけを返す。誤りの無いシナリオは空。各ケースで `publishErrors(s).length === 0` と `safeParseScenarioFile('scenarios/<id>.json', toScenarioFile(s)).ok` が一致し、誤りの各行がサーバーの文面に含まれる。`safeParseScenarioFile` の文面を、参照の誤りとタイプの食い違いの両方があるシナリオで完全一致で比べる（切り出しの前に足して Green を確かめておく）。`editableSceneNodes` は最上位の導入・シーン・結末だけをデッキの並びで返す（入れ子・プール用のノードは返さない）

画面のロジック（`apps/web/src/test/` に置く。testing.md の単体の置き場所）
