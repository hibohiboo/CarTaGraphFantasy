# シナリオ製作の導線を分かりやすくする

要望：[シナリオ製作の導線を分かりやすくする](../backlog/creator-flow-clarity.md)（[ロードマップ](../roadmap.md#local-flow) local-flow の残り）

状態：プラン作成済み（2026-10-17）。D1〜D11 は2026-10-17に人間と確かめた（質問4ラウンド）。次は手順1「プランの AI レビュー」（新しいセッション・**強い**）

## 1. 概要

シナリオ製作者が、タイトル → シーン → 選択肢で結末までつなぐ → 公開の前に決めること（概要・想定人数など）→ 公開、の順に迷わず進めるようにする。シナリオ編集の画面はデッキ構造と結末を主役にし、メタ情報は畳んだ「公開の前に決めること」へ移して1行の要約で見せる。初めて公開するまでは「次にすること」の案内を出し、公開の前に、公開を止める誤りと止めない注意を画面に出す。シーン編集はカードの配置を主役にし、前後のシーンへ移る導線とこのシーンの注意を足す。どちらの編集画面も、保存していない編集があるときは画面内の移動の前に確かめる。

## 2. 背景

- 2026-10-14、シナリオの下書きの API の C2 の人間レビューで PO が指摘した（[要望](../backlog/creator-flow-clarity.md)）。メタ情報がずっと表示されていてビジーで、導線が分かりにくい
- 正式仕様：[シナリオの構造とセッション開始までの流れ](../cartagraph/scenario-flow.md)「シナリオのメタデータ」「シナリオの公開」（下書きは書きかけでもよい。公開の検査に通らなければ公開できない）。シーンの移り方は[次のシーンへ進む](../cartagraph/play-and-field.md#次のシーンへ進む)（選択肢カードの効果で移る）
- 未解決論点には触れない
- 今の作り
  - シナリオ編集（`pages/creator/scenario-edit/ui/CreatorScenarioEditPage.tsx`）は2段組で、左にメタデータ（タイトル・概要・シナリオタイプ・前提タグ・想定人数・空間モデル・推奨CP・基本CP）を常に開いて出し、右にデッキ構造と結末を出す
  - 公開の検査は MSW の `writeScenarioFile` が `safeParseScenarioFile`（`packages/domain/src/scenario/file.ts`：形・ファイル名と id・`findScenarioRefErrors`・`findScenarioTypeErrors`）を通す。誤りは押してから 422 で知る。画面の操作では、移り先に指されているノードを消せないので、参照の誤りはほぼ起きない
  - 先へ進む選択肢の無いシーンの判定 `deadEndNodes`（`scenario/deadEnd.ts`）は、GM 不在の募集の注意（`RecruitForm.tsx`）だけが使っている
  - 新規作成（`CreatorScenarioListPage.tsx`）はタイトルだけで作り、導入と結末「結末」を対で置く（`handlers.ts` の `POST /scenarios`）。説明文「共有設定をテンプレートとして使える」は、今は使えない
  - シーン編集（`CreatorSceneEditPage.tsx`）は、シーン情報・ロケーション・配置されているカードの順に並ぶ。他のシーンへ移るには、シナリオ編集へ戻る
  - どちらの編集画面も、保存していない編集があっても、リンクで移ると黙って消える。ルーターは `createHashRouter`（データルーター。テストも `createMemoryRouter`）なので `useBlocker` が使える

## 3. 詳細設計

### 決定事項（人間が決定、2026-10-17）

- **D1 1画面のまま、デッキが主役** — シナリオ編集は1画面のまま、デッキ構造と結末を主役に置く。メタ情報は畳んだ「公開の前に決めること」へ移し、今の値を1行の要約で見せる（例：冒険・2〜4人・推奨CP 3・空間なし）。タブ・ステップ・別画面には分けない
- **D2 範囲** — シナリオ編集の組み替えに加え、次にすることの案内・公開の検査の結果を前もって出す・一覧から作るときの流れ・シーン編集の画面を含む
- **D3 検査の結果は、止める誤りと止めない注意** — 今の公開の検査（通らないと公開できない）を公開ボタンの前に出す。あわせて、公開を止めない注意を出す。公開の条件は変えない
- **D4 止めない注意は3つ** — 先へ進む選択肢の無いシーン（`deadEndNodes` と同じ判定）、導入から届かないシーン・結末、概要が空。カードが0枚のシーンは注意にしない
- **D5 案内は初めて公開するまで** — 一度も公開していない下書き（`publication` が `none`。コピーした下書きも含む）にだけ出す
- **D6 案内の「済み」は中身から判定する** — ①タイトルを付ける＝タイトルが空でない ②シーンを作る＝導入以外のシーンが1つ以上 ③選択肢で結末までつなぐ＝導入から選択肢でどれかの結末のノードまで辿れる ④公開の前に決めること＝概要が空でない ⑤シナリオ集へ公開。済みに印を付け、最初の未済みを「次にすること」として目立たせる。印が無くても公開はいつでも押せる（止めるのは D3 の誤りだけ）
- **D7 タイトルは上、概要は公開の前** — タイトルは画面の一番上で直せる。概要は想定人数などと一緒に「公開の前に決めること」に入れる
- **D8 読み取り専用では、メタ情報を開いて出し、案内・注意は出さない** — 製作者でない人には、想定人数などが大事なので畳まずに出す
- **D9 一覧から作るときは、タイトルだけで作り案内へつなぐ** — 今は使えない説明（共有設定のテンプレート）を外し、作った後の流れを短く言う。作成の API の初期値は変えない
- **D10 シーン編集** — カードの配置を主役にし、ロケーション・目的・終了条件（仮）は畳む。前後へ移る導線として「選択肢の移り先」「ここへ来るシーン」「デッキの並びの前・次」を出す。このシーンに当たる注意（D4 のうちシーンのもの）を出す。画面の課題は[画面ごとの課題](../screens/issues.md)に ID 付きで洗い出す
- **D11 保存していない編集があれば、画面内の移動の前に確かめる** — シナリオ編集とシーン編集の両方。react-router の `useBlocker` で止め、確かめて「移る」なら移る

### AI が決めた設計

- **G1 docs（最初のコミット）**
  - `docs/screens/issues.md`：「シナリオ管理（製作者）」「シナリオ編集」「シーン編集」の節を足し、課題を ID 付きで置く（状態は対応中、要望はこの要望）。CRL-1 今は使えない説明（共有設定のテンプレート）がある／作った後に何をするか分からない。CRE-1 メタ情報がずっと出ていてビジー（2026-10-14 の PO の指摘）。CRE-2 次に何をすればよいか分からない。CRE-3 公開を押すまで、通るか・遊べる形かが分からない。CRE-4 保存していない編集がリンクで移ると黙って消える。SCE-1 補足の項目（ロケーション・目的・終了条件）が先に並び、カードの配置が下にある。SCE-2 他のシーンへ移るにはシナリオ編集へ戻る。SCE-3 このシーンが行き止まり・届かないかが分からない。SCE-4 CRE-4 と同じ
  - `docs/screens/index.md`：シナリオ管理（製作者）・シナリオ編集・シーン編集の行に、案内・公開の前の確かめ・畳んだ「公開の前に決めること」・前後へ移る導線・保存前の確かめを足す
  - `docs/cartagraph/scenario-flow.md`「シナリオの公開」に1項：**公開の前の確かめ** — 製作者は公開する前に、検査に通るかと、公開を止めない注意（先へ進む選択肢の無いシーン・導入から届かないシーンや結末・概要が空）を見られる。注意があっても公開できる（下書きは書きかけでもよく、行き止まりを GM が裁定で抜けることもあるため）。語は「製作者」「公開版」を使う。画面の配置は書かない（`spec-writing.md`）
  - `docs/notes/scenario-flow.md`：注意を公開の条件にしなかった理由（GM のいるセッションでは行き止まりを裁定で抜けられる。GM 不在の募集には既に同じ注意がある）、カードが0枚のシーンを注意にしなかったこと（2026-10-17 の人間の判断）。将来の拡張候補に「共有設定をテンプレートにして作る」（今は説明だけがあった）
- **G2 domain（`packages/domain/src/scenario/readiness.ts`、新規）** — 公開の前の確かめの純粋関数。シナリオ編集とシーン編集の両方が使うので domain に置く
  - `reachableNodeIds(deck): Set<string>`：導入（`kind: 'intro'`）から、選択肢カード（`kind: 'choice'`）の `nextNodeId` を辿って届くノードの id（導入を含む。入れ子の `children` も `walk` で見る。選択肢カード以外の `nextNodeId` は辿らない＝ `deadEndNodes` と同じ考え方）
  - `unreachableNodes(deck): DeckNode[]`：導入以外で、届かないノード（シーン・結末）
  - `reachesEnding(deck): boolean`：届くノードに結末のノードがあるか
  - `publishWarnings(scenario): PublishWarning[]`：`{ kind: 'deadEnd' | 'unreachable', node: DeckNode }` と `{ kind: 'noSummary' }`。並びは deadEnd → unreachable → noSummary、ノードはデッキの並び順
  - `publishErrors(scenario): string[]`：止める誤り。`file.ts` の `safeParseScenarioFile` から、形（`scenarioSchema`）・`findScenarioRefErrors`・`findScenarioTypeErrors` の部分を `scenarioContentErrors(raw): string[]`（`file.ts` に置く）に切り出し、`safeParseScenarioFile` もそれを使う（サーバーと画面で検査が食い違わないように）。`safeParseScenarioFile` の返す文面（`<path> の…`）は変えない。ファイル名と id の検査は画面では要らないので含めない
- **G3 シナリオ編集（`CreatorScenarioEditPage.tsx`）**
  - 1段組にする。上から：ヘッダ（見出し・状態・コピー・保存・公開）→ 注意の行（今の `DraftNotes` など）→ タイトルの入力 → 案内（D5）→ シナリオデッキの構造 → 結末 → 公開の前の確かめ → 公開の前に決めること（畳む）
  - 案内 `CreationSteps`（同じスライスの `ui/`）：判定は `lib/steps.ts` の `creationSteps(scenario, publication)`（D6 の5段。`{ id, label, done }[]`）。編集中の値（`draft`）で判定する。最初の未済みに `aria-current="step"` と「次にすること」の表示。④の段には「開く」ボタンを置き、「公開の前に決めること」を開いてそこへスクロールする
  - 公開の前の確かめ `PublishCheck`（同じスライスの `ui/`）：製作者だけ、公開の状態に関係なく出す（公開し直す前にも見る）。編集中の値で判定する。誤りがあれば「公開できない理由」として並べ、公開・公開し直すを押せなくする（今の `dirty` による無効化に足す）。注意は「公開はできます」と添えて並べ、ノードの注意は保存済みのノードならシーン編集へのリンクにする（未保存のノードは今の `editLink` と同じく「保存すると編集できる」）。何も無ければ「公開の前の確かめ：問題はありません」の1行
  - 公開の前に決めること：`<details>`。`summary` に見出しと1行の要約（シナリオタイプ・想定人数・推奨CP・空間モデル・前提タグの数。概要が空なら「概要が未記入」）。中身は概要と今のメタデータの項目（タイトルは除く）。製作者は閉じて始め、読み取り専用は開いて始める（D8）。開閉は `open` の状態で持つ（案内の「開く」から開くため）
  - 読み取り専用では案内と公開の前の確かめを出さない（D8）
  - 「メタデータ」の見出しの説明文「GMがシナリオを選ぶ際の判断材料。…」は「公開の前に決めること」の説明として残す
- **G4 シナリオ管理（製作者）（`CreatorScenarioListPage.tsx`）**：「新しいシナリオを作る」の説明を「タイトルを付けて下書きを作ります。作ったら、シーンを作り、選択肢で結末までつないで公開します。」にする。共有設定の文は外す。ボタン名「下書きを作成」は変えない
- **G5 シーン編集（`CreatorSceneEditPage.tsx`）**
  - 並び：ヘッダ → 名前（今のシーン情報の名前の入力だけを上に）→ このシーンの注意（製作者だけ）→ 配置されているカード → つながり → 補足（`<details>`：ロケーション・目的（仮）・終了条件（仮）。製作者は閉じて始め、読み取り専用は開いて始める）
  - このシーンの注意：`publishWarnings` のうちこのノードのもの（deadEnd・unreachable）。保存済みのシナリオのデッキで、このノードだけ編集中の値に差し替えて判定する（このシーンの選択肢を直したら、すぐ注意が変わる。他のノードは保存済みの値）。結末のノードには deadEnd は出ない（`deadEndNodes` が導入・シーンだけを見る）
  - つながり（`ui/SceneLinks.tsx`、新規）：「選択肢の移り先」＝このノードの編集中の選択肢カードの `nextNodeId` のノード（重複は1つに）。「ここへ来るシーン」＝保存済みのデッキで、選択肢カードがこのノードを指すノード。「並びの前・次」＝`walk` の並びで前後のノード。どれもノード名のリンク（`/creator/scenarios/:id/scenes/:nodeId`）。無ければ「なし」。製作者でない人にも出す（読むときにも辿りたい）
- **G6 保存前の確かめ（`shared/lib/useUnsavedGuard.ts`、新規）**：`useUnsavedGuard(dirty: boolean)`。`useBlocker` で、`dirty` のときに別のパスへの移動を止め、`window.confirm('保存していない編集があります。移ると消えます。移りますか？')` が真なら `proceed`、偽なら `reset`。同じパス（検索・ハッシュだけの変化）は止めない。保存の後は `Editor` が `key={updatedAt}` で作り直されて `dirty` が偽になるので止まらない。シナリオ編集の「コピーして編集」で移るときも、未保存の編集があれば確かめる（コピーされるのは公開版で、未保存の編集は消えるため。前のサイクルの「未保存の編集があっても押せる」は変えない）。リロード・タブを閉じる（`beforeunload`）は対象にしない
- **G7 docs（実装の後）**：`docs/screens/issues.md` の状態を完了に、要望ファイルの状態・サイクル、`docs/architecture/web-app.md` に画面の部品の記述があれば合わせる（無ければ足さない）

`packages/domain` の変更：あり（G2。型は変えず、関数を足して `file.ts` を切り出す）。API・応答の形は変えない。仮ルールは足さない。新しい機械的な検査は足さない。

## 4. テスト影響範囲

- **メタデータの入力を見つけるテスト**：`scenarioType.test.tsx`（10か所）・`scenarioPublishScreens.test.tsx`・`pages.test.tsx` は、ラベル（想定人数・空間モデルなど）で入力を探している。畳んだ `<details>` の中の入力も DOM にはあり、`getByLabelText` で見つかるが、`user.click`・`user.type` は見えない要素で失敗しうる。実装で確かめ、要るなら先に「公開の前に決めること」を開く手順をテストに足す（期待値は変えない）
- **見出し「メタデータ」**を探すテストがあれば、新しい見出しに直す（実装で grep する）
- **`safeParseScenarioFile` を使うテスト**（`file.test.ts`・`scenarioFiles.test.ts`・公開のテスト）：文面を変えないので通るはず。切り出しの前後で全部通ることを確かめる
- **公開ボタンの無効化**：誤りのあるシナリオで公開を押して 422 を確かめているテストがあれば、ボタンが押せなくなるので落ちる。MSW 側の 422 は API のテスト（`fetch` で直接）で確かめ、画面のテストは「押せない・理由が出る」に直す
- **ブラウザの通し**：`apps/web/e2e/dev/scenario-authoring.mjs`・`scenario-publish.mjs` はメタデータの入力・ボタンを操作する。畳んだ中の入力を操作するなら開く手順を足す
- **シーン編集のテスト**（`CreatorSceneEditPage.test.tsx`・`scenarioAuthoringScreens.test.tsx`）：並びが変わる。補足（ロケーション・目的）を操作するテストは開く手順を足す
- **画面からの移動**：未保存のまま移るテストがあれば、確かめのダイアログで止まる。`window.confirm` を `vi.spyOn` で返すか、保存してから移る

## 5. 新規テストケース

domain（`readiness.test.ts`）

- **T1 届くノード**：導入 → A → 結末の一本道は全部届く。どこからも指されないシーン B は unreachable。入れ子の `children` のノードも、指されていれば届き、指されなければ届かない。選択肢でないカード（情報カードなど）の `nextNodeId` は辿らない。輪（A → B → A）でも止まる。導入が無いデッキは何も届かない（導入以外すべて unreachable）
- **T2 結末に届くか**：届く結末のノードがあれば真。結末のノードが届かない所にだけあるなら偽。結末のノードが無ければ偽
- **T3 注意**：deadEnd・unreachable・noSummary が D4 のとおりに出て、並びが決まっている。概要が空白だけでも noSummary。カードが0枚のシーンは、それだけでは注意にならない（deadEnd としては出る）
- **T4 止める誤り**：参照の誤り（存在しないノードを指す選択肢）とシナリオタイプの食い違い（戦闘なしで空間モデルあり）を返す。形の誤り（想定人数が数でない）も返す。誤りの無いシナリオは空。`safeParseScenarioFile` の文面は切り出しの前と同じ（既存の `file.test.ts` が通る）

画面のロジック（`pages/creator/scenario-edit/lib/steps.test.ts` か `apps/web/src/test/` の流儀に合わせる）

- **T5 案内の段**：作った直後（導入と結末だけ）は①済み・②が次。シーンを足すと②済み・③が次。選択肢で結末までつなぐと③済み。概要を書くと④済み。公開すると案内ごと出なくなる。途中の段を飛ばしても（概要だけ書いても）、最初の未済みが「次」

web（画面）

- **T6 シナリオ編集の並び（D1・D7）**：製作者が開くと、タイトルの入力・デッキ構造・結末が見え、「公開の前に決めること」は閉じていて要約（例：冒険・2〜4人・推奨CP 3・空間なし）が出る。開くと概要・想定人数などが直せて、保存すると下書きに入る。要約は編集に合わせて変わる
- **T7 案内（D5・D6）**：新しく作ったシナリオに案内が出て、「次にすること」がシーンを作る段。④の「開く」で「公開の前に決めること」が開く。公開すると案内が消える。公開版のある自分のシナリオには出ない。コピーした下書き（公開版なし）には出る。読み取り専用には出ない
- **T8 公開の前の確かめ（D3・D4）**：作った直後は「導入に先へ進む選択肢が無い」「結末に届かない」「概要が未記入」の注意が出て、公開は押せる（押すと公開できる）。選択肢で結末までつないで概要を書くと「問題はありません」。注意のノードの名前からシーン編集へ移れる。止める誤り（戦闘なしにしたうえで自動戦闘のシーンがある下書きを API で作る）があると、理由が出て公開・公開し直すが押せない。読み取り専用には出ない
- **T9 読み取り専用（D8）**：他人のシナリオでは「公開の前に決めること」が開いていて、案内と確かめが無い
- **T10 一覧（D9）**：「新しいシナリオを作る」に共有設定の文が無く、作った後の流れの文がある
- **T11 シーン編集の並びと注意（D10）**：カードの配置が補足より前にあり、補足は閉じている（読み取り専用では開いている）。行き止まりのシーンに「先へ進む選択肢がありません」が出て、選択肢カードに移り先を付けると（保存前でも）消える。どこからも指されないシーンに「導入から届きません」が出る
- **T12 つながり（D10）**：導入 → A → 結末で、A の画面に「ここへ来るシーン：導入」「選択肢の移り先：結末」「並びの前・次」が出て、それぞれのリンクで移れる（移り先にしか無い要素を待つ）。移り先の無いシーンは「なし」
- **T13 保存前の確かめ（D11）**：シナリオ編集でタイトルを変えて保存せず「一覧へ戻る」を押すと確かめが出る。断ると移らず編集が残る。認めると移る。保存した後は確かめずに移る。シーン編集で、つながりのリンクで同じことを確かめる。シナリオ編集で未保存のまま「コピーして編集」を押すと確かめが出て、認めるとコピーへ移る。編集していなければ確かめは出ない

骨抜きの確かめ（`node scripts/mutate-check.mjs`）：T1（選択肢以外のカードも辿る、children を辿らない）、T3（noSummary の trim を外す）、T5（最初の未済みでなく最後を「次」にする）、T7（`publication` の条件を外す）、T8（誤りによる無効化を外す）、T11（編集中の値でなく保存済みで判定する）、T13（`dirty` の条件を外す）が落ちること

## 6. 実装順（担当はすべて新しいセッションで1人。手順番号は下のとおり）

1. プランの AI レビュー（依頼文「2」の観点は設計整合・仕様整合。運用は当てはまらない）と人間の確認。ここでセッションを区切る — **強い**

4. 保存前の確かめ（G6）、T13 の一部 — **標準**
5. シナリオ編集・一覧（G3・G4）、T5〜T10、既存テストの手順の追従（4章） — **標準**
