# API のリクエストのスキーマを、バックエンドと共用する

要望：[API のリクエストのスキーマを、バックエンドと共用する](../backlog/api-schemas.md)（[ロードマップ](../roadmap.md#backend-1on1) backend-1on1 の下ごしらえ）

状態：完了（PR #22）。D1〜D5 は2026-10-10に人間と確かめた。プランの AI レビュー（設計整合性・運用・テスト網羅）の P0・P1 を反映した

## 1. 概要

API のリクエストの本文の形を zod のスキーマとして新しいパッケージ `packages/schemas`（`@cartagraph/schemas`）に置き、モック（MSW のハンドラ）は本文を検査してから使う。通らなければ 422 で返し、500 にしない。画面（`entities/*/api` の mutation）は同じスキーマから型を引く。`request.json()`・`request.text()` で本文を直接読む書き方は、Biome の GritQL プラグインで止める。

## 2. 背景

- 冒険者だけにする C3 の振り返り（2026-10-10、`docs/process/evolution.md`「候補」、採用済み）。`apps/web/src/mocks/handlers.ts` は本文を `(await request.json()) as {...}` で型を付け替えるだけで使う箇所が10か所あり、`null`・数・項目の型違いの本文で 500 になる穴を、実装の AI レビュー（異常系）が C2・C3 と続けて1か所ずつ見つけていた
- 既知の問題（`docs/architecture/known-issues.md`）：「キャラクターの作成の API が…」の追記（`POST /api/characters`・`start-solo` が本文 `null` などで 500）
- 正式仕様（`docs/cartagraph/`）は API の形を決めていない。API とモックの仕組みの正は `docs/architecture/web-app.md`
- 本文を読むエンドポイントは16本（下の表）。うち `readJson` で読むのは5本（2・3・10・15・16）で、手書きの判定（`isStringArray`・`parseNarration` など）で形を見ている。残りの11本は型を付け替えるだけ（C3 で直した5番を含む）
- 依存の配置：pnpm の厳格な配置で、`apps/web` は zod を解決できない（`apps/web/package.json` に無い）。`@cartagraph/domain` は `exports` のワイルドカードで `src/*.ts` を直接公開している
- Biome 2.5.13。`overrides[].plugins` に GritQL のプラグインを書けば、`includes` で範囲を絞れ、除外もできる（プランレビューでスクラッチで確かめた）。同じファイルに当たる後ろの override の `noRestrictedImports` は、前の override の `patterns` を併合せず置き換える

## 3. 詳細設計

### 決定事項（人間が決定。2026-10-10）

- **D1 置き場所** — 新しいパッケージ `packages/schemas`（`@cartagraph/schemas`）。`@cartagraph/domain` に依存してよい（ドメインのスキーマ・型を使う）。逆は禁止。`apps/web` と将来のバックエンドが使う
- **D2 範囲** — リクエストの本文だけ。応答は今の domain の型を使い続け、応答のスキーマはバックエンドに着手するときに別の要望で足す（要望ファイルの題名・要約をリクエストに絞る）
- **D3 画面の型** — `entities/*/api` の mutation の本文の型は、スキーマから引く。画面では検査しない（送る側なので型だけ）
- **D4 検査の書き方** — `safeParse` で検査し、通らなければ 422（`{ message }`）で返す。`parse` と、例外を 422 に変える包みの組み合わせは採らない
- **D5 下書きの保存（H1、案A）** — `PATCH /api/scenarios/:id` は「本文がオブジェクトか」だけを見る（今の振る舞い）。応答を 400 から 422 にそろえる。`scenarioSchema.partial()` は採らない（知らないキーを断る作りで、再挑戦不可の結末に結末タグを求める業務の検査も含み、書きかけの下書きを保存できなくなるため）。既知の問題の「`scenarioType: null` で編集画面が落ちる」は残す

### AI が決めた設計（プランの AI レビューを反映）

- **G1 パッケージの形** — `packages/domain` と同じ作り：`package.json`（`exports` はワイルドカードで `./*.test` を除く、`zod`（domain と同じ `^4.6.5`）と `@cartagraph/domain`（`workspace:*`）に依存）・`tsconfig.json`（apps/web と同じく `noUnusedLocals`・`noUnusedParameters` を持つ）・`vitest`。`src/` の直下にファイルを置かず、`index.ts` を作らない。ディレクトリは URL の最初の区切りごと：`characters/`・`recruitments/`・`sessions/`・`scenarios/`（`/scenarios/:id/start-solo` と `/scenarios/:id/recruitments` は `scenarios/`）、それぞれ `request.ts`（スキーマと型）とテスト。共通の検査は `body/parse.ts`。依存の向きは「各ディレクトリ → `body/`」だけ（`body/` はどこにも依存しない）
- **G2 検査とメッセージは schemas に置く** — `body/parse.ts` に純粋な関数 `safeParseBody(body, unknown)` を置き、`{ ok: true, data } | { ok: false, message }` を返す。将来のバックエンドも同じメッセージの形を使える（SSOT）。`apps/web` は zod を見ない（依存を足さない）
  - スキーマは `defineBody(schema, messages)` で、本文のスキーマと「最初の区切りのキー → 個別のメッセージ」の表を組にする。メッセージは、誤り（最初の1件）の場所の最初のキーが表にあればその文、本文そのもの（場所が空）の誤りは表の `''` かなければ「本文の形が正しくありません」、それ以外は「本文の形が正しくありません（<場所を . でつないだもの>）」。zod の `error` パラメータは使わない（配列・オブジェクトに付けると要素の誤りに効かず、既定の英語のメッセージと見分けられないため。プランレビューで確かめた）
- **G3 スキーマに書くのは形だけ** — 型・必須か・配列の要素の形。業務の検査（名前が空でない、能力値の配分、CP 予算、募集人数が1以上の整数、移り先が選べるノードか、使う条件が3種のどれか、優先順位が1枚以上など）はハンドラ・ドメインに残し、今のメッセージを保つ。そのため、業務の検査が今のメッセージを返している項目は、形だけを見る（12番の `when` は `z.string()`、`priority` は省ける）
- **G4 知らないキー** — `z.object`（知らないキーは捨てる）。例外は5番 `PATCH /characters/:id`：`abilities`・`hp`・`baseActionValue` のキーがあれば値が何でも 422（`z.never().optional()`。C3 で決めた振る舞い）
- **G5 本文を読む口を1つにする** — `apps/web/src/mocks/body.ts` に `readBody(request, body)`：本文の文字列が空なら `{}` として、それ以外は JSON として読み（壊れていれば本文そのものの誤り）、`safeParseBody` に渡す。通らなければ 422 の `HttpResponse` を返す。呼ぶ位置は、今 `request.json()`・`readJson` を呼んでいる位置（404・403・409 の判定の順は変えない）。`readJson`・`isStringArray`・`isOptionalString`・`parseNarration` は消す
- **G6 lint（GritQL）** — `scripts/biome/no-request-body.grit`（`request.json()` と `request.text()` を誤りにする。実装時に `$x.json()`・`$x.text()` から絞った：`mocks/devScenarioFileStore.ts` の応答の `res.text()` にも当たったため。MSW のハンドラは `({ request })` で受け取るのが定石なので、名前で見れば足りる）を、`biome.json` の `overrides` で `apps/web/src/mocks/**` にだけかけ、`apps/web/src/mocks/body.ts` を除く（画面の `shared/api/api.ts` の `res.json()` は対象外）。置き場所を `scripts/` にするのは、進化ログの検査（`scripts/check-evolution-log.mjs` の `PROCESS_FILES`）がそのまま見るため。`static-analysis.md` の frontmatter の `paths` に `scripts/biome/**` を足し、`node scripts/sync-claude-rules.mjs` を流す。GritQL のプラグインを採る理由（nursery のルールを入れていないこととの違い）と、`request['json']()` などのすり抜けは許すことを `static-analysis.md` に書く。置き換えが終わってから入れるので、既知の問題には載せない
- **G7 依存の向き（Biome）** — `@cartagraph/schemas` を import してよいのは `apps/web/src/entities/**`・`apps/web/src/mocks/**`・`apps/web/src/test/**`。それ以外の層（app・pages・widgets・features・shared）と、層の直下のファイル用の override の **すべて** の `noRestrictedImports` に `@cartagraph/schemas`・`@cartagraph/schemas/**` を足す（後ろの override が置き換えるため）。`packages/schemas/src/**` に domain と同じ override（`noBarrelFile`・`noReExportAll`・自分のパッケージ名での import の禁止・ディレクトリの向き）を足す。`packages/domain` から schemas への import は、domain が依存を宣言しないので解決に失敗して止まる（lint は足さない。architecture.md にそう書く）
- **G8 依存の宣言とコマンド** — `apps/web/package.json` に `"@cartagraph/schemas": "workspace:*"`、`pnpm install` で `pnpm-lock.yaml` を作り直してコミット。ルートの `package.json` に `schemas:typecheck`・`schemas:test`。`.githooks/pre-push`（と冒頭のコメント）・CI（`.github/workflows/ci.yml`）に足す

## 5. 新規テストケース

`packages/schemas`（単体）

- **T1** `safeParseBody`：場所の最初のキーが表にあればその文、本文そのものの誤り（`null`・数・文字列・配列）は `''` の文か「本文の形が正しくありません」、それ以外は「本文の形が正しくありません（characterId）」の完全一致、入れ子は「（choices.0.name）」。誤りが複数あれば最初の1件。通れば `data`（知らないキーは捨てる）
- **T2** 各エンドポイントのスキーマ：正しい本文が通る。必須の項目が無い・型が違う（数の代わりに文字列、配列の代わりに文字列、配列の要素の型違い）と失敗する。省ける項目は省いても通る
- **T3** 5番：`addCardIds` だけ・`{}` なら通る。`abilities`・`hp`・`baseActionValue` は値が `null`・`0` でもキーがあれば失敗する（今の `'k' in body` と同じ）。ほかの知らないキーは捨てて通る
- **T4** 4番：`abilities` に `luck` を混ぜても通り、結果に `luck` が無い。`abilities` のキーが欠ける・数でない値・入れ子の誤りでも、メッセージは「能力値（体・技・心）を数で送ってください」

MSW

- **T5** `readBody`（`apps/web/src/test/body.test.ts`）：本文の文字列が空なら `{}` としてスキーマに渡す。JSON として壊れていれば 422 で本文そのものの誤りのメッセージ
- **T6** 表で全エンドポイント（1〜16）を回す（`apps/web/src/test/requestBodies.test.ts`）：各行に、本文 `null` と「項目の型違い」（例：`{ characterId: 1 }`・`{ text: 5 }`・`{ name: 5 }`・`{ title: 5 }`・`{ cardName: 5 }`・`{ reason: 5 }`・`{ mode: 'x' }`）を送り、**エンドポイントごとに期待する `message`** で 422 になり、500 にならず、状態（キャラクター・セッション・募集・シナリオの件数と対象の中身）が変わらない。前提の検査（受付中でない・GM 不在・プレイ中でないなど）で止まらない状態を用意する

## PR 下書き

**タイトル**：API のリクエストの本文を packages/schemas のスキーマで検査する

### 課題

MSW のハンドラ（`apps/web/src/mocks/handlers.ts`）は、本文を `(await request.json()) as {...}` で型を付け替えるだけで使う箇所が10か所あり、`null`・数・項目の型違いの本文で 500 になっていた。実装の AI レビュー（異常系）が C2・C3 と続けて1か所ずつ見つけていたので、冒険者だけにする C3 の振り返りで、読む口を1つにして機械で止めると決めた。置き場所は、バックエンドと共用する `packages/schemas`（人間の案）。要望 `docs/backlog/api-schemas.md`、プラン `docs/plans/2026-10-10-APIスキーマの共用.md`。

### 解決策

- `packages/schemas`（`@cartagraph/schemas`）を新設し、本文を読む16本のエンドポイントの本文の形を zod で置いた。書くのは形だけで、業務の検査（名前が空、能力値の配分、募集人数など）はハンドラ・ドメインに今のメッセージのまま残した
- 本文の文字列の読み方（空・空白だけは `{}`、壊れた JSON は本文の誤り）と、誤りのときの日本語のメッセージ（`safeParseBodyText`）も schemas に置いた。将来のバックエンドが同じものを使える。個別のメッセージは「最初のキー → 文」の表で持つ（zod の `error` は配列・オブジェクトの要素の誤りに効かないため）
- ハンドラは `mocks/body.ts` の `readBody` で検査してから使い、崩れていれば 422 で何も変えない。`apps/web` は zod を直接使わない
- 下書きの保存（`PATCH /api/scenarios/:id`）は、書きかけでも保存できるよう、本文がオブジェクトかだけを見る（400 を 422 にそろえた。人間の判断、案A）
- 画面の mutation の本文の型をスキーマから引く
- lint：`request.json()`・`request.text()` の直接の呼び出しを Biome の GritQL プラグイン（`scripts/biome/no-request-body.grit`）で止める。`@cartagraph/schemas` を import してよい層を entities・mocks・test に絞った（層ごとの override すべてに足した。後ろの override が前の禁止を置き換えるため）
- `schemas:typecheck`・`schemas:test` を pre-push・CI に足した
