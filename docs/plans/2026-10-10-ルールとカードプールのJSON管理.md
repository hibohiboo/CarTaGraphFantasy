# ルールと基本カードプールの JSON 管理

要望：[ルールと基本のカードプールを JSON でリポジトリ管理する](../backlog/rules-json.md)（[ロードマップ](../roadmap.md) M1 の完成の条件1）

## 1. 概要

システム製作者が作るものを、リポジトリ直下の `rules/` に JSON で置く。

- `rules/cards.json` — システムのカード一覧。キャラクターが持つカード（基本カードプールのカード、村のお店で習う戦闘スキル、仮に置く報酬カード）を1か所で定義する。仕様の用語ではなく、実装上のカタログ（基本カードプールより広い集合）
- `rules/character-creation.json` — 基本カードプール（カードの id の列）と、キャラクター作成の数値（CP 予算・能力値の合計と範囲・作成時の HP）。能力値の配分と作成時の HP は、未解決論点に残る**仮ルール**

MSW・画面・`packages/domain` はここから読み、コードに書いた同じ値を消す。シナリオは、システムのカードを中身ごと持たず id で指す（村はずれの一歩のお店）。テスト専用の試験シナリオの試験官は、村はずれの一歩の JSON から読む。既知の問題「シナリオの JSON と fixtures に、同じカード・敵の定義が重複している」の3件のうち2件（戦闘スキル・試験官）が消える。

M1 では専用の画面は作らない。システム製作者は JSON を直してコミットする（ライトルート。下の「ドキュメント」）。

## 3. 詳細設計

### 決定事項（grilling とプランレビューの結果、人間が決定。2026-10-10）

- **D1 範囲** — システムのカード一覧・基本カードプール・キャラクター作成の数値（CP 予算・能力値の合計と範囲・作成時の HP）を JSON にする。自動戦闘・村の成長の仮ルールの計算はコードのまま
- **D2 シナリオからは id で参照** — シナリオの JSON はシステムのカードを id だけで持ち（`soloEffect.gainCardIds`）、使うときにカード一覧から引く。読み込み時の検査で、存在しない id を止める
- **D3 置き場所** — リポジトリ直下 `rules/` に、`cards.json` と `character-creation.json` の2ファイル
- **D4 試験官も片づける** — テスト専用の試験シナリオは、村はずれの一歩の JSON の試験官を読んで使う。灰色館の手札の重複は今回触らない
- **D5 報酬カード** — 「航海の心得」「炎の剣」もシステムのカード一覧に置く（基本カードプールには入れない）。仕様では報酬カードの持ち主はシナリオ（または共有設定）なので、仮置きとして既知の問題に記録し、シナリオに報酬の定義を作るときに移す
- **D6 能力値の上限は1つ** — 村の成長の上限も、`character-creation.json` の能力値の上限を使う（domain の村の関数に上限を渡す）。solo-village.md の「上限は5」は「キャラクター作成の能力値の上限（いまは5）」に書き換える
- **D7 作成時の HP は仮ルールとして JSON に載せる** — `initialHp`。付けるのは今と同じく、能力値を持って作ったときだけ。未解決論点「キャラクター作成時の体・技・心の初期配分方法」に、作成時の HP（いまは仮に14、能力値を持つときだけ）を含める

### その他の設計判断（AI が決めたもの）

- **E1 「仮」を消さない** — 能力値の配分と作成時の HP は、`character-creation.json` の `$comment`、domain のスキーマの説明、画面の表示「（配分方法は未決の仮ルール）」の3か所で「仮」と示す（architecture.md「境界」）。`{ total, min, max }` の形はいまの仮ルール（合計を範囲内で配る）を表すだけで、論点が決まったら作り直すと説明に書く
- **E2 範囲を画面で効かせる** — 能力値の範囲を、入力欄の属性だけでなく作成ボタンの条件にも入れる（合計が `total` と等しく、どれも `min`〜`max`）。JSON の範囲が表示だけで効かないのを避ける。サーバー側の能力値の検査は今もしておらず、今回も足さない（スコープ外）
- **E3 画面の初期値** — 能力値の初期値は `abilities` から作る（`total` を3つにできるだけ均等に配り、余りを体から1ずつ。範囲に収まらなければ `min` で埋める）。純粋関数にして domain の `character/creation.ts` に置く
- **E4 シナリオ固有のカードは今までどおり中身ごと** — 引換カード・達成カードは `gainCards`・`achievement` に中身ごと書く。`gainCardIds` はシステムのカードだけ。加える順は `gainCards` → `gainCardIds`
- **E5 参照の検査の範囲** — `findSystemCardRefErrors` が見るのは `soloEffect.gainCardIds` の実在と、シナリオ固有のカード（`gainCards`・`achievement`・ノードに置いたカード）の id がシステムのカードの id とぶつからないこと。`dealWhen`・`playWhen` の `lacksCards` などのカードの id は、シナリオ固有のカードも指すので見ない
- **E6 読み込みを関数に切り出す** — `rulesFiles.ts` と `scenarioFiles.ts` は、モジュールの読み込み時に検査して止まる。呼び出しを外してもテストが落ちるよう、domain に入力を受けて検査する関数（`loadRules`・`loadScenarioFiles`）を置き、壊れた入力でパスつきの例外になることを単体で確かめる（testing.md「骨抜き禁止」）
- **E7 複雑度を上げない** — `applySoloEffect` は既存の違反として `biome-ignore` で抑えている。id を引く処理は `resolveGainCards(effect, cards)`（`CardDef[]` か誤り）に切り出し、`applySoloEffect` の分岐を増やさない
- **E8 カードは深く複製して渡す** — カード一覧は `resetDb()` で戻らないモジュールの定数になる。デッキ・手札に入れるときは、POST・PATCH `/api/characters` を含め `structuredClone` する（今の POST・PATCH は複製していない）
- **E9 `/api/card-pool` に能力値のルールも載せる** — 予算がすでに載っているので、`abilities` を足す。型は domain の `CharacterCreationRules['abilities']` を使う
- **E10 基本カードプールのカードは CP コストを持つ** — 基本カードプールに入るカードは `cpCost` が0以上の整数であることを、作成のルールの検査で止める（無いと0扱いで無料になるため）。基本カードプールは1枚以上

### JSON の形

`rules/cards.json`

```json
{
  "$comment": "システムのカード一覧（実装上のカタログ）。…",
  "cards": [ { "id": "c-lantern", "kind": "item", "name": "灯火のランタン", … } ]
}
```

- 各カードは `cardDefSchema`（カードごとの `$comment` も書ける）。並びは今の `fixtures.ts` の `cards` の順。値は変えない
- 検査：形（知らないキーは誤り）、`cards` が必須、id の重複

`rules/character-creation.json`

```json
{
  "$comment": "キャラクター作成のルール。能力値の配分と作成時の HP は仮ルール（docs/open-questions.md）…",
  "basicPoolCardIds": ["c-lantern", …],
  "cpBudget": 5,
  "abilities": { "total": 9, "min": 1, "max": 5 },
  "initialHp": 14
}
```

- 形の検査（zod）：知らないキーは誤り、すべて必須、数値は整数、`cpBudget`・`initialHp`・`abilities.min` は1以上
- 関係の検査（zod の `superRefine`）：`min ≤ max`、`3×min ≤ total ≤ 3×max`
- カード一覧との検査（`parseCharacterCreationRules` の中）：`basicPoolCardIds` が1件以上・重複なし・すべて一覧に実在、そのカードの `cpCost` が0以上の整数
