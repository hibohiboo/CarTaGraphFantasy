# 技術スタック

CarTaGraphFantasyの実装に使う技術スタックの方針を整理する。決めた理由・採らなかった案・将来の拡張候補は[デザイナーノート](../notes/architecture/index.md)にある。

## 開発フェーズの段階分け（決着）

いきなりセッション管理システム（ドライバー・ナビゲーターの非同期プレイ、GM/PL操作）まで作るのではなく、**段階的に**進める。

1. まず、[カードモチーフでの閲覧体験](../cartagraph/index.md#webサイト)を提供する公開閲覧サイトを作る。
2. 実際にプレイできるセッション管理機能は、後続フェーズで追加する。

## 実装言語（決着）

**TypeScriptのみ**で統一する。厳密な決定性よりも「機械的な自動判定より人間の裁量を優先する」というゲームデザインの方針（[論点Mで決着した通り](../cartagraph/play-and-field.md#提案の裁定待ちの間の状態遷移)）と揃え、開発スピードを優先する。

## インフラ・ホスティング（決着）

- **クラウド** — AWSを使い、CDK（TypeScript）でIaCする。
- **閲覧サイトのホスティング** — いまはGitHub Pages。移行先はS3 + CloudFront。移行の時期は[未解決論点](../open-questions.md#開発の仕組み)。
- **バックエンドAPI・グラフDB（Neptune等）の具体的な構成** — セッション管理機能のフェーズで決める（[未解決論点](../open-questions.md#開発の仕組み)）。

## パッケージマネージャ・モノレポ構成（決着）

- **パッケージマネージャ** — pnpm。
- **フォルダ構成** — モノレポ構成。

```text
├─ apps/       # 閲覧サイト等のアプリケーション
├─ packages/   # 共有ロジック・スキーマ等
├─ infra/      # CDKによるIaCコード
└─ docs/       # 設計仕様書（VitePress、このサイト）
```

## データベース（決着）

- **RDB** — Neon（サーバーレスPostgres）を使う。
- **正史グラフ・PC発見グラフの表現方法** — 専用のグラフDB（Neptune等）は使わず、RDB上で（隣接リストテーブル＋再帰CTE等で）グラフ構造を表現する。

## 閲覧サイトの実装方針（決着）

- **既存のVitePress docsサイトとの関係** — 分離する。VitePress docsは開発者・企画側の仕様書として維持し、カードモチーフの閲覧体験は別の新規フロントエンドとして構築する。
- **フロントエンドフレームワーク** — React。

## 閲覧サイトのUI（Webアプリ）

デザイントークン・カードの縦横比・UIパターンと、React への移植の指針は [Webアプリの仕組み](web-app.md#デザインシステム) に置く。

## この章の設計原則

1. いきなり全部作らず、閲覧サイト→セッション管理システムの順で段階的に進める。
2. 実装言語はTypeScriptで統一し、決定性より人間の裁量を優先するゲームデザインの方針と揃える。
3. クラウドはAWS＋CDKを選び、学習目的とコスト最小化のバランスを取る（コストが嵩む部分は代替サービス〈Neon〉を使ってよい）。
4. 設計仕様書（VitePress）とプロダクト（閲覧サイト・将来のアプリケーション）は分離する。
5. グラフ構造は、必要性が具体化するまで専用グラフDBを導入せず、RDB上で表現する。
