# 閲覧サイト・セッション画面プロトタイプ 引き継ぎまとめ

`docs/public/preview/` 配下に作った、静的HTML・CSSのみによる全15画面のデザイン試作を、React実装フェーズに引き継ぐための まとめ。デザイン検証が目的であり、実装コードそのものではない（コンポーネント化・状態管理・実データ接続はこれから）。

## 経緯・位置づけ

[技術スタック](index.md)で決着した「まず閲覧サイト→後にセッション管理システム」という段階分けのうち、閲覧サイト（用語集・グラフの閲覧体験）の試作から着手した。その後ユーザーの依頼で、本来は後続フェーズのはずのセッション管理系UI（プレイ画面・GM承認・戦闘画面など）もデザイン探索として先行して試作することになり、結果的に全15画面まで広がった。**フェーズ分けの方針自体は変更していない** — ここでの試作はあくまで見た目・UI構造の検証であり、実装の着手順は改めて技術スタックの方針に従う。

すべてGitHub Pages上で公開中（`https://hibohiboo.github.io/CarTaGraphFantasy/preview/<ファイル名>`）。VitePressの`public/`ディレクトリにそのまま置いた生のHTMLで、サイドバーの「試作」セクションから辿れる。

## デザインシステム

### カラートークン（全画面共通）

```css
--felt: #1f2a24;        /* 卓上フェルト地（背景） */
--felt-panel: #24322b;  /* パネル背景 */
--felt-panel-2: #1a241e;/* さらに暗いパネル/伏せ札の地 */
--card: #efe7d8;        /* カード地（生成り紙） */
--ink: #2b241c;          /* カード上の文字 */
--ink-soft: #55493a;     /* カード上の副次テキスト */
--parchment-text: #ddd3bf;     /* 卓上の文字 */
--parchment-text-dim: #a99f8c; /* 卓上の副次テキスト */
--seal: #a33227;    /* 朱印・GM系の強調色 */
--thread: #b8935a;  /* 金糸＝グラフ/場のエッジ、装飾線 */
--focus: #d9b877;   /* フォーカスリング・強調枠 */
```

役割バッジは色で統一：ドライバー＝金（`--role-driver`）／ナビゲーター＝スレード（`--role-navigator`）／GM＝朱（`--role-gm`）／戦闘の敵＝朱（`--role-enemy`）。状態セマンティック色は`--pending`（承認待ち・黄）／`--approved`（緑）／`--rejected`（赤）／`--neutral`（灰）で、アクセントの金とは役割を分離している。

### タイポグラフィ

- 見出し・カード名：Zen Old Mincho（明朝、Google Fonts）
- 本文・UI：Zen Kaku Gothic New（ゴシック、Google Fonts）

### カードの縦横比

**5:7（≒白銀比 1:1.4）に統一**。CSSでは`aspect-ratio: 5 / 7`。法隆寺五重塔などに使われる「大和比」と呼ばれる日本の伝統的な比率で、かつポーカー/MTG等の実物トレーディングカード規格ともほぼ一致する。用語集カード・手札・場のカード・ロケーションカード・カードプール等、「単一のゲーム内カードを表す」要素はすべてこの比率。GM承認のチケットや募集カードなど「複数の情報を束ねたUI部品」は意図的に対象外（別のコンポーネント系統として扱う）。

### カードの視覚言語

- **朱印スタンプ**（丸・朱色・「決」の字）＝ `docs/open-questions.md` の「決着」ステータスをそのまま図像化したもの（図鑑ページのみ）
- **伏せ札**（`repeating-linear-gradient`の斜線パターン、暗い地）＝ 内容不明・秘匿情報。存在は見えるが中身が分からない状態（card-face-back.mdの「ゾーンで隠す/裏表で隠す」の後者に相当）
- **ゾーンピル**（GM専用／PL可視の小さな角丸ラベル）＝ card-face-back.mdの「場のゾーン構造」をそのままUIラベル化
- **カード画像＋アイコンフォールバック**（`.card-portrait`）＝ 背景画像があればそれを表示、無ければ人型シルエットのSVGアイコン（金線画）にフォールバック。character-create.htmlとscene-builder.html/scene-play.htmlに実装例あり

### 確立したUIパターン

- **CSSのみのタブ切り替え**：隠しradioボタン＋`:checked`＋兄弟結合子（`~`）で、JS無しで表示を切り替える。session-play.html初期版の「場/手札」タブ、combat-play.html系の「パーティー他メンバーの手札に切り替え」で使用
- **1画面完結レイアウト**（プレイ画面・戦闘画面）：`body { height: 100dvh; overflow-y: auto; display: flex; flex-direction: column; }` とし、可変の中央コンテンツは `flex: 1 1 auto; min-height: 0`。ナビ・HUDは**折り返さず横スクロール**（`flex-wrap: nowrap; overflow-x: auto`）に統一 — 折り返すとスマホ幅で縦方向の予算を圧迫し表示が崩れるため（実際に発生した不具合）
- **プレイマット式の奥行き表現**：GMが用意するもの（シーン・場に出たカード）を上（奥）、PLが操作するもの（選択肢・パーティー）を下（手前）に配置する縦積みレイアウト

## 未解決・要検討事項（grilling候補）

React実装の詳細設計に入る前に詰めた方がよい項目。`docs/open-questions.md`の「次に詰める候補」にも記載済み。

1. **シーンカードの「目的」「終了条件」**（scene-builder.html / scene-play.htmlで試作） — 既存の選択肢カード＝イベントカードの3要素構造（発火条件・効果・GM向け補足）には無い、新しい属性。持たせる場合、既存構造や[セッションの終了条件](../cartagraph/party-and-session.md#非同期セッションの進行決着)と役割が重複しないか要確認
2. **キャラクター作成時の体・技・心の初期配分方法** — [探索者向けの判定ルール](../cartagraph/exploration-check.md)は能力値の使い道は決着しているが、配分方法（ポイント制／固定／CPとの連動有無）は未検討
3. **敵のHP・能力の非公開ルール**（combat-play.html系） — 現状の試作は「基本的に見せない」想定で敵HPバーを非表示にしたが、「看破」等のスキルで開示する仕組みは正式には未設計

## Reactへ引き継ぐ際の推奨事項

- **トークンの移植** — 上記CSS変数はそのままCSS-in-JSやCSS Modulesのテーマ変数に移せる。色・比率(5:7)・フォント指定は既に検証済みなので流用してよい
- **コンポーネント分割の単位（試作から見える境界）**
  - `Card`（5:7比率、`.card-portrait`込み。種類バリアント: 用語/場/手札/ロケーション/プール）
  - `HandDock`（横スクロールの手札列）
  - `Hud` / `ProtoNav`（横スクロール1行の固定ヘッダー）
  - `TurnChips`（行動順表示、クリックで表示中PC切り替え）
  - `MatZone` / `PlayMat`（奥行き順の簡易俯瞰）
  - `ZonePill`・`RoleBadge`・`StatusPill`（状態表示の小部品）
- **実データモデルが必要な箇所** — 試作は`docs/cartagraph/`の用語・ルールを手作業で当てはめたダミーデータ（シナリオ「灰色館の一夜」「鉄鎖のガレオン船」「灰塔の遺跡」、PC「迅」「灯」「彰」「澪」等）。React実装では、カード・デッキ・場・ゾーンの実データ構造（[カード・デッキの考え方](../cartagraph/card-and-deck.md)、[場・手札・プレイ](../cartagraph/play-and-field.md)）に沿ったスキーマ設計が別途必要
- **モバイル対応の教訓** — ナビ/HUDの横スクロール化、`100dvh`+`overflow-y:auto`のフォールバックは、実装時も同じ理由（固定高さ内での折り返しによる崩れ）で有効なパターンとして踏襲してよい
- **VitePressのSPAルーター干渉** — 参考情報。今回はVitePressの`public/`に生HTMLを置く都合上、サイドバーリンクに`target: '_self'`が必要だった。Reactアプリとして独立させれば発生しない問題
