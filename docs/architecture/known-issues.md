# 既知の問題

実装で見つかった不具合や、レビューで見送った課題（P2 など）を、直すまでの間ここに置く。

- **ここに置くもの** — アプリ・テスト・ドキュメントの実装上の問題。ゲームの仕様として決まっていない論点は[未解決論点トラッカー](../open-questions.md)に、開発プロセスの改善候補は[体制の進化ログ](../process/evolution.md)に置く
- **足すとき** — 1件ごとに「何が起きるか」「どこで見つかったか」「直すときの目安」を書く。[レビュールール](../process/rules/review.md)で「TODO 化」と決めた指摘も、ここに書く
- **直したとき** — その項目を消す（経緯は git の履歴とプランに残る）。直す作業のプランには、ここから項目を引用する

## 画面

### 自動戦闘の設定中に、プレイ画面のレイアウトが崩れる

- **起きること** — 自動戦闘のシーン（村スタートの冒険者試験）で、「戦い方を決める」パネルの上に、卓上の描写（GMの台詞カード）が重なって表示される。本来は台詞カードの下に出る案内文（「戦い方を決めて、戦闘を始めよう。」）も、台詞カードの横に出る
- **見つけた経緯** — 2026-09-27、PR #6（C2）の人間レビューで、ブラウザで確認して発見
- **原因の見立て（未調査）** — プレイ画面は HUD・卓・手札を1画面に収める縦並びのレイアウト（[試作の引き継ぎ](prototype-handover.md)「1画面完結レイアウト」）。自動戦闘のときだけ、手札の代わりに高さのある `AutoCombatPanel` が入り、1画面に収まらずに卓と重なっていると思われる
- **直すときの目安** — パネルを下からのシートに出す、またはこの状態の画面だけスクロールできるようにする。E2E か目視で崩れないことを確かめる

### 自動戦闘の全挑戦の記録を見る画面が無い

- **起きること** — 全挑戦の経過は `Session.combatHistory` に残るが、画面に出るのは直前の挑戦（`autoCombat.lastResult`）だけ。結末へ進むと、それも見えなくなる
- **見つけた経緯** — C2 の実装レビュー（`docs/plans/2026-09-23-自動戦闘エンジン.md`）
- **直すときの目安** — セッションのログ（feed）か、キャラクターシートから挑戦の一覧を開けるようにする

### GM不在でないセッションで、「GMの描写を待っている」が GM の台詞として出る

- **起きること** — 卓上の描写はすべて「GM」の台詞カードで出すため、人間GMのセッションで簡易スクリプトの無い選択肢を選ぶと、「『〇〇』を選んだ。GMの描写を待っている。」が GM の台詞になり、GM 自身が GM を待っている形になる。行動カードの「〇〇は『斬撃』を使った。」も同じ
- **見つけた経緯** — PR #6 の導入体験の修正のレビュー
- **直すときの目安** — 待ち状態の文言を、台詞カードではなく案内文（ヒント）に出す

## データ・API（MSW）

### 提案の採用・却下で、GM 本人かを確かめていない

- **起きること** — `/proposals/:pid/approve`・`reject` は、セッションの GM が自分かを確かめない。GM が採用で移り先を付けられるようになったので、GM 不在のセッションでドライバーが自分の提案を採用し、結末へ移るカードを作れてしまう（モックは利用者が1人なので、いまは起きない）
- **見つけた経緯** — 2026-10-04、GM 不在の募集の実装後の異常系レビュー（確かめていないのは main から）
- **直すときの目安** — 認証を作るときに直す（2026-10-05、人間の判断）。GM だけが裁定できるようにし、GM でなければ 403 にする（`/narrate` と同じ）。既存のテスト（`ss-mansion` の GM は霧乃）が採用を API で呼んでいるので、あわせて直す

### 中断中のプレイ画面に、GM の裁定が自動では届かない

- **起きること** — プレイ画面はセッションを定期的には取り直さない。PL と GM が別の人だと、GM が裁定しても、PL は画面を開き直すまで「続きを遊ぶ」が出ない（モックは同じタブでキャッシュが更新されるので見えている）。2026-10-05、人間レビューの要望で、ホームの「いま進んでいること」に「中断中：再開できます」を出すようにした（開き直せば分かる）
- **見つけた経緯** — 2026-10-04、GM 不在の募集の実装後の異常系レビュー
- **直すときの目安** — 中断中だけ、セッションの取得に `refetchInterval` を付ける。バックエンドで GM と PL が別の人になるとき（backend-1on1）に

### セッションが PC とシナリオをコピーせず参照している（スナップショット未実装）

- **起きること** — 仕様では、セッション開始時に参加 PC のデータとシナリオの必要な範囲をコピーして持ち出す（`scenario-flow.md`「セッション開始までの全体フロー」6、`graph.md`「セッションスナップショットとマージ」）。MSW のセッションは PC を `db.characters` から直接参照し、シナリオもシーンを移るたびに引き直している。開始後にシナリオを直すと、進行中のセッションも変わる（2026-10-06 から、公開中のシナリオの保存は開発サーバーでは `scenarios/*.json` にも残る）
- **見つけた経緯** — 2026-10-03、募集からのセッション開始のプランレビュー（仕様整合性）。ソロ開始の頃から続いている
- **直すときの目安** — セッション終了後の結果の反映（下の結末タグの件）や、バックエンドでセッションを保存するとき

### GM不在でないセッションで、結末タグが PC に反映されない

- **起きること** — 結末タグを PC へ反映する処理は、GM不在のソロの即時反映（`solo-village.md`）しか無い。人間GMのセッションでは、セッション終了後に所有者が選んで反映する画面（`party-and-session.md`）が未実装のため、結末タグが付かない
- **見つけた経緯** — 2026-09-27、C4 のプランレビュー
- **直すときの目安** — セッション終了後の結果の反映画面を作るとき


### GM不在のソロで、カードを選んだ直後に「選べる／選べない」の表示が一瞬古くなる

- **起きること** — プレイ画面は、セッションはプレイの応答で即座に更新するが、キャラクターは取り直すので少し遅れる。その間は新しい手札を古いデッキで判定する。たとえば最後の引換カードで斬撃を習った直後、残りの「〇〇を習う」が一瞬選べる表示になり、押すと 422 のエラーが出る。キャラクターの取得に失敗したときも、判定をせず全部選べる表示になり、失敗したことが画面に出ない
- **見つけた経緯** — 2026-09-27、C3（村パート）の実装レビュー（異常系）
- **直すときの目安** — プレイの応答にキャラクターも含めてキャッシュへ直接入れるか、取り直している間は条件付きのカードを選べなくする。取得の失敗は ErrorNote で出す


### 同じ自動戦闘のシーンに戻ると、敵カードが場に増える

- **起きること** — 自動戦闘のシーンに入るたびに、シナリオの定義から敵カードを新しくコピーして場に置く。一度出たシーンに戻ると、前回の敵（勝っていれば「戦闘不能」付き）が場に残ったまま2枚目が加わり、挑戦回数も0から数え直しになる
- **見つけた経緯** — C2 の実装レビュー
- **いまは起きない理由** — 村スタートのシナリオでは、試験へ進むと結末まで一本道で、試験に戻る選択肢が無い（街道からも村へは戻れない）
- **直すときの目安** — シーンを移るときに場のカードをどう片付けるかは仕様に無い。C3（村パート）では村のシーンに敵が出ず、試験へ戻る選択肢も無いため見送った。自動戦闘のシーンを行き来できるシナリオを作るときに仕様を決めてから直す

### 手札に配る選択肢カードが、シナリオ定義のオブジェクトをそのまま参照している

- **起きること** — ソロ開始・シーン遷移・勝利時に配る選択肢カードは、`db.scenarios` 内のカードオブジェクトそのもの。いまは手札のカードを書き換える処理が無いので実害は無いが、将来カードのタグなどを書き換えると、シナリオ側にも波及する
- **見つけた経緯** — C2 の実装レビュー
- **追記（2026-10-07）** — シナリオの公開の C2 で、製作者が画面で移り先を付け替え、シーンを消せるようになった。進行中のセッションの手札には古い移り先が残るので、移り先を付け替えてから古いシーンを消す、または結末を消して結末のノードも消えると、そのセッションでその選択肢を選んだときに 422 になる（上の「スナップショット未実装」と同じ種類の問題）
- **直すときの目安** — 敵カードと同じく、配るときに複製する

### GM不在の選択肢の描写で、境界の扱いが甘い

- **起きること** — 選んだカードを手札から消すときに ID で絞り込むので、同じ ID のカードが手札に複数あると全部消える。カードの説明文が空文字だと、定型文に切り替わらず空の描写になる
- **いまは起きない理由** — 提案から生まれるカードの ID は一意で、説明文が空文字のカードも無い
- **見つけた経緯** — PR #6 の導入体験の修正のレビュー
- **直すときの目安** — 選んだ1枚だけを消す、空文字も定型文にする

### GM不在のソロの成長の効果・使える条件は、選択肢カードでしか画面と揃っていない

- **起きること** — サーバー（`/play`）は種類を問わず使える条件と成長の効果を扱うが、画面が選べない理由を出すのは選択肢カードだけ。また、成長の効果の描写（「体が1上がった」など）は、次のシーンへ進むカードと、描写する人のいない選択肢カードでしか描写に入らず、簡易スクリプトを持つカードや選択肢以外のカードでは feed にだけ残る
- **いまは起きない理由** — 使える条件・成長の効果を持つカードは、村パートの選択肢カードだけ
- **見つけた経緯** — 2026-09-27、C3（村パート）の実装レビュー（異常系）
- **直すときの目安** — 選択肢以外のカードにも条件・効果を持たせるときに、画面の判定と描写の分岐をそろえる

### 「提案の扱い」がGM必須のシナリオを、GM不在で始められてしまう

- **起きること** — `POST /api/scenarios/:id/start-solo` はシナリオの提案の扱い（GM必須／提案不可／自動解決）を確かめない。GM必須のシナリオをソロで始めると、提案が裁定待ちのまま残る
- **いまは起きない理由** — ソロで始められる導線は、自動解決・提案不可のシナリオにしか無い
- **見つけた経緯** — PR #6 の導入体験の修正のレビュー
- **直すときの目安** — GM必須のシナリオは start-solo を 422 にする

## テスト

### 自動戦闘のテストに、fixtures の値の書き写しがある

- **起きること** — `apps/web/src/test/AutoCombat.test.tsx` の `PREFIX`（シナリオIDとノードIDの接頭辞の対応）は、`mocks/fixtures.ts` の値（テスト専用の試験シナリオ `sc-exam-*`）をテストに書き写している。[テストルール](../process/rules/testing.md)の「独自のマジック値を作らない」に反する（2026-10-03 確認：遊べるシナリオは `scenarios/*.json` に移ったが、ここで書き写しているのは fixtures に残るテスト専用シナリオの値）
- **見つけた経緯** — C2 の異常系レビュー
- **追記（2026-10-10）** — 一緒に挙げていた初期装備の HP20・行動値10 の書き写しは、冒険者だけにする C3 で HP・行動値の出どころが `rules/character-creation.json` になり、テストもそこから引くようにしたので片づいた
- **直すときの目安** — fixtures から試験シナリオの接頭辞を export して参照する

### テスト専用のシナリオが、本番のシナリオ一覧のデータに入っている

- **起きること** — `sc-exam-always-win` などのテスト専用シナリオ（C1 の `sc-village-no-propose` も同じ）が、`fixtures.ts` の `scenarios` 配列に、遊べるシナリオと一緒に入っている。draft・システム作成なので一覧 API には出ない（2026-10-03、`scenarioFiles.test.ts` で公開済みの一覧に出ないことを確かめた）。GM・シナリオ製作者のシナリオ一覧画面に出ないかは確かめていない
- **追記（2026-10-03）** — 遊べるシナリオは `scenarios/*.json` に分かれた。テスト専用シナリオは引き続き `fixtures.ts` にあり、同じ `scenarios` 配列に入る（MSW のメモリ上の DB は1つのため）
- **見つけた経緯** — C2 の異常系レビュー
- **追記（2026-09-27、C3）** — テスト専用セッション `ss-village-human-gm`（人間GMで村のシナリオを遊ぶ、自分が参加していないセッション）を足したところ、GMのセッション一覧の「参加者として関わっているセッション」に出るようになった。この一覧は、GMが自分でないセッションを参加の有無を見ずにすべて出しているため
- **追記（2026-10-06）** — シーン編集のテストのために、製作者が自分のテスト専用 `sc-mansion-mine`（灰色館の写し）を足した。製作者が自分なので、デモ・開発サーバーの「自分のシナリオ」の一覧に「（テスト用）自分の灰色館」として出る。カード画像の localStorage のキーはカードの id だけなので、写しで画像を付けると、同じ id の灰色館のカードにも出る
- **直すときの目安** — 一覧画面で出ないことを確かめるテストを足すか、テスト専用のデータを分ける

### 灰色館の一夜の選択肢カードが、シナリオの JSON と fixtures に重複している

- **起きること** — 灰色館の一夜の選択肢カード（`ch-open`・`ch-inspect`・`ch-back`）が、`scenarios/sc-gray-mansion.json` と、`fixtures.ts` のセッション `ss-mansion` の手札（`openDoor` などの定数）の両方にある。片方だけ直すと食い違う
- **見つけた経緯** — 2026-10-03、シナリオの JSON 管理のプランとプランレビュー（`docs/plans/2026-10-03-シナリオのJSON管理.md`「重複の記録」）。そのとき一緒に挙がった、お店で習う戦闘スキルと試験官の重複は、2026-10-10 に[ルールとカードプールの JSON 化](../backlog/rules-json.md)で解いた（戦闘スキルは `rules/cards.json` を id で指し、試験官は fixtures が JSON から読む）
- **いまの手当て** — `apps/web/src/test/scenarioFiles.test.ts` が一致することを確かめている（片方だけ直すとテストが落ちる）
- **直すときの目安** — セッションの手札を JSON から引く（村のテスト用セッションの `villageCards()` と同じ形）

### シナリオでしか得られないカードを、仮にシステムのカード一覧に置いている

- **起きること** — 次のカードは基本カードプールに入らず、特定のシナリオでしか得られないが、`rules/cards.json`（システムのカード一覧）に置いている
  - 「航海の心得」「炎の剣」：鉄鎖のガレオン船の報酬カード（デモのプレイヤーの解放済みプールに入っている）。仕様では報酬カードは「シナリオがあらかじめ用意した特定のカード」（[成長とキャラメイク](../cartagraph/character-growth.md)）。シナリオに報酬の定義が無いので、仮にここへ置いた
  - 「素早い突き」：村はずれの一歩のお店でしか習えない戦闘スキル。シナリオで生まれたカードを他のシナリオでも使えるようにするのは[共有設定](../glossary.md#共有設定)への格上げ（[グラフの役割](../cartagraph/graph.md#正史グラフの共有設定への格上げ)）だが、その手続きを経ずにシステムの側に置いている
- **見つけた経緯** — 2026-10-10、ルールとカードプールの JSON 化のプランレビューと実装レビュー（`docs/plans/2026-10-10-ルールとカードプールのJSON管理.md` D5）
- **直すときの目安** — シナリオに報酬カードの定義（結末で得るカード）を作るときに、報酬カードをシナリオの JSON へ移す。お店のスキルは、シナリオ固有のカードとして持つか、共有設定に格上げするかを決める

### 画面からの公開の口に、システムのカードの参照の検査が無い

- **起きること** — シナリオの読み込み時には、成長の効果の `gainCardIds` がシステムのカード一覧に実在するか、シナリオ固有のカードの id がシステムのカードとぶつからないかを確かめる（`findSystemCardRefErrors`）。画面からの公開・保存で JSON に書く前の検査（`safeParseScenarioFile`）はこれを見ない。画面からは `gainCardIds` を編集できず、カードの id も重ならない形で作る（`CreatorSceneEditPage`）ので普段は起きないが、API（`PATCH /api/scenarios/:id`）を直接呼んで壊れた `gainCardIds` や `c-slash` のような id のカードを送ると、開発サーバーではファイルに書かれ、次の読み込みでアプリ全体が止まる
- **見つけた経緯** — 2026-10-10、ルールとカードプールの JSON 化のプランレビュー（スコープ外とした）
- **直すときの目安** — 書き込む前の検査にも `findSystemCardRefErrors` をかける（開発サーバーの書き込みの口は `@cartagraph/domain` を静的に import できないので、MSW 側でかける）

### キャラクターの作成の API が、存在しないカードの id を黙って捨てる

- **起きること** — `POST /api/characters` は、存在しないカードの id を黙って捨てて作る（`PATCH` は 422）
- **追記（2026-10-10、冒険者だけにする C3 の実装レビュー（異常系））** — 以前から、`POST /api/characters` と `POST /api/scenarios/:id/start-solo` は本文の形を見ずに `name.trim()`・`cardIds` を使うので、本文が `null`・`cardIds` が無い・`name` が文字列でないと 500 になる（能力値の形は C3 で検査するようにした。`PATCH /api/characters/:id` も本文がオブジェクトでなければ 422 にした）。直すときは、本文を zod などで検査してから使う
- **見つけた経緯** — 2026-10-10、ルールとカードプールの JSON 化の実装レビュー（異常系）。プランでスコープ外とした。同じとき見つけた「能力値をルールで検査しない」は、冒険者だけにする C3 で直した（`POST` は能力値を `abilitiesValid` で検査し、`PATCH` は能力値・HP・行動値を受け付けない）
- **直すときの目安** — `POST` の存在しない id を `PATCH` に合わせて 422 にする

### 灰色館の一夜のカードの効果が、コード（handlers.ts）にある

- **起きること** — 灰色館の一夜の「開ける」「調べる」「戻る」を選んだときの卓上の変化（描写・追加の選択肢・表にするカード）は、`apps/web/src/mocks/handlers.ts` の `playScript` にカード id をキーにして書いてある。シナリオの JSON だけでは、このシナリオの中身がそろわない
- **見つけた経緯** — 2026-10-03、シナリオの JSON 管理の grilling（D6。今回は動かさないと決めた）
- **いまの手当て** — `scenarioFiles.test.ts` が、`playScript` のキーが灰色館の JSON に実在することを確かめている
- **直すときの目安** — カードの効果（描写・選択肢の追加・表にする）を仕様（`play-and-field.md`）とドメインの型に足し、JSON に移す。GM 必須のシナリオなので、GM の裁定との関係も決める

### シナリオの JSON の検査が、数値の範囲と結末・導入の構造を見ていない

- **起きること** — `scenarioSchema` は型（数値か・文字列か）と列挙だけを見る。`maxRounds: 0`・ダイスの `count: 0`・敵の `hp: -1`・`partySize` の `min > max` のような値も読み込みを通り、自動戦闘を始めたときに初めて 422 になる。`findScenarioRefErrors` も、`kind: 'ending'` なのに `endingId` が無いノード、どのノードからも指されない `endings`、`intro` が0枚・2枚以上のシナリオを止めない（灰色館・ガレオン・後日談の結末のノードは、いまも `endingId` を持たない）
- **見つけた経緯** — 2026-10-03、シナリオの JSON 管理の実装レビュー（異常系）
- **いまの手当て** — 村はずれの一歩は、画面から結末まで通すテスト（`VillagePart.test.tsx`）が守っている
- **追記（2026-10-06）** — [シナリオの公開](../backlog/scenario-publish.md)の C1 で、画面から公開すると `scenarios/*.json` に書くようになった。書き込む前の検査はこの検査のまま強めないと決めた（`docs/plans/2026-10-06-シナリオ公開のJSON書き込み.md` D3）。画面から作った不自然な数値のシナリオも書き込まれる
- **追記（2026-10-07）** — シナリオの公開の C2 で、シナリオ編集の「結末を削除」で結末と結末のノードを対で消せるようになった。結末を全部消すと結末のノードが無くなり、GM 不在のセッションが終われないシナリオも画面から作って公開できる（`docs/plans/2026-10-07-選択肢の移り先と結末の編集.md`）
- **直すときの目安** — 数値に `int()`・`positive()` などの範囲を付け、GM 不在のシナリオに限って結末・導入の構造を検査する

### シナリオ・ルールの JSON が1本でも壊れていると、アプリが起動しない

- **起きること** — `scenarios/*.json` と `rules/*.json` は MSW の起動時（モジュールの読み込み時）に検査するので、1本でも誤り（形、シナリオの中の参照、シナリオからシステムのカード一覧への参照を含む）があると、アプリ全体が真っ白になる。誤りはブラウザのコンソールにだけ出る
- **見つけた経緯** — 2026-10-03、シナリオの JSON 管理の実装レビュー（異常系）
- **いまの手当て** — pre-push と CI の `pnpm web:test` で止まるので、壊れた JSON は main に入らない
- **追記（2026-10-06）** — 画面からの公開で書くときは、書く前に同じ検査（`safeParseScenarioFile`）を MSW と開発サーバーの口の両方でかけるので、画面からは壊れた JSON を書かない。手で直した JSON は今までどおり
- **直すときの目安** — 1本ずつ失敗を分けて扱う（壊れた1本だけ外して起動し、画面に出す）かを決める

### 開発サーバーの書き込みの口の、時間切れまわりの取りこぼし

- **起きること** — (1) Biome の整形が10秒で返らず止めるとき、止まるのは Node の起動スクリプトだけで、Windows では Biome の本体が残ることがある。(2) ブラウザの保存先は15秒で諦めて 500 にするが、口の中の処理（初回の `ssrLoadModule`・本文の読み込み）には上限が無い。ブラウザが諦めた後に口が書き終えると、ファイルだけ書き換わり、メモリと食い違う。(3) 公開の操作を待つ間に別のシナリオへ移ると、そちらのボタンも「保存中…」になる
- **見つけた経緯** — 2026-10-07、シナリオの公開の実装の再レビュー（異常系）。どれもまれで、開発サーバーだけの話
- **直すときの目安** — 口の処理全体に上限を付ける。Biome は JS API（`@biomejs/js-api`）で整形して子プロセスをやめる。保存中の表示を対象のシナリオで絞る

### シナリオ編集で下書きを変えたまま「編集」へ移ると、下書きが消える

- **起きること** — シナリオ編集の「編集」（導入・シーン・結末のノード）はリンクで、下書き（保存していないデッキ・結末・メタデータの変更）があっても確認なしにシーン編集へ移り、戻ると下書きは消えている。保存していないノードにはリンクを出さない（2026-10-07）が、保存済みのノードのリンクは押せる
- **見つけた経緯** — 2026-10-07、シナリオの公開 C2 の実装の再レビュー（異常系）。前からの挙動
- **直すときの目安** — 下書きがあるときはリンクを押せなくする（「保存してから編集」）か、離れる前に確認を出す

### シーン編集で保存に失敗しても、カード画像だけ localStorage に残る

- **起きること** — シーン編集は、保存の API を呼ぶ前にカード画像を localStorage に書く。保存が失敗しても（製作者でない 403、公開中の検査の 422、書き込みの 500）画像は残り、リロードすると保存できなかったはずの画像がカードに出る
- **見つけた経緯** — 2026-10-07、シナリオの公開の実装レビュー（異常系）。元からの作りだが、公開で失敗する経路が増えた
- **直すときの目安** — 保存が成功してから画像を書く（画像を書けなかった誤りの出し方も合わせて直す）

### シナリオを非公開にしても、募集・セッションが残り、下書きからも募集を出せる

- **起きること** — 「非公開にする」はシナリオ集の一覧（`GET /api/scenarios`）から外すだけ。既にある募集（通常・GM 不在）とセッションは残り、PL のセッション一覧からも始められる。`POST /api/scenarios/:id/recruitments` などは公開状態を見ないので、GM のシナリオ詳細を URL で開けば、下書きのシナリオからも募集を出せる
- **見つけた経緯** — 2026-10-06、シナリオの公開のプランレビュー（仕様整合性）。今回は止めないと人間が決めた（`docs/plans/2026-10-06-シナリオ公開のJSON書き込み.md` D9）
- **直すときの目安** — 非公開にしたときに受付中の募集を締め切るか、下書きからの募集を 422 にするかを決める。ログインと権限を入れる backend-1on1 で一緒に見る
- **シナリオタイプとの関係**（2026-10-10、冒険者だけにする C2 の実装レビュー（異常系））— 下書きの保存はシナリオタイプと中身を検査しないので、「戦闘なし」の下書きに自動戦闘のシーンを足して URL から募集を出すと、セッション選択に「戦闘なし」と出るのに自動戦闘に入る。下書きの `PATCH /api/scenarios/:id` は本文の形も検査しないので、`scenarioType: null` を送ると編集画面が落ちる（ほかの項目も同じ作り）。下書きからの募集を止めるか、募集の作成でも `findScenarioTypeErrors` を見るかを、上と一緒に決める
