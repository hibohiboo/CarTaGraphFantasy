# 実装パターン

[境界づけられたコンテキスト](bounded-contexts.md)ごとに、業務ロジックのパターン・アーキテクチャのパターン・テストの形を決める。バックエンド（[ロードマップ](../roadmap.md#backend-1on1)の backend-1on1）で、保存の単位とモジュールを作るときの型にするため。ドメイン駆動設計の業務ロジックの実装パターン・アーキテクチャのパターン・設計判断の経験則にあたる。決めた理由・採らなかった案は[デザイナーノート](../notes/architecture/implementation-patterns.md)にある。

## パターンの意味

| 種類 | パターン | 意味 |
|---|---|---|
| 業務ロジック | ドメインモデル | 集約のいまの状態を保存する。不変条件は集約の操作（純粋関数）が守る |
| 業務ロジック | イベント履歴式ドメインモデル | 起きたことの列（イベント）を保存し、それを正とする。いまの状態は、列を頭から畳んで作る |
| 業務ロジック | 値オブジェクトと純粋関数 | 集約も保存も持たない。入力を受けて結果を返す計算だけ |
| アーキテクチャ | ポートとアダプター | 業務ロジック（`packages/domain`）を中心に置き、保存・API の口・イベントの配信を外側のアダプターにする |
| アーキテクチャ | CQRS | 書き込みのモデル（集約）と、読むためのモデル（読みモデル）を分ける |
| アーキテクチャ | モジュラーモノリス | 1つのバックエンドの中を、コンテキストごとのモジュールに分ける |

## コンテキストごとの選択

| コンテキスト | 業務ロジック | アーキテクチャ | テストの形 |
|---|---|---|---|
| プレイ | イベント履歴式ドメインモデル | ポートとアダプター＋CQRS | ピラミッド（判断を「イベント → コマンド → イベント」で確かめる） |
| シナリオ製作 | ドメインモデル | ポートとアダプター | ピラミッド |
| セッション運営 | ドメインモデル（簡素） | ポートとアダプター | ピラミッド |
| キャラクター | ドメインモデル（簡素） | ポートとアダプター | ピラミッド |
| 判定・戦闘 | 値オブジェクトと純粋関数 | 保存を持たないモジュール | 単体＋数値のシミュレーション |
| 利用者 | 外部サービスに任せる | 各コンテキストの側に腐敗防止層（[コンテキストマップ](bounded-contexts.md#コンテキストマップ)） | — |
| グラフ・ライブラリ、進化（将来） | 着手するときに決める | 同左 | 同左 |

## 全体：モジュラーモノリス

- **1つのバックエンドに、コンテキストごとのモジュール** — モジュールは自分の集約の保存先だけを読み書きする。ほかのモジュールの集約へは、公開した口かイベントで渡す（下の「連携の実装」）
- **業務ロジックは `packages/domain`** — どのモジュールも同じ純粋関数を使う。保存・イベントの配信・時刻・乱数はアダプターが受け持つ（[アーキテクチャルール](../process/rules/architecture.md)「副作用の分離」）。いまは MSW のハンドラ（`apps/web/src/mocks/handlers.ts`）がアダプターの代わりをしている
- **API の口は `packages/schemas`** — API の一覧が、モジュールの外へ公表する言葉になる

## プレイ：イベント履歴式

- **正はセッションスナップショットごとのイベントの列** — いまの状態（場・手札・いまのシーン・提案・自動戦闘の状態）は、列を頭から畳んで作る
- **操作は2つの純粋関数**
  - **判断** — いまの状態とコマンドを受け、起きるイベントの列か、断る理由を返す
  - **反映** — 状態とイベント1つを受け、次の状態を返す。判断はしない（断らない）
  - [集約の書き方の方針](aggregates.md#書き方の方針)の「新しい集約と、起きたイベントを返す」は、判断のあとに反映を畳んだものにあたる
- **イベントには結果を入れる** — ダイスの目・時刻・GM やドライバーが書いた文は、判断の外（アダプター）で決めて入力として渡し、イベントに残す。列から状態を作り直すときに、乱数を引き直さない
- **最初のイベント** — 「セッションを始めた」を受けて、版の指し先・持ち出した PC のコピー・参加者の役割を持つ最初のイベントで列を始める（[ドメインイベント](aggregates.md#ドメインイベント)）
- **イベントの一覧** — [イベントの流れ](event-flows.md)で、集約がセッションスナップショットのイベント
- **保存したイベントは書き換えない** — イベントの形を変えるときは、読むときに古い形を新しい形へ直す。破棄したセッションの列を消すかは、破棄を誰がいつ行うかと一緒に決める（[未解決論点](../open-questions.md#仕様の細部の未決)）
- **読みモデル（CQRS）** — イベントの列から作る。作り直せるので、列と食い違ったら作り直す

| 読みモデル | 見る人 |
|---|---|
| 場と手札・いまのシーン | ドライバー・ナビゲーター・GM（プレイ画面） |
| 語りの記録 | 参加者 |
| 裁定待ちの提案 | GM |
| セッションログ（将来） | 進化ループ（[EV-1](use-cases.md#ev-1-セッションログに印を付ける)） |
| 発見（将来） | グラフ（[GR-5](use-cases.md#グラフ将来)） |

## シナリオ製作・セッション運営・キャラクター：ドメインモデル

- **集約のいまの状態を保存する** — 操作は[集約の書き方の方針](aggregates.md#書き方の方針)のとおり、新しい集約と起きたイベントを返す純粋関数
- **シナリオ製作** — 版は作ったら変わらないので、版の並びがシナリオの履歴を兼ねる。下書きの編集の履歴は持たない
- **セッション運営・キャラクター（補完）** — [集約の一覧](aggregates.md#集約の一覧)の不変条件と、[ドメインイベント](aggregates.md#ドメインイベント)の送り受けだけを持たせ、それ以上の作り込みはしない

## 判定・戦闘：値オブジェクトと純粋関数

- 集約も保存も持たない。プレイと数値のシミュレーションから呼ばれる（[判定・戦闘はプレイから独立させる](bounded-contexts.md#コンテキストの一覧)）
- 乱数は呼ぶ側から渡す（いまの `autoCombat/resolve.ts` の形）

## 連携の実装

集約やコンテキストをまたぐイベント（[ドメインイベント](aggregates.md#ドメインイベント)）を、どう届けるか。

### 届け方：アウトボックス

- **保存と同じトランザクションで書く** — 集約を保存するのと同じトランザクションで、集約の外へ出すイベントを Neon のアウトボックスの表に書く。プレイは、イベントの列がアウトボックスを兼ねる
- **コミットしたらその場で配る** — 同じリクエストの中で受け取る側へ配る。配れなかったものは後から配り直す。GM 不在のセッションの即時反映（[即時反映](../cartagraph/solo-village.md#即時反映例外)）も、この「その場で配る」で行う
- **二重に届いても一度だけ反映する** — 少なくとも1回は届く（二重に届くことがある）ので、受け取る側はイベントの id で、同じイベントを二度反映しない
- **1つの集約から出たイベントは、出た順に配る**
- **受け取る側も、1回に変えるのは集約1つ** — 参加した PC が3人なら、キャラクターを3回変える
- **プロセスマネージャー（サーガ）は使わない** — どの流れも、受け取る側がそれぞれ反映するだけで、順番の決まりも取り消しも無いため

### イベントの種類

| イベント | 種類 | 中身 | 受け取る側 |
|---|---|---|---|
| セッションを始めた | ドメインイベント（状態の転送を兼ねる） | 版の指し先・参加者と役割・GM 不在か・外したシーン・提案の扱い・開始の時点の PC のデータ（キャラクターの公開する形） | セッション運営はセッションを作る。プレイは PC のデータを腐敗防止層で「PC のコピー」に変え、スナップショットの列の最初のイベントにする |
| セッションが終わった | ドメインイベント | 参加した PC・最後に入った結末の結末タグの情報（結末のノードに入らずに終わったら無し） | プレイは承認待ちの提案を閉じるイベントを列に足す。キャラクターは PC ごとに結末タグを付ける |
| ほかのイベント | ドメインイベント | 起きたことと、受け取る側が反映に要る値 | [ドメインイベント](aggregates.md#ドメインイベント)のとおり |

- **PC のデータは開始の操作が入れる** — 開始の操作が、そのときのキャラクターを読んでイベントに入れる。受け取る側が後から読みにいくと、その間に別のセッションの反映でキャラクターが変わりうるため
- **最後に入った結末はセッションが持つ** — セッション運営が「結末に達した」を受けて記録し、「セッションが終わった」に入れる。キャラクターはプレイの中を読まずに反映できる
- **結末タグを付けるのは「セッションが終わった」だけ** — GM 不在のセッションでも、「結末に達した」でセッションを終え、「セッションが終わった」で付ける

### 読むだけで済ませるもの

イベントで写さず、判断のときにアダプターがほかのモジュールの公開した口を読んで、判断（純粋関数）に入力として渡すもの。

- **セッションの状態（進行中・中断・終了）** — プレイのコマンドを受けたとき。「セッションを中断した」「再開した」はスナップショットの列に入れない。届くまでの間にプレイが進むことが無いため
- **PC が持つ結末タグ** — 募集への応募と開始のときの、再挑戦不可の検査

### ソロ開始

- 1回の操作で、「キャラクターを作る」と「その PC で公開版から始める」の2つのコマンドを順に実行する。それぞれが自分の集約だけを変え、「セッションを始めた」は運営の開始の操作が出す
- 2つ目が失敗しても、作った PC は取り消さない。PC はそれだけで正しく、その PC で始め直せる

## テストの形

- **どのコンテキストもピラミッド** — 土台は `packages/domain` のドメインテスト（[テストルール](../process/rules/testing.md)「種別と実行コマンド」）。画面のテスト・E2E はその上に少なく置く
- **プレイの判断** — それまでのイベント・コマンド・起きるはずのイベント（か断る理由）の3つで書く。反映と読みモデルは、イベントの列から作った状態を確かめる
- **判定・戦闘** — 境界値の単体テストと、数値のシミュレーション（[Webアプリの仕組み](web-app.md#自動戦闘の数値シミュレーション)）
- **保存（アダプター）の結合テスト** — バックエンドに着手するときに、テストルールに種別を足す

## いまのコードとの対応

いまはどのコンテキストも、状態をそのまま書き換えている。プレイの操作（`session/transition.ts`・`session/narrate.ts` など）は新しい `Session` を返し、イベントを返さない。セッションとセッションスナップショットに分けるときに、スナップショットをイベント履歴式にする（[既知の問題](known-issues.md#session-がセッション運営とプレイの両方を持っている)）。
