# デザイナーノート：Webアプリの仕組み

対応する仕様：[Webアプリの仕組み](../../architecture/web-app.md)

## バックエンドを作らずモックで画面を作った理由

セッション管理系の画面も含めて先に画面を作っているのは、モック（MSW）で体験を検証するため。[フェーズ分け](../../architecture/index.md#開発フェーズの段階分け決着)（まず閲覧サイト→後にセッション管理）の方針は変えていない。

## TanStack Query のキャッシュ設定を最小にしている理由

`QueryClient` は `retry: false, staleTime: 5_000` だけを設定している。実レイテンシ・更新頻度を測定できる材料がまだ無いため、データ種別ごとのキャッシュチューニングは実バックエンド接続後に実測してから見直す（[未解決論点](../../open-questions.md#開発の仕組み)）。

## API ドキュメントの Redoc を CDN から読む経緯

Redoc の本体は `cdn.redocly.com` から読む。`@redocly/cli` の `build-docs` は Redoc を同梱できないため、2026-10-11 に人間が受け入れた。

開くとブラウザのコンソールに React のハイドレーションの誤り（#418・#423）が出る。`@redocly/cli` 2.62.1 が作る HTML と CDN の Redoc の組み合わせで、最小の文書でも出ることを 2026-10-11 に確かめた（[既知の問題](../../architecture/known-issues.md#redoc-のハイドレーションの誤りがコンソールに出る)）。

## `vitepress preview` が 404 を返した件

`vitepress preview` は起動した後に dist に足したディレクトリを把握せず 404 のページを返す。2026-10-11、API ドキュメントのハイドレーションの誤りの切り分けで、測った「誤り0件」が 404 のページのものだったことがあった。それ以来、測る前にそのページが本当に返っているかを確かめる。
