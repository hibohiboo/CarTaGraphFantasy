# デザイナーノート：中核のユースケース

対応する定義：[中核のユースケース](../../architecture/use-cases.md)

## 書いた経緯

2026-10-16、[業務領域の分類](domain-map.md)・[境界づけられたコンテキスト](bounded-contexts.md)・[集約とドメインイベント](aggregates.md)に続けて、中核の業務領域ごとのユースケースを並べた。人間が「コアドメインのそれぞれのユースケースを作って理解を深めたい」と希望したため。仕様のページは仕組みの単位（場・手札・プレイ、シナリオの公開など）で分かれていて、利用者が何を成し遂げるかを通して読みにくかった。

## 画面の列を足した理由（2026-10-26）

要望・ユースケース・画面・テストのつながりを図にする（[テストレポート](../../architecture/test-report.md)「トレースの見方」）にあたり、ユースケースと画面のつながりがどこにも書かれていなかった。人間が、ユースケースの表に「画面」の列を足して書くことを選んだ（D4）。

- **列は中核の2つの表（シナリオ製作・プレイ）にだけ足す** — 将来の表（グラフ・進化ループ）は画面がまだ無く、列の形も違う（「起きること」「進化候補のステータス」）
- **画面は `routes.ts` のパスで書く** — まだ無い画面（GM のホーム）は導線図の点線のノードのラベル。パスの食い違いは `pnpm docs:build` が止める（`scripts/check-trace.mjs`）。画面が消えたときに表が黙って古くならないようにするため
- **ユースケースごとの画面の別置き（画面の側に UC を書く）は採らなかった** — 画面一覧は画面の役割の説明が主で、ユースケースの ID を書くと、どちらを直すか分からなくなる。つながりは目的の単位（ユースケース）の側に置く
- **画面の無いユースケース（ナビゲーターの助言）は `—`** — 列を空にせず、書き忘れと区別する

## 書き方を選んだ理由

- **1ユースケース＝1アクター・1回の操作・1つの集約** — 集約の「1回の変更で書き換えるのは1つの集約だけ」に合わせると、ほかの集約への反映がイベントとして見え、コンテキストマップの矢印と突き合わせられる
- **アクターに「システム」を入れる** — GM 不在のセッションでは、配る条件の判定・描写・自動解決をシステムが GM の代わりに行う。GM の欄に置き換わるものとして、アクターに数える
- **振る舞いの細部は書き写さない** — ユースケースは目的ごとの索引にとどめ、ルールの正は仕様のページに残す。書き写すと、仕様を直したときに古くなる
- **将来のコンテキストも書く** — グラフ・進化ループは未着手でも中核なので、仕様に決まっている範囲で書き、決まっていないところは未解決論点へリンクする
