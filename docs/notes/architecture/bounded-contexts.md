# デザイナーノート：境界づけられたコンテキスト

対応する定義：[境界づけられたコンテキスト](../../architecture/bounded-contexts.md)

## 決めた経緯

2026-10-16、[業務領域の分類](domain-map.md)に続けて決めた。AI が今の型（`CardDef`・`Session`・`Recruitment`・`Character`）を読み、同じ言葉がどこで違う意味になるかから叩き台を出し、人間が次の4点を決めた。

- **カードは共有カーネル** — 仕様の原則（どのカードも同じ構造）を守る。ただし、プレイ中の状態（表か裏か・ゾーン）は定義から外し、プレイの側に持たせる方向にする
- **判定・戦闘はプレイから独立させる** — 数値のシミュレーションをセッション抜きで回せる状態を、境界として守れるため（業務領域の分類で「シミュレーションできる状態は今後に役立つ」としたことを受けた）
- **ソロの村はプレイに含める** — GM 不在のプレイの進め方の一種。いまのコードも `session/` に依存している
- **成果物は文書だけ** — コードの組み替えは、バックエンドに着手するときなどに別のプランで判断する

## 採らなかった案

- **カードをコンテキストごとに別のモデルにする**（製作のカード・プレイのカード・キャラクターのカードを分けて変換する） — 仕様の原則「どのカードも同じ構造」を見直すことになる。プレイで生まれたカードが進化で正式なカードになる、という進化ループの考え方とも相性が悪い
- **カードを今のまま共有する**（プレイ中の状態も定義に持たせたまま） — 同じカードでもセッションごとに表裏・ゾーンが違うので、定義に置くと共有カーネルにプレイの都合が混ざる
- **判定・戦闘をプレイに含める** — シミュレーションがプレイのモデルに引きずられやすくなる
- **ソロの村をキャラクターに含める、または独立させる** — お店で買う・成長するのはキャラクターを育てる面もあるが、進み方は GM 不在のプレイそのもの

## コンテキストマップのパターンについて

上流・下流の関係のパターン（順応者・公表された言語など）は、本来はチームの間の力関係を表すもの。このプロジェクトは人間1人と AI で作っているので、チームの関係としてではなく、「どちらがどちらのモデルに合わせるか」と「何を受け渡すか」を表すために使っている。

2026-10-17、関係ごとのパターンを表の列として決めた（『ドメイン駆動設計をはじめよう』の手順の続き）。AI が叩き台を出し、人間が次の2点を決めた。残り（公開版・結末と成長・判定と戦闘・ロール）は叩き台のまま。

- **セッション運営とプレイはパートナーシップ** — 叩き台を作る中で、マップに運営 → プレイの矢印しか無いのに、プレイから運営へも「提案が出た」「提案を裁定した」「結末に達した」が流れていることに気づき、矢印を足した。両向きに流れ、中断・再開・終了の扱いはいつも一緒に変わるので、片方を上流にしない。顧客・供給者（運営を上流にし、プレイ → 運営の向きは運営が順応者）は採らなかった
- **持ち込む PC はプレイの側に腐敗防止層** — プレイはイベント履歴式（[実装パターン](../../architecture/implementation-patterns.md)）で、保存したイベントを書き換えない。キャラクターの型をそのままコピーすると、キャラクターの型を変えるたびに、古い形のイベントを読む変換がプレイの側に増える。開始のときに自分の「PC のコピー」の形に変えておけば、それが起きない。順応者は採らなかった

## 将来の候補

- **コードをコンテキストに合わせて組み替える** — `Session` をセッション運営の部分とプレイの部分に分けることは、[集約とドメインイベント](../../architecture/aggregates.md)で決めた。コードを組み替えるのは、バックエンドで保存の単位を作るとき
- **ドメインイベントをコードにする** — イベントの一覧は[集約とドメインイベント](../../architecture/aggregates.md#ドメインイベント)で決めた。GM 不在でないセッションの結果の反映（[既知の問題](../../architecture/known-issues.md#gm不在でないセッションで結末タグが-pc-に反映されない)）を直すときが、コードにする機会になる
