# デザイナーノート：業務領域の分類

対応する定義：[業務領域の分類](../../architecture/domain-map.md)

## 分類を始めた経緯

2026-10-16、プロジェクトをドメイン駆動設計の考え方で整理したいという人間の希望から、戦略的設計の最初の段階として業務領域を分けた。戦術的設計（集約・リポジトリなど）より先に戦略から入る。叩き台を AI が出し、迷う3点を人間が決めた。

## 人間が決めた3点

- **キャラクター作成・成長は補完** — いまはまだ補完。成長が進化ループにつながれば、中核に上がる候補になる
- **判定・自動戦闘は補完** — 遊べれば十分な部分。そのうえで、数値のシミュレーション（`pnpm sim:auto-combat`）を回せる状態を保つことは、今後のバランス調整や進化ループのためにも役立つので続ける
- **シナリオ製作とプレイは別の中核** — シナリオ → セッション → プレイの3段階なので、1つの中核（カードモデル）の両面としてまとめず、別々に扱う。間のセッション運営（募集〜開始）は補完

## 見直しのきっかけを置いた経緯

2026-10-17、ドメイン駆動設計の適用（11章）で、「分類は固定ではない」とだけ書いてあった所に、見直しのきっかけの表を足した。入れたのは、実装パターンのノートの将来の候補（キャラクターのイベント履歴式・「セッションの終わり」のプロセスマネージャー・途中の状態のキャッシュ）の、いつ見直すかの条件。条件が起きるまでは変えないので、表は「起きたら考え直す」の目印にとどめ、先回りの作り込みはしない。
