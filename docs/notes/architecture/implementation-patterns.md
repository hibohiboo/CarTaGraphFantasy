# デザイナーノート：実装パターン

対応する定義：[実装パターン](../../architecture/implementation-patterns.md)

## 決めた経緯

2026-10-17、『ドメイン駆動設計をはじめよう』の手順を続けて当てはめる中で、[イベントの流れ](event-flows.md)に続けて決めた。AI が本の経験則（業務領域の分類と、いま・将来に要るもので業務ロジックのパターンを選び、そこからアーキテクチャとテストの形を導く）で叩き台を出し、人間が次の2点を決めた。

- **プレイはイベント履歴式** — 語りの記録・セッションログ（進化ループの入力）・正常終了のときだけ行う発見のマージ（GR-5）・「今回は使われなかった」の判定は、どれも「何がどの順で起きたか」から組み立てるものなので、起きたことの列を正にする。判断に使う前に、[イベントの流れ](../../architecture/event-flows.md)のプレイ側のイベントで、セッションの始まりから終わりまでを列にできることを確かめた（このとき、カードを明かすイベントが抜けていたので足した）
- **セッション運営とキャラクターは簡素なドメインモデル** — [集約の書き方の方針](../../architecture/aggregates.md#書き方の方針)（純粋関数が新しい集約とイベントを返す）と、Functional Core / Imperative Shell のルールにそのまま揃う。補完の業務領域なので作り込まない

シナリオ製作（ドメインモデル）・判定・戦闘（いまのまま）・全体のモジュラーモノリスは、叩き台のまま異論が無かった。

テストの形は[テストルール](../../process/rules/testing.md)と食い違わないことを確かめた（どれも「ドメイン：純粋関数の判定・変換」に収まる）。保存の結合テストだけは、いまのテストルールに種別が無いので、バックエンドに着手するときに足す。

## 採らなかった案

- **プレイを、状態の保存＋追記だけの記録にする** — いまのコードに近いが、状態と記録の2つが正になり、食い違っても気づけない
- **プレイを、状態だけのドメインモデルにする** — いまのまま。セッションログと発見のマージのために、あとで別に記録を足すことになる
- **セッション運営・キャラクターをアクティブレコードにする** — 簡単だが、検査がハンドラ（サービスの層）に散り、イベントを返す形と、Functional Core のルールから外れる
- **シナリオの下書きもイベント履歴式にする** — 公開した版が作ったら変わらないので、版の並びで履歴は足りる。下書きの編集の履歴を使う仕様が無い
- **すべてのコンテキストで CQRS** — 読みモデルを分ける理由（イベントの列から画面の形を作る）があるのはプレイだけ
- **マイクロサービス** — 1人＋AI の規模では、配備と連携の手間に見合わない
- **層状のアーキテクチャ** — ドメインモデルを選んだコンテキストでは、業務ロジックが保存の層に引きずられないポートとアダプターのほうが、`packages/domain` を外側から切り離すいまの形と揃う

## 気をつけること

- **イベントの形の変更** — 保存したイベントは書き換えないので、形を変えるたびに、古い形を読む変換が増える。イベントには結果だけを入れ、画面の都合（表示の文言など）を入れない
- **破棄** — 「破棄したセッションは何も残さない」（[グラフの役割](../../cartagraph/graph.md#セッションスナップショットとマージ)）と「イベントは書き換えない」の関係は、破棄の仕様が決まるまで決めない
- **長いセッション** — 毎回列を頭から畳むと重くなる。重くなってから考える（下の将来の候補）

## 将来の候補

- **途中の状態のキャッシュ** — 列の途中までを畳んだ状態を保存し、そこから畳む。長いセッションで重くなったら
- **キャラクターのイベント履歴式** — キャラクターの成長が進化ループにつながり、成長の経緯を読む仕様ができたら（見直しのきっかけは[業務領域の分類](../../architecture/domain-map.md)に置く予定）
