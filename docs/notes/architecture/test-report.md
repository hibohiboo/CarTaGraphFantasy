# デザイナーノート：テストレポート

対応する定義：[テストレポート](../../architecture/test-report.md)

## 書いた経緯（トレースのページ、2026-10-26）

人間の要望（[アイデアから実装までをたどれるようにする](../../backlog/trace-report.md)）。RDRA とドメイン駆動設計を合わせて、アイデアから実装まで一貫して見られる図で開発を管理したい。目的は、アイデアが実装・テストまで届いているかを見ること。ユースケースごとの結果のページ・ルールの節ごとの結果のページは、それぞれ1つの層の結果しか見せず、要望から先をたどれなかった。

## 決めた理由

- **要望からのつながりは、要望ファイルの `trace` に書く（D1）** — 要望ごとに「どこで確かめるか」を決めるのは要望を書く人。ユースケースの表に要望の列を足すと、要望が増えるたびに表が横に伸びる。要望の先頭に書けば、要望を開けばつながりが読める
- **要望は画面・ルールの節にも直接つなげる（D2）** — 画面の要望（PL のホームなど）やルールの要望は、ユースケースを持たない。ユースケースだけにつなぐと、そうした要望の届き具合が見えなくなる
- **状態は最新のテストの結果まで出す（D3）** — つながりだけでは「書いてある」ことしか分からない。デプロイがテストを流した後に組み立てる（usecase-report・rule-test-report と同じ）。仕様書サイト（VitePress）の中のページにはしない（結果が要るので、ビルド後のスクリプトで作る）
- **図は層ごとの列に並べ、押した要素の上流・下流だけを濃くする（D5）** — 自前の SVG と素の JS で描き、ライブラリ・CDN を足さない（ページ1枚で、描く量が小さいため）
- **届き具合は、つなぐ先の状態のうちいちばん悪いもの（D6）** — 1つでも届いていなければ、要望は届いていない。平均や多数決にすると、落ちたものが隠れる
- **全件に `trace` を必須にする。つなぐ先が無い要望は `none` を理由付きで書く（D7）** — 書き忘れと「つなぐ先が無い」を区別するため。必須にしないと、書いた要望だけが図に出て、書いていない要望が黙って消える
- **図に出すのはテストと結果まで（D8）** — ソースのファイル・ディレクトリと API は出さない（量が多く、要望から先は画面・テストで十分たどれる）。集約・イベントは DDD の層として出す

## 不安定な E2E のスキップ（2026-10-27）

人間の要望（[不安定な E2E は、いったんスキップにして直す要望を起票する](../../backlog/e2e-flaky-skip.md)）。`retries` を足さない方針（不安定なテストが CI を通り「確認済」に見える）を保ったまま、たまに落ちるテストで PR の CI が止まり続けないようにする。P5 の人間レビューでは、スキップだけの UC が「落ちた」と出ることも指摘された。設計は `docs/plans/2026-10-27-P6-不安定なE2Eのスキップ.md`。

- **スキップを認めるのはユースケースの E2E だけ（D2）** — smoke が落ちるのは画面の不具合の合図なので、スキップで逃がさない。Biome の `noSkippedTests` は抑制コメント1行で通り、トレースでは黙って「テストなし」になるので、抑制コメントがあっても検査で止める
- **一部だけスキップなら、スキップでないテストの状態で出す（D5）** — 同じ UC を別のテストが通していれば、その UC は確かめられている。全部スキップのときだけ「全スキップ」にする。ルールとの対応の見方の「スキップのみ」と同じ考え方
- **UC の段ではスキップがいちばん弱く、要望の段では落ちたの次に悪い（D6）** — UC の段は「この UC を確かめられているか」を見るので、ほかのテストが通っていればよい。要望の段は「届いていないものを目立たせる」ので、壊れていると分かっていて直す要望がある全スキップを、まだ作っていない（未実装）・まだ書いていない（テストなし）より悪くする。完了の要望が全スキップなら未達も付く
- **スキップは宣言の形だけ（D9）** — 書き方を1つにして静的に読めるようにする（本文の中の条件付きのスキップは、走ってみないと分からない）。ステップ単位にしないのは、後のステップが前のステップの画面の状態に頼る通しで、途中だけ飛ばせないため
- **全スキップにするのは、`skipped` で直す要望の注記があるテストだけ（D12）** — 注記の無い `skipped` は serial の手前の失敗などで走らなかったテストなので、今どおり「手前で止まった」。注記があっても通った・落ちたならその状態で出す（注記の消し忘れで落ちたのを隠さない）。注記は `tests[]`（静的な注記）と `results[]`（実行時の注記）の両方を見て、Playwright のどちらか片方の作りに頼らない
- **「開いている」要望は、通す側の一覧で決める（D16）** — 空・打ち間違いの状態を黙って通さない。後片付けの漏れを探す `branch-id.mjs` の一覧（進行中を含まない）とは用途が違うので共有しない
- **ラベルを分ける（D7）** — UC・要望の状態は「全スキップ」、テストの一覧の各テストは「スキップ中」。ルールとの対応の見方の「スキップのみ」は、Vitest の `skip`・`todo` をまとめたもので直す要望へのリンクを持たないので、別の言葉にした
- **Vitest のスキップは、トレースでは「テストなし」のまま** — Vitest には直す要望の注記の決まりが無く、スキップが不安定のためか分からない。E2E とは非対称だが、今回のスコープの外にした

採らなかった案：

- `retries` を足す（D8。上記の方針のとおり）
- Biome の GritQL プラグインで注記を必須にする — 構文の形は書けるが、要望の状態と `trace` は見られず、自前の検査が要る。検査を2か所に分けないため、既にテストのファイルを読んでいる `check-usecase-tags.mjs` に足した
- 機能の PR の中でスキップを入れる（D15）— プランにない変更になり、実装の AI が止まる

## 採らなかった案

- ユースケースの表に要望の列を足す（D1。上記）
- つなぎ先に要望の ID を使う（要望のファイル名で指すので、別の ID は要らない）
- 絞り込み（状態・マイルストーン・コンテキスト）とズーム — 要素が増えて読めなくなったら検討する
- RDRA の要求モデル（要望の手前の「要求」）と、人の目線の業務フロー — 次のサイクルで、このページに層を足す形で検討する
