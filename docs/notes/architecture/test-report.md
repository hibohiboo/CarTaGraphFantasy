# デザイナーノート：テストレポート

対応する定義：[テストレポート](../../architecture/test-report.md)

## 書いた経緯（トレースのページ、2026-10-26）

人間の要望（[アイデアから実装までをたどれるようにする](../../backlog/trace-report.md)）。RDRA とドメイン駆動設計を合わせて、アイデアから実装まで一貫して見られる図で開発を管理したい。目的は、アイデアが実装・テストまで届いているかを見ること。ユースケースごとの結果のページ・ルールの節ごとの結果のページは、それぞれ1つの層の結果しか見せず、要望から先をたどれなかった。

## 決めた理由

- **要望からのつながりは、要望ファイルの `trace` に書く（D1）** — 要望ごとに「どこで確かめるか」を決めるのは要望を書く人。ユースケースの表に要望の列を足すと、要望が増えるたびに表が横に伸びる。要望の先頭に書けば、要望を開けばつながりが読める
- **要望は画面・ルールの節にも直接つなげる（D2）** — 画面の要望（PL のホームなど）やルールの要望は、ユースケースを持たない。ユースケースだけにつなぐと、そうした要望の届き具合が見えなくなる
- **状態は最新のテストの結果まで出す（D3）** — つながりだけでは「書いてある」ことしか分からない。デプロイがテストを流した後に組み立てる（usecase-report・rule-test-report と同じ）。仕様書サイト（VitePress）の中のページにはしない（結果が要るので、ビルド後のスクリプトで作る）
- **図は層ごとの列に並べ、押した要素の上流・下流だけを濃くする（D5）** — 自前の SVG と素の JS で描き、ライブラリ・CDN を足さない（ページ1枚で、描く量が小さいため）
- **届き具合は、つなぐ先の状態のうちいちばん悪いもの（D6）** — 1つでも届いていなければ、要望は届いていない。平均や多数決にすると、落ちたものが隠れる
- **全件に `trace` を必須にする。つなぐ先が無い要望は `none` を理由付きで書く（D7）** — 書き忘れと「つなぐ先が無い」を区別するため。必須にしないと、書いた要望だけが図に出て、書いていない要望が黙って消える
- **図に出すのはテストと結果まで（D8）** — ソースのファイル・ディレクトリと API は出さない（量が多く、要望から先は画面・テストで十分たどれる）。集約・イベントは DDD の層として出す

## 採らなかった案

- ユースケースの表に要望の列を足す（D1。上記）
- つなぎ先に要望の ID を使う（要望のファイル名で指すので、別の ID は要らない）
- 絞り込み（状態・マイルストーン・コンテキスト）とズーム — 要素が増えて読めなくなったら検討する
- RDRA の要求モデル（要望の手前の「要求」）と、人の目線の業務フロー — 次のサイクルで、このページに層を足す形で検討する
