# デザイナーノート：集約とドメインイベント

対応する定義：[集約とドメインイベント](../../architecture/aggregates.md)

## 決めた経緯

2026-10-16、[境界づけられたコンテキスト](bounded-contexts.md)に続けて決めた。AI が今の型と仕様（シナリオの公開・募集とセッション・セッションスナップショット・解放済みカードプール）から叩き台を出し、人間が次の3点を決めた。

- **シナリオ製作は「シナリオ」と「版」の2つ** — 版は作ったら変わらないので、別の集約にしても整合の心配が無い。版が増えても、製作者が直すシナリオは重くならない
- **今の Session を「セッション」と「セッションスナップショット」に分ける** — コンテキストを分けた（運営とプレイ）のに合わせる。プレイ側の名前は、仕様にある言葉「セッションスナップショット」（[グラフの役割](../../cartagraph/graph.md#セッションスナップショットとマージ)。PC のデータ全般にも広げてある）を使い、新しい言葉を作らない
- **書き方は関数型** — 集約は zod スキーマの型のまま、操作は「新しい集約とイベント」を返す純粋関数。今の Functional Core / Imperative Shell とそのまま揃う

「集約」という言葉は、用語集のタグの項目にあった「強い集約を持つ要素を、無理に個別カード化せずに表現する」とぶつかっていた。その考え方は既に撤回されていた（[カード・デッキのノート](../card-and-deck.md#デッキの再定義)）ので、用語集を正の仕様（[カルタグラフ構想](../../cartagraph/index.md#カルタグラフの構成要素)）に合わせて直し、ぶつかりを解いた。

## 採らなかった案

- **シナリオ製作を、下書き・掲載・版の3つにする** — 公開のたびに下書きと掲載の2つの集約をまたぐことになり、版番号を1ずつ増やす不変条件が集約の外に出る
- **シナリオ製作を1つにまとめ、すべての版を中に持つ** — 単純だが、版が増えるほど製作者の編集のたびに重くなる
- **Session を1つのまま保存する** — 提案が出たときの中断が1回の変更で揃う利点はあるが、運営とプレイのコンテキストを分けた意味が保存の単位で崩れる。中断は「提案が出た」イベントで後から合わせる
- **集約をクラスにする** — DDD の教科書には近いが、zod スキーマが型の正という今の方針と二重になる

## 気をつけること

- **提案が出てから中断するまでの間** — 「提案が出た」イベントで中断する形なので、反映されるまでの短い間はセッションが進行中に見える。GM 不在の募集から始めたセッションのドライバーは1人なので、その間に別の人が進めることは無いが、バックエンドで非同期に配信するなら、スナップショットの側でも裁定待ちの間はプレイを止める
- **「通常の募集からはセッション1つ」** — 募集を開始済みにすることとセッションを作ることは別の集約なので、二重に始めないことは募集の側の状態（開始済み）で止める

## 将来の候補

- **リポジトリ** — 集約ごとの保存の口。バックエンドに着手するときに、Neon（Postgres）のテーブルの単位と一緒に決める
- **既読のルール・グラフ・進化の集約** — それぞれ着手するときに決める
