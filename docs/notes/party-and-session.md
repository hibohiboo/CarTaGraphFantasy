# デザイナーノート：パーティー編成と非同期セッション参加

対応する仕様：[パーティー編成と非同期セッション参加](../cartagraph/party-and-session.md)

## 経緯

ドライバーとナビゲーターをはじめ、このページの参加モデルは grilling による深掘りで決めた。

じっくり進行の中身（戦闘の具体的な判定・ダイスなど）は、この論点では範囲外として保留し、後から[戦闘ルール](../cartagraph/combat.md)・[判定ルール](../cartagraph/check.md)として決めた。

## ドライバーを1人にした理由

手軽に非同期で遊びたい、という動機による。戦闘でカードを逐次選択する駆け引き（[戦闘ルールのノート](combat.md#カウント制の考え方)）も、この決め方の理由の一つ。

## 既定ですべて反映することにした経緯

はじめは、セッションの結果を PC データへフィードバックするかを、PC の所有者が選ぶとしていた。他人に貸した PC が望まない方向に変化することを防ぐため。

2026-10-16、[中核のユースケース](../architecture/use-cases.md)を書いていて、PC 発見グラフへのマージも所有者が選ぶのかが決まっていないとわかった。人間が、セッションを PC の経験として採用するか、なかったことにするかを1つの選択とみなし、既定ではすべてを経験として反映すると決めた（発見グラフも PC データも）。「なかったことにしたい」という要望が出るまで、選ぶ仕組みは作らない（YAGNI）。選ぶ仕組みは[要望](../backlog/pc-session-opt-out.md)に置いた。

## 反映する結末を「最後に入った結末」にした経緯

2026-10-17、[イベントの流れ](../architecture/event-flows.md)（イベントストーミング）を書いていて、GM 不在でないセッションでは、結末のノードへ進んでも GM が終了を宣言するまで終わらないため、終わったときにどの結末の結末タグを反映するかが決まっていないとわかった。人間が、GM 不在のセッションと同じく「結末のノードへ入ったこと」で決め、終了の宣言の時点で最後に入った結末を使うと決めた。結末のノードに入らずに終えたら結末タグは付けない。

採らなかった案：終了を宣言するときに GM が結末を選ぶ（シナリオから外れた終わり方にも対応できるが、終了の操作が重くなる）。

## GM が描写のたびに選択肢を配れるようにした経緯

はじめは「新しい提案が出たときだけ GM が選択肢を追加する」としていた。GM があらかじめ選択肢カードを用意しておけば、ドライバーはそれを選ぶだけで進められる、という前提だった。2026-10-03、GM が PL を兼ねて結末まで遊ぶ機能（`docs/plans/2026-10-03-GMがPLを兼ねて遊ぶ.md`）で、[場・手札・プレイ](../cartagraph/play-and-field.md#gmレスセッションでの選択肢の描写)の「人間GMのセッションでは、選択肢を選ぶとGMの描写を待つ」（GM が結果を描写し、次の選択肢を配る）流れと食い違うことがわかった。選択肢を用意していないシナリオでは、GM が描写のたびに配らないと先へ進めない。そこで、GM は描写のたびに配ってよい、提案が出たときはそれに応えて追加する、に改めた。

## 中断を終了から一時停止に変えた経緯

はじめは「一定期間反応がなければ中断扱い」を、セッションの終了条件の1つとしていた。2026-10-04、GM 不在の募集（`docs/plans/2026-10-04-GM不在の募集.md`）で、提案の裁定待ちのあいだセッションを止め、GM の裁定後にドライバーが再開する形を作るとき、同じ「中断」を使うことにした（人間の判断）。そのため中断を、終了ではなく再開できる一時停止として定義し直し、理由（無反応／提案の裁定待ち）を持たせた。無反応の中断をいつ・誰が再開できるかは、未解決論点に残した。

2026-10-10、中断と再開の権限を決めた（人間の判断）。中断はドライバーもGMもでき（理由に「ドライバーかGMが中断した」を足した）、再開（PCがまた遊べるようにすること）もドライバーとGMのどちらもいつでもできる（候補にはナビゲーターもあったが、外した）。GMだけに許すのは、裁定待ちのような状態を変えることで、提案の裁定待ちはGMが裁定するまで解けない。途中、再開をGMだけに限る案で書きかけたが、「再開」の指すものが人間と AI でずれていた（人間は裁定待ちなどの状態を変えることを指していた）とわかり、この形に落ち着いた。

同じ日に、「一定期間、参加者から反応がなかったら中断する」もやめた（人間の判断）。何日で中断するかは考えず、止めたいときはドライバーかGMが任意で中断する。提案の裁定待ちのタイムアウト（[場・手札・プレイ](../cartagraph/play-and-field.md#タイムアウト)）も、この無反応の中断を当てていたので、タイムアウトは無しになった。あわせて、GMが中断中のセッションに絞って確かめられるようにする（[要望](../backlog/gm-resume-suspended.md)）。

## 通常進行・じっくり進行と呼ぶことにした経緯

はじめは「軽量モード」「濃密モード」と呼んでいた。2026-10-16、ドメイン知識の設計の中で、人間が「濃密モードは耳慣れない言葉であまりよくない」と出した（[要望](../backlog/progress-mode-names.md)）。候補は、通常進行／じっくり進行、ダイジェスト／クローズアップ、通常シーン／山場、カード進行／手番進行、さくさく／じっくり。中身が戦闘と NPC との会話の両方にまたがるので、どちらかに寄った言葉（手番・山場）は採らず、細かさだけを表す「通常進行」「じっくり進行」にした（人間の判断）。あわせて「モード」をやめて「進行」にし、「非同期セッションの進行」と言葉をそろえた。

コードの識別子（`Session.mode` の `'light'`・`'dense'`、シーンの `dense`）は変えていない。API とシナリオの JSON も変わらない。
