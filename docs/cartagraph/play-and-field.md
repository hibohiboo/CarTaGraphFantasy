# 場・手札・プレイ

デッキ・場・手札・カードのプレイの4つの役割を整理する。

## 選択肢カードとGMの生成

イベントでは選択肢カードをPLに渡し、そこから選んで出してもらう。選択肢が足りなければPLが提案し、GMがその場で選択肢カードを生成してセッションに反映する。

```text
シナリオデッキ
      │
      ▼
  イベント発生
      │
      ▼
選択肢カードを生成
      │
      ▼
   PLに提示
      │
      ▼
PLがカードを選んで場に出す
      │
      ▼
    世界が変化
      │
      ├── 想定内 → シナリオに従って進行
      │
      └── 想定外
             │
             ▼
       PLが新しい案を提案
             │
             ▼
       GMが選択肢カード化
             │
             ▼
       場に出してセッションへ反映
             │
             ▼
          セッションログ
             │
             ▼
       後から人間が発見・評価
             │
             ▼
       シナリオ等の進化候補
```

「選択肢カードが存在しない＝選択できない」ではない。

```text
Aカード、Bカードが提示されている
→ PL「Cもできませんか？」
→ GM「ではCという選択肢カードを作ります」
→ Cカードが場に出る
→ 世界がCを選んだ結果に進む
```

となる。「選択肢カード」はシナリオの固定された分岐ではなく、その時点でPLに提示されている**世界への介入可能性**になる。

例：

```text
【イベント】
古びた扉を発見した

     ↓

┌────────┐ ┌────────┐
│ 開ける   │ │ 調べる   │
└────────┘ └────────┘

      PL「壊してみたい」

             ↓

        GMが生成

        ┌────────┐
        │ 破壊する │
        └────────┘

             ↓

          場に出す

             ↓

      【扉が破壊された】
```

GMは、PLに一時的に渡した選択肢カード（ノードに入ったときやカードの効果で配られたもの・GMがその場で生成したもの）を、プレイされる前に手札から取り下げられる。

## 場・デッキ・カードの関係

- **デッキ** ＝ まだゲームに投入されていない可能性・情報のパッケージ
- **場** ＝ 現在のセッションで有効になった情報
- **カード** ＝ 世界を構成する意味のある単位

場は単なる画面上のUIではなく、**現在のセッションで有効になっているカードの集合**と定義する。

```text
シナリオデッキ
    ↓ カードを出す
┌──────────────┐
│       場       │
│                │
│ NPCカード      │
│ 場所カード     │
│ 選択肢カード   │
│ 状態カード     │
│ PL生成カード   │
└──────────────┘
    ↓
カードの移動・追加・除去・反転
    ↓
セッションの状態が変化
```

## 「場に出す」と「プレイする」は別の状態

「カードを場に出すこと」と「カードをプレイすること」は区別する。例えば「森」というロケーションカードが場に出ている状態と、「森へ行く」という選択肢カードをPLがプレイした状態では意味が違う。

- **場にあるカード** ＝ 現在の状況・可能性
- **プレイされたカード** ＝ プレイヤーが選択・実行したこと

## PLはカードをプレイすることでセッションに干渉する

これを原則として置く。

```text
現在の状況
    ↓
GMから選択肢が提示される
    ↓
┌────────────────────┐
│ PLの手札             │
│ ・能力カード         │
│ ・アイテムカード     │
│ ・特徴カード         │
│ ・選択肢カード       │
└────────────────────┘
          ＋
┌────────────────────┐
│ GMから一時的に渡される │
│ 選択肢カード           │
└────────────────────┘
          ↓
       PLが1枚選ぶ
          ↓
       カードをプレイ
          ↓
     セッションに干渉
          ↓
       状況が変化
```

「選択肢が提示されている」ことと「選択肢をプレイした」ことは別の状態、という点が重要。

例：

```text
場：
「古びた扉」

GMから提示：
[ 開ける ] [ 調べる ] [ 戻る ] [ 新たな選択肢を提案 ]

PL：
「新たな選択肢を提案」をプレイ

↓
PLが「扉を壊したい」と提案

↓
GMが「扉を破壊する」カードを生成

↓
そのカードが選択肢としてPLに渡される

[ 開ける ]
[ 調べる ]
[ 戻る ]
[ 扉を破壊する ]

↓
PLが「扉を破壊する」をプレイ
```

## 「新たな選択肢を提案」カード

これを単なる便利機能ではなく、正式なカードとして扱う。つまり、

> 「カードに書かれていないことをする」ためのカードが、最初から存在する。

```text
選択肢カード
├─ 開ける
├─ 調べる
├─ 戻る
└─ 新たな選択肢を提案
```

## カードのプレイ＝世界への操作

「新たな選択肢を提案」だけが特殊なのではなく、カードのプレイそのものが世界への操作である。

```text
カードを見る
  ↓
カードを選ぶ
  ↓
カードをプレイする
  ↓
何らかの関係・状態・出来事が発生する
```

例えば：

- 「扉を開ける」→ 場に新しい場所カードが出る
- 「攻撃する」→ エネミーとの戦闘状態になる
- 「調べる」→ 情報カードが公開される
- 「仲間を説得する」→ NPCとの関係が変化する
- 「新たな選択肢を提案」→ 新しいカードが生成される

カード＝選択肢だけではなく、**カード＝セッションに対する操作・介入の単位**である（[カード・デッキの考え方](card-and-deck.md) の「カードはプレイによって生まれる」）。

```text
          ┌──────────────┐
          │   カードを持つ │
          └──────┬───────┘
                 ↓
          ┌──────────────┐
          │   カードを選ぶ │
          └──────┬───────┘
                 ↓
          ┌──────────────┐
          │   カードをプレイ│
          └──────┬───────┘
                 ↓
          ┌──────────────┐
          │ セッションが変化│
          └──────┬───────┘
                 ↓
          ┌──────────────┐
          │ 新しいカード等 │
          │    が生まれる  │
          └──────────────┘
                 ↓
              次の手番
```

セッションそのものが、カードを生産する装置にもなる。

## カードをプレイした結果として何が変化するのか

### 選択肢カード＝イベントカード

PLがプレイする「選択肢カード」と、場に置かれる「イベントカード」（シーンに設定されたイベントなど）は、同一の1枚のカードとして扱う。シーンに設定されたイベントも、実体としては場に置かれた（まだプレイされていない）イベントカードである。

カードは次の3要素を持つ。

- **発火条件** — 即時発火型（プレイ＝発火）と条件待ち型（場に置かれた状態で、何らかのトリガーを待つ）の両方があり得る。条件待ち型の条件は、特定のカードがプレイされること・ターン経過・場の状態などをGMが自由記述で設定する。機械的に自動判定せず、GMがその都度確認・判断してよい。GM不在のソロプレイでは例外として、システムがカードの「配る条件・使える条件」を判定する（[GM不在のソロの進行（仮ルール）](solo-village.md#配る条件使える条件)）。
- **効果** — 下記「基本操作セット」の組み合わせとして構造化して記述する。
- **GM向け補足** — 自由記述のヒント・裁定補足。GMは基本効果を目安にしつつ、状況に応じて采配してよい。

効果として場に追加されるカードは、シナリオ作者があらかじめ用意したものでも、GMがその場で生成したものでもよい（[カードは「プレイによって生まれる」こともある](card-and-deck.md#カードはプレイによって生まれることもある)）。

### 基本操作セット

イベント効果は、以下の基本操作の組み合わせとして表現する。GM不在のソロプレイでは例外として、基本操作に無い成長の効果（能力値を上げる、HP・＜行動値＞を与える、キャラクターデッキのカードを手放す）も使う（[GM不在のソロの進行（仮ルール）](solo-village.md#成長の効果)）。

1. 場にカードを追加する
2. 場からカードを除去する
3. カードを裏返す（裏⇔表）
4. カードを別のデッキへ移動する（手札など）
5. カードの状態タグを変更する
6. PLの手札に（一時的な）選択肢カードを配る
7. GM専用ゾーンからPL可視ゾーンへカードを移動する（秘匿解除）
8. 次のシーンへ進む（シナリオデッキの別のノードへ移る）

場（現在の状況・可能性）と手札（PLが選択・プレイできるものの集合）は別概念なので、「場への操作」と「手札に配る」は別の基本操作として区別する。

場のゾーン構造（GM専用ゾーン／PL可視ゾーン）については [カードの裏表](card-face-back.md) を参照。

#### 次のシーンへ進む

[シナリオの入れ子構造](scenario-flow.md#シナリオの基本構造)（導入→シーン→結末）のノード間を移る操作。

- 選択肢カードの効果として、移り先のノードを指定する。GMがその場で生成する選択肢カードにも移り先を指定できる。移ると、手札の選択肢カードは移り先のノードのもので配り直される
- 7（秘匿解除）との役割分担：7は場のカードをPLに見せる操作、8は「いまシナリオのどのノードにいるか」を移す操作である。シーンカードを公開する演出は、8に伴って7で行ってよい
- 結末のノードへ進んだとき、**GM不在のセッション（システムが進行するセッション）では、その時点でセッションが終了する**。GM不在でないセッションでは、GMが[終了を宣言](party-and-session.md#非同期セッションの進行)するまで終わらない
- シーン側に「目的」「終了条件」を持たせて遷移させるかどうかは、[未解決論点](../open-questions.md#次に詰める候補)のまま。8は選択肢カードの効果による遷移だけを扱う

## 提案の裁定待ちの間の状態遷移

「[新たな選択肢を提案](#新たな選択肢を提案カード)」カードをPLがプレイしてから、GMが採用／却下を裁定して場に反映するまでの間の振る舞い。

### 停止の粒度

セッション全体を「休止」状態にはしない。「提案に対する返答（採用カード化／却下）が来るまでは、その提案から生まれるはずの新しいカードが手札に用意されない」という緩やかな待ち状態に留める。専用の状態値は持たない。

例外：[GM不在の募集](scenario-flow.md#募集とセッション)から始めたセッションで、提案の扱いが「GM必須（GMが後から裁定）」なら、提案するとセッションは[中断](party-and-session.md#非同期セッションの進行)し、元の選択肢も選べない。GMが採用・却下したあと、ドライバーが再開する。

### 元の選択肢は選べるか

提案をプレイした後も、元の選択肢カード（例：「開ける」「調べる」「戻る」）は手札に残り、ドライバーはGMの裁定を待たずに選んで先に進められる。待つかどうかはドライバーの裁量に委ねる。GMの裁定が追いつく前に他の選択肢が先に選ばれた場合、提案カードが後から採用されても「今回は使われなかった」扱いとして、次項の却下相当の記録に残す。

### 却下の扱い

却下された提案は削除せず、却下ステータスのまま判断理由とあわせて記録を残す（[進化候補の却下](../concept/index.md#進化候補の評価)と同じ扱い）。却下された提案とその理由は、PLにも見える形（[PL可視ゾーン](card-face-back.md#場のゾーン構造)）に置く。

### タイムアウト

GMの裁定待ちに専用のタイムアウトルールは設けない。[非同期セッションの進行](party-and-session.md#非同期セッションの進行)にある「一定期間、参加者から反応がなければ『中断』する」を、GMの裁定待ちにもそのまま適用する。

### 採用時の検証

採用した提案を機械的に検証する仕組み（壊れた改編を拒否するなど）は持たない。GMがその場で選択肢カードを1枚生成するだけでよく、生成されたカードは[通常のカードと同じ構造](card-and-deck.md#カードはプレイによって生まれることもある)を持つ。壊れた改編を防ぐ判断はGMの裁量に委ねる。

## GMレスセッションでの提案の扱い

GM不在のセッション向けに、シナリオは「提案の扱い方」を次の3種類から選べるメタデータを持つ（[シナリオのメタデータ](scenario-flow.md#シナリオのメタデータ)）。

- **GM必須（デフォルト）** — 上記「[提案の裁定待ちの間の状態遷移](#提案の裁定待ちの間の状態遷移)」の通り、人間GMの裁定を待つ。[GM不在の募集](scenario-flow.md#募集とセッション)の画面では「GMが後から裁定」と呼び、提案するとセッションは中断する（同節の例外）。ソロ開始のセッションでは中断せず、裁定待ちのまま残る。
- **提案不可** — 「[新たな選択肢を提案](#新たな選択肢を提案カード)」カード自体を手札に出さない。GM不在でも成立するが、PLの自由な介入は許可しない。
- **自動解決** — 人間GMの裁定を待たず、提案文をそのまま（辞書形などへの機械的な変換のみ行い）採用する。創造的な言い換え・壊れた改編の防止といった人間の裁量は働かない。

「自動解決」はソロ開始のGM不在のセッションでのみ使う。GM不在でないセッションの振る舞いは変えない。

[GM不在の募集](scenario-flow.md#募集とセッション)では、提案の扱いはシナリオのメタデータではなく、募集でGMが選んだ値（GM必須＝GMが後から裁定／提案不可）を使う。自動解決は選べない。シナリオが提案不可なら、募集でも提案不可にする。

## GMレスセッションでの選択肢の描写

GM不在のセッションで、[次のシーンへ進む](#次のシーンへ進む)効果を持たない選択肢カード（「辺りを見回す」のような様子見の選択肢や、[自動解決](#gmレスセッションでの提案の扱い)で採用された提案カードなど）を選んだときの振る舞い。

- システムが、そのカードの説明文を描写として返す。説明文が無いカード（自動解決で採用された提案カードなど）は「〇〇は『△△』を試みた。」のような定型文を返す
- 選んだカードだけを手札から消し、ほかの選択肢は手札に残す。セッションは同じシーンに留まる（同じカードを繰り返し選ぶことはない）
- 行き止まりにならないのは、そのシーンに次のシーンへ進む選択肢があるか、提案の手段がある場合に限る。提案の手段は、[自動解決](#gmレスセッションでの提案の扱い)か、GM不在の募集の「GMが後から裁定」（GMが[次のシーンへ進む](#次のシーンへ進む)移り先を付けて採用できる）。GM不在で遊ばせたいシナリオの作者は、各シーンに先へ進む選択肢を用意する
- GM不在でないセッションの振る舞い（選択肢を選ぶとGMの描写を待つ）は変えない

## カード効果の「対象（Target）」指定方法

[基本操作セット](#基本操作セット)のうち、「PLの手札に選択肢カードを配る」「カードの状態タグを変更する」等、対象を必要とする効果の指定方法。

### 役割参照と実名参照の区別

PCを対象とする指定は、次の2種類に区分する。

- **役割参照** — シナリオ作者が事前に書くシナリオデータの中で使ってよい。シナリオ作者は執筆時点で、実際に参加するPCの実名を知らないため。
- **実名参照** — 特定のPCを名指しする指定。GMがセッション中にその場で使う（[提案の採用時のカード化](#提案の裁定待ちの間の状態遷移)など）専用とし、シナリオ作者データには使わない。

シナリオデータへの実名参照の混入を機械的に検出する仕組みは持たない。GM／シナリオ制作者の裁量に委ねる。

### 役割参照の種類

最初に用意する役割参照は次の2種類。

- **Party** — パーティー全員。
- **Driver** — カードをプレイする権限を持つドライバー本人。[ドライバーの離脱・交代](party-and-session.md#非同期セッションの進行)が起きても、常にその時点の担当者を指す動的な参照とする。

これ以外の役割参照（例：HPが最も低いPCなど条件付き参照）は、必要になった時点で追加する（追加しても既存データは壊れない設計とする）。

### NPC・エネミーへの対象指定

PCの「役割参照／実名参照」の区別は**PC専用**の話とする。NPCカード・エネミーカードはシナリオ作者自身が定義したカードなので、シナリオデータの中で通常のカードID参照として直接指定してよい。

### 戦闘の対象選択（射程・グループ）との関係

[戦闘ルールの「射程・グループ」](combat.md#射程とグループ)によるプレイ時の対象選択とは別の仕組みとして扱う。射程・グループはPLが攻撃カードをプレイする瞬間に動的に選ぶ空間的な対象選択であり、Targetはカード定義側があらかじめ記述する配布・状態変更の対象である。
